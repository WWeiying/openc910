# Chips and Cheese 微信公众号文章规范

本文档记录以 SiFive P550 文章为基准形成的长期写作要求。后续处理 Chips and Cheese 的其他 CPU、SoC 和体系结构文章时，默认遵循本规范；用户对单篇文章另有要求时，以当次要求为准。

## 1. 成品定位

- 成品是适合微信公众号发布的中文体系结构教学文章，不称为“译注”。
- 保留英文材料的论证顺序、技术观点、测试观察、推测、保留意见和结论，不做生硬逐句翻译，也不能用概述代替关键正文。
- 中文表达以直接讲技术内容为主。不要反复使用“原文认为”“作者指出”“第三方认为”等审计式主语，也不要刻意把段落改成“我测试”“我认为”。
- 测试结果可写成“测试显示”“曲线表明”，推断可写成“较合理的解释是”“可能”“据此估计”，公开规格直接注明 SiFive、Arm、Eswin 等资料来源。
- 语言自然、连贯、有技术判断，少用模板化标签、机械清单和重复结论。

## 2. 完整性要求

- 写作前建立正文段落、标题和图表清单，逐段确认摘要、正文、测试方法、参数、负面结果、限制条件、结论和必要的文末信息均已覆盖。
- 不只保留漂亮结果。负面测试、没有找到某种现象的结果、候选解释、未知项和“尚不能判断”同样属于正文要点。
- 图表中的坐标、系列、单位、关键拐点、容量、位宽、频率、延迟、带宽和测试规模必须进入中文说明。
- 材料内部存在矛盾时并列保留。例如正文与图轴、总览图与详细测试、不同表格之间的容量差异，不能静默选择一种口径。
- 页面末尾若包含与文章直接相关的参考资料、支持入口或社区入口，可用简短自然的方式保留；排版控件、评论和推荐卡片不计入正文。

## 3. 证据边界

行文中必须始终区分以下内容，但不要给每一段机械粘贴方括号标签：

1. 厂商或项目公开规格；
2. Chips and Cheese 的微基准、计数器和曲线观察；
3. 根据测试拐点反推的容量、端口或内部组织；
4. 中文稿补充的通用体系结构分析；
5. RTL 明确确认的实现——只有确实提供并核对 RTL 时才能这样表述。

具体写法：

- 官方资料使用“数据表给出”“公开规格显示”。
- 实测使用“测试显示”“微基准测得”。
- 反推值保留“约”“可能”“似乎”“支持……判断”等限定。
- 没有 RTL 时，不把 BTB 层级、队列深度、调度拓扑、恢复算法或互连位宽写成确认实现。
- 中文补充只能解释通用机制以及现象可能意味着什么，不能倒推成该处理器已经采用某套具体逻辑。
- 单独进行的算术换算、图轴核对或跨图冲突分析不能冒充英文材料的结论。

## 4. 文章结构

推荐采用以下骨架，并根据材料特点灵活调整：

1. 中文标题；
2. 文首来源信息：英文标题、撰文者、首发平台、发布日期和原始链接；
3. 引言与产品背景；
4. 测试平台、对照平台和可比性边界；
5. 按英文材料的论证顺序展开前端、后端、存储系统和性能结果；
6. 在相关章节后插入显式的“体系结构视角：……”小节；
7. 保留材料自身的总评、批评、保留意见和技术演进判断；
8. 结尾可增加“体系结构视角：从该处理器可以看到的若干件事”，数量按内容决定，不机械固定为五点或六点；
9. 参考资料。

“体系结构视角”必须显式标出，使读者能够区分材料本身的测试叙述与中文稿补充的机制分析。不要改用“高层架构启示”“编者核查”“内容说明”等标题。

## 5. 体系结构教学深度

应根据材料覆盖范围解释以下主题：

- 前端：方向预测、BTB、间接目标、RAS、取指、对齐、译码与重定向；
- 流水线：级数、误预测代价、前后端填充与反压；
- 重命名和乱序：物理寄存器、ROB、checkpoint、恢复、精确异常；
- 调度与执行：调度器分区、端口可达性、依赖链延迟、吞吐与回写冲突；
- Load/Store：AGU、LSQ、内存依赖、Store forwarding、未对齐和跨页慢路径；
- 地址翻译：L1/L2 TLB、TLB reach、页表遍历和并发度；
- Cache：容量、相联度、bank、命中延迟、带宽、MSHR 和内存级并行；
- 多核系统：共享 L3、fabric、目录一致性、核间传输、NoC、内存控制器和 DRAM。

对重要机制尽量回答：

- 它解决什么问题；
- 正常情况下如何工作；
- miss、冲突、异常或资源满时如何阻塞和恢复；
- 对 IPC、单次延迟、稳态吞吐和能效有什么影响；
- 可以用哪些微基准、体系结构计数器或 RTL 状态验证。

验证建议必须使用公开、通用的事件和状态描述。未公开 P550 专用 PMU 编码时，不凭空发明事件名；没有 RTL 时，不凭信号名称猜测实现。

## 6. 图表处理

- 提取全部正文关键图表，保持出现顺序，不直接嵌入网页截图或 PDF 页面。
- 图目录命名为 `<article_slug>_figures/`，图片使用英文文件名和两位数字序号，例如 `01_microarchitecture_overview.png`。
- 文件扩展名必须与真实编码一致；上传前检查 PNG/JPEG/WebP 的 MIME，必要时转换格式。
- 每张图都需要中文图题和图解。图解至少覆盖：图中内容、坐标或配置、关键数据、读图结论，以及最重要的证据边界。
- 只有网页真正提供的 `figcaption` 才称为英文正式图注；其他中文说明属于辅助读图，不冒充原始图注。
- 密集矩阵、三维曲面和模块框图保持可点击查看的原尺寸，不二次裁切或覆字修正。
- 图内的问号、近似号、拼写差异和内部矛盾保留，并在正文自然解释。

## 7. Benchmark 与可比性

- 明确测试版本、编译器与参数、输入、单核或多核、频率、平台、页大小、预热、重复次数和误差；材料没有给出的项目必须明确为未披露，不能自行补齐。
- 区分 cycles、ns、B/cycle、GB/s、IPC、MPKI 等指标，不做无依据换算。
- 跨 ISA、跨 SoC、跨频率或跨软件栈比较时，只讨论材料能支持的结构趋势，不升级为产品总排名。
- 容量拐点通常同时受真实容量、冲突和别名影响，不能仅凭一张曲线识别具体预测算法或阵列组织。
- 单个微基准只能说明对应机制，不能外推到全部应用；SPEC 等套件还要说明版本、编译参数、输入和估算方法。

## 8. 微信公众号表达

- 专业术语首次出现时给出自然中文和英文名称或缩写，之后使用一致写法。
- 以短段落为主，避免连续大表格和过长清单；参数关系复杂时优先用原图配合文字分析。
- 标题应体现最有价值的体系结构矛盾或设计取舍，避免夸张结论。
- 文首直接显示出处和链接；正文不再重复大段来源声明。
- 不使用“内容性质”“内容说明”“译注”“编者核查”“高层架构启示”等栏目或措辞。
- 公众号正文可以明确使用“体系结构视角”，但其内容必须是实质机制分析，而不是泛泛感想。

## 9. 固定交付物

每篇公众号文章原则上生成：

- 母稿：`<article_slug>_wechat_article_zh.md`；
- 图片目录：`<article_slug>_figures/`；
- WeMD 副本：`<article_slug>_wechat_article_zh_wemd.md`；
- 发布资料：`<article_slug>_wechat_publish_kit.md`。

WeMD 固定主题：

```yaml
theme: custom-1786280678341-jnfpaqasm
themeName: "学术论文 (副本)"
title: "<article_slug>_wechat_article_zh"
```

使用以下命令生成 WeMD/COS 副本：

```bash
prepare-wemd-cos article/chipsandcheese/output/<article_slug>_wechat_article_zh.md
```

- 腾讯云 COS 图片应为 HTTPS 可匿名读取，存储桶保持公有读、私有写。
- SecretId、SecretKey 等凭据只放在本地安全配置或环境变量中，绝不写入仓库。
- 脚本应复用相同内容的缓存对象，避免重复上传。
- `article/chipsandcheese/input/` 中下载的网页及伴随资源不纳入 Git；`article/chipsandcheese/output/` 中的文章、图表和发布资料需要纳入版本管理。

发布资料至少包含：正式标题、署名、来源、日期、原始链接、摘要、封面文案、分享文案、备选标题、标签、栏目、图片说明、移动端排版、后台设置和发布前检查项。

## 10. 发布前静态检查

完成后逐项核对：

- 正文段落、图表、参数、测试条件、负面结果和结论均已覆盖；
- 公开规格、实测、反推、教学补充和 RTL 结论没有混写；
- 所有近似值、未知项和内部矛盾仍然存在；
- 图片数量、图号和图注一一对应，本地链接全部有效；
- 母稿与 WeMD 除 H1、frontmatter 和图片 URL 外正文完全一致；
- COS URL 返回 HTTP 200，`Content-Type` 与图片格式一致；
- Markdown 能通过 Pandoc 解析，`git diff --check` 无格式错误；
- 没有 `TODO`、`TBD`、断链、错误文件名或凭据；
- 没有把其他平台、其他核心或 SoC 结果错误归因到被测 CPU IP；
- 只修改本篇文章相关文件，不触碰工作区中无关的用户改动。

## 11. 完成后的提交与推送

- 一篇公众号文章的母稿、图片、WeMD 副本、发布资料和静态检查全部完成后，默认继续执行 Git 提交并 push，不再等待用户另行提醒；用户当次明确要求暂不提交或暂不推送时除外。
- 本工作区默认直接使用当前分支，不为公众号文章单独新建分支；如果用户另有分支要求，以当次要求为准。
- 提交前必须用 `git status` 和 diff 再次确认范围，只暂存本篇文章、对应图片、WeMD/COS 清单及本次要求修改的规范文件。
- 工作区中已有的其他未跟踪文件、其他任务产物和用户改动不得顺带提交；混合工作区禁止使用不加选择的 `git add -A`。
- 提交信息使用简洁英文，能够明确指出处理器或文章主题；提交后 push 当前分支，并核对本地提交与远端分支一致。
- push 失败时保留本地提交，说明失败原因和可恢复状态，不用破坏性 Git 命令回退用户文件。

## 12. SiFive P550 成稿形成的关键经验

- 最自然的风格是直接陈述技术观察，而不是在每段前重复来源归属。
- 不能为了行文简洁删掉负面结果。例如找不到单端口 FP 操作、未对齐访问的额外指令、测试方法缺失和曲线归属不清都必须保留。
- “约 32 项 BTB”“约 96 项 ROB”“约 16 项 RAS”等微基准反推不能写成官方确定参数。
- 图文冲突必须保留。P550 未对齐 Load/Store 的 1062/741 周期在正文与图轴之间可能对调，不能擅自统一。
- 核心 IP 与 SoC 实现必须分开。DRAM、共享 L3 和核间传输包含 EIC7700X 互连、控制器、板级与软件因素，不能全部归因于 P550。
- “体系结构视角”应显式存在，但只承担教学补充；英文材料自身的判断和中文稿的机制推演不能相互冒充。
