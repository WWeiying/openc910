## 1. IDU 是什么

### 1.1 在处理器中的位置

```
┌──────┐   指令流    ┌──────────────────────────────────┐   就绪指令   ┌────────┐
│ IFU  │ ─────────▶ │              IDU                 │ ─────────▶ │ 执行单元│
│取指  │  (IBUF)    │  译码→重命名→发射→读寄存器        │  (8 管线)  │ IU/LSU │
└──────┘            └──────────────────────────────────┘            │ VFPU   │
                            ▲              │                         └────────┘
                            │ flush/alloc  │ create ROB                   │
                            └──────────────┴─────────────────────────────┘
                                      RTU（退休单元，含 ROB）
```

IFU 负责"**取什么指令**"（顺序+预测），IDU 负责"**指令怎么调度执行**"。
IDU 是**顺序到乱序的转换点**：它按程序顺序接收指令，但允许指令乱序执行，
最后由 RTU 按程序顺序退休（提交），从而对外表现为顺序执行（精确异常）。

### 1.2 IDU 的核心使命

1. **译码（Decode）**：把 RISC-V 指令字翻译成内部控制信号，识别指令类型、源/目的寄存器、立即数。
2. **拆分（Split）**：把复杂指令（向量、特殊指令）拆成多个微操作（micro-op）。
3. **重命名（Rename）**：把架构寄存器（x0-x31）映射到更大的物理寄存器池，消除假依赖（WAR/WAW）。
4. **发射（Issue/Dispatch）**：把指令分发到各功能单元对应的发射队列，乱序唤醒就绪指令。
5. **读寄存器（Read & Forward）**：从物理寄存器堆读操作数，或从执行单元旁路（前递）最新结果。

### 1.3 规模与复杂度

C910 是 **3 译码 / 4 分发 / 8 执行端口**的乱序超标量处理器：
- 每周期最多译码 **3 条**指令
- 每周期最多向发射队列分发 **4 条**指令（dispatch）
- 拥有 **8 条执行管线**（pipe0~pipe7）
- 拥有 **7 个发射队列**（aiq0/aiq1/biq/lsiq/sdiq/viq0/viq1）

IDU 是全核最大的单元：56 个 RTL 文件，约 10.4 万行。

## 2. 体系结构基础

> 如果你已熟悉乱序执行原理，可跳过本节；否则强烈建议精读，否则后续模块难以理解。

### 2.1 为什么要乱序执行？

顺序执行的处理器，遇到一条慢指令（如 cache miss 的 load）会阻塞后面所有指令，
即使后面的指令与它无关。乱序执行允许**无依赖的后续指令越过阻塞指令先执行**，
大幅提升指令级并行度（ILP）。

代价是：必须解决三类"冒险"，并保证程序语义正确。

### 2.2 三类数据冒险

```
RAW（写后读，真依赖）：  add x1, x2, x3   ← x1 被写
                        sub x4, x1, x5   ← x1 被读，必须等 add 完成
                        这是真正的依赖，无法消除，只能靠唤醒+前递加速

WAR（读后写，假依赖）：  add x4, x1, x5   ← x1 被读
                        sub x1, x2, x3   ← x1 被写，物理上不必等 add 读完
                        通过重命名消除

WAW（写后写，假依赖）：  add x1, x2, x3   ← x1 被写
                        sub x1, x4, x5   ← x1 又被写
                        通过重命名消除
```

WAR/WAW 之所以是"假"依赖，是因为它们源于**架构寄存器数量有限（只有 32 个）导致的复用**。
如果给每次写入分配一个全新的物理寄存器，这两类冒险就消失了——这就是**寄存器重命名**。

### 2.3 寄存器重命名原理

```
架构寄存器（程序可见）：x0 ~ x31（32 个）
        ↓ 映射
物理寄存器（硬件实际）：p0 ~ pN（远多于 32 个）

重命名表（RAT, Register Alias Table）记录：每个架构寄存器当前映射到哪个物理寄存器。

例：
  指令          架构视角        重命名后（物理）       RAT 更新
  add x1,x2,x3  x1=x2+x3        p10=p2+p3            x1→p10
  sub x1,x4,x5  x1=x4+x5        p11=p4+p5            x1→p11（旧 p10 仍保留）
  or  x6,x1,x7  x6=x1+x7        p12=p11+p7           x6→p12（x1 读最新的 p11）
```

两条写 x1 的指令分别用 p10、p11，WAW 消失；后续读 x1 总是读 RAT 里最新的映射 p11，正确。

### 2.4 唤醒-选择（Wakeup-Select）

发射队列中的指令在等待其源操作数就绪。当某条指令执行完、产生结果时，
它广播自己的目的物理寄存器号；所有发射队列项比对：如果我的某个源等的就是这个号，
就把该源标记为"就绪"（**唤醒**）。当一条指令所有源都就绪，它成为发射候选；
仲裁逻辑从多个候选中**选择**一条发射（通常按年龄/优先级）。

C910 的唤醒由发射队列 entry 内的依赖项（`dep_*` 模块）完成，是乱序调度的心脏。

### 2.5 投机执行与精确异常

分支预测让 IDU 投机地处理预测路径上的指令。一旦预测错误或发生异常，
RTU 发出 **flush**，IDU 必须冲刷所有错误路径上的指令，并恢复重命名表到正确状态。
这要求 IDU 维护足够的恢复信息（重命名表的检查点/历史）。

## 3. IDU 四级流水总览

```
        IBUF（来自 IFU）
            │ 每周期最多 3 条指令
            ▼
┌───────────────────────────────────────────────────────────────┐
│  ID 阶段（Instruction Decode，译码）                            │
│   • 3 路并行译码（id_decd ×3）                                  │
│   • 复杂指令拆分（split_long / split_short）                    │
│   • fence 处理（id_fence）                                      │
│   控制：id_ctrl   数据通路：id_dp                               │
└───────────────────────────────────────────────────────────────┘
            │ pipedown 最多 4 条微操作
            ▼
┌───────────────────────────────────────────────────────────────┐
│  IR 阶段（Instruction Rename，重命名）                          │
│   • 分配物理寄存器，更新重命名表                                │
│   • 整数表 ir_rt / 浮点表 ir_frt / 向量表 ir_vrt               │
│   控制：ir_ctrl   数据通路：ir_dp（含 ir_decd）                │
└───────────────────────────────────────────────────────────────┘
            │ dispatch 最多 4 条
            ▼
┌───────────────────────────────────────────────────────────────┐
│  IS 阶段（Instruction Select/Issue，发射）                      │
│   • 分发到 7 个发射队列                                         │
│   • 唤醒-选择，乱序发射                                         │
│   • 向 RTU 创建 ROB 表项，向 LSU 创建 VMB                       │
│   控制：is_ctrl   数据通路：is_dp（含 is_pipe_entry）          │
│   队列：aiq0 aiq1 biq lsiq sdiq viq0 viq1                       │
└───────────────────────────────────────────────────────────────┘
            │ launch 到各管线
            ▼
┌───────────────────────────────────────────────────────────────┐
│  RF 阶段（Register File read，读寄存器）                        │
│   • 从物理寄存器堆读操作数                                      │
│   • 前递网络旁路最新结果（rf_fwd）                             │
│   • 各管线指令最终译码（rf_pipe0-7_decd）                      │
│   控制：rf_ctrl   数据通路：rf_dp   寄存器堆：rf_prf_*regfile  │
└───────────────────────────────────────────────────────────────┘
            │ 操作数 + 控制信号
            ▼
        8 条执行管线（IU / LSU / VFPU）
```

**关键时序观念**：ID/IR/IS/RF 是**顺序流水**的前端（in-order front-end），
指令在这四级中保持程序顺序；只有进入发射队列后，才开始**乱序**（out-of-order）发射执行。

## 4. ID 阶段：译码

**模块**：`id_ctrl`（控制）、`id_dp`（数据通路）、`id_decd ×3`（译码器）、
`id_split_long/short`（拆分）、`id_fence`（屏障）、`id_decd_special`（特殊指令）

### 4.1 三路并行译码

ID 阶段每周期从 IBUF 接收最多 3 条指令（inst0/1/2），用 3 个相同的 `id_decd` 实例并行译码。
译码产生每条指令的：指令类型、功能单元归属、源/目的寄存器号、立即数、是否分支/访存/向量等。

### 4.2 指令拆分（Split）

某些指令一条无法对应单个微操作，需要拆分：
- **短拆分（split_short）**：拆成 2 个微操作。如某些 load-pair、特殊运算。
- **长拆分（split_long）**：拆成 2 个以上微操作。主要是**向量指令**——一条向量指令按
  元素组或访存粒度可能拆成很多微操作。`id_split_long.v` 高达 7600 行，是 ID 阶段最复杂的部分。

拆分的存在使得 ID 接收 3 条、却可能向 IR 下发 1~4 条（`pipedown 1/2/3 inst`），
具体下发几条由 id_ctrl 根据拆分情况和下游 stall 决定。

### 4.3 fence 处理

`id_fence` 处理 `fence` / `fence.i` / `sfence.vma` 等屏障指令。屏障要求严格的执行顺序，
ID 阶段需识别并施加必要的 stall，确保屏障前后的指令不被乱序重排越过。

**详见**：[01_id_ctrl](01_id_ctrl.md) · [02_id_decd](02_id_decd.md) · [03_id_dp](03_id_dp.md) · [04_id_split](04_id_split.md) · [05_id_fence](05_id_fence.md)

## 5. IR 阶段：寄存器重命名

**模块**：`ir_ctrl`、`ir_dp`（含 `ir_decd`）、`ir_rt`（整数）、`ir_frt`（浮点）、`ir_vrt`（向量）

### 5.1 三套独立重命名表

C910 有三类架构寄存器，各自独立重命名：

| 重命名表 | 文件 | 管理对象 | 规模 |
|----------|------|----------|------|
| `ir_rt` | ct_idu_ir_rt.v (5275 行) | 整数寄存器 x0-x31 | 整数物理寄存器池 |
| `ir_frt` | ct_idu_ir_frt.v (6114 行) | 浮点寄存器 f0-f31 | 浮点物理寄存器池 |
| `ir_vrt` | ct_idu_ir_vrt.v | 向量寄存器接口 | 当前开源 RTL 为常量输出占位实现 |

> F/D 的 f0-f31 与 V 的 v0-v31 是两套独立架构状态。`ir_frt` 有完整的 33 项
> 逻辑映射结构并连接 64 项浮点物理寄存器池；当前 `ir_vrt` 没有保存映射状态，
> 普通源返回物理编号 64 的越界哨兵及 ready/writeback 常量。阅读向量路径时必须把
> "接口仍存在"与"完整向量重命名已经实现"区分开。

### 5.2 重命名表的工作

每周期对下发的指令：
1. **查表**：每个源寄存器查 RAT，得到当前映射的物理寄存器号。
2. **分配**：为每个目的寄存器从空闲列表分配一个新物理寄存器。
3. **更新**：把目的架构寄存器的映射更新为新分配的物理寄存器。
4. **同周期旁路**：如果 inst1 的源是 inst0 的目的（同周期内的依赖），
   必须把 inst0 刚分配的物理寄存器号旁路给 inst1，而不是查到旧映射。这是重命名的关键难点。

### 5.3 精细 stall 设计

`ir_ctrl` 把 IS dispatch stall、IS type stall 与 IR 本级重命名资源 stall 分开
处理。需要特别注意生成源注释的概括与最终方程之间的边界：
`ctrl_ir_pipedown_stall = ctrl_ir_stage_stall || ctrl_is_dis_type_stall`，所以从 IR
取新槽的 valid **会考虑 type stall**；从 IS 保留 slot2/slot3 前移的选择分支则
不受该项阻断。dispatch stall 不直接串入每个局部 pipedown-valid 项，而由 IS
寄存器更新、create 有效和向 IR 的总反压共同处理。RTL 注释中的 “creg stall”
也不应擅自展开成 Committed Register；生效逻辑实际汇总 preg/vreg/freg/ereg
分配无效、flush stall 和 mispredict stall。该分层减少了单一总 stall 方程的
依赖集中，但实际关键路径收益必须由 STA 证明。

## 6. IS 阶段：乱序发射

**模块**：`is_ctrl`、`is_dp`（含 `is_pipe_entry ×4`）、7 个发射队列及其 entry、`dep_*` 依赖项

### 6.1 七个发射队列

每个发射队列对应一类功能单元。**深度并非一律相同**：AIQ0/AIQ1/VIQ0/VIQ1 为 **8 项**，
而 **BIQ/LSIQ/SDIQ 为 12 项**（分支与访存指令更多发、更长延迟，需更深缓冲；总容量
8+8+12+12+12+8+8 = **68 项**，由各 `*_entry_vld` 位宽 `[7:0]` vs `[11:0]` 可核实）：

| 队列 | 文件 | 深度 | 服务的功能单元 | 目标管线 |
|------|------|------|----------------|----------|
| `aiq0` | is_aiq0.v | **8** | ALU0 + 特殊指令（CSR/同步） | pipe0 |
| `aiq1` | is_aiq1.v | **8** | ALU1 + 乘法 MULT | pipe1 |
| `biq` | is_biq.v | **12** | 分支跳转 BJU | pipe2 |
| `lsiq` | is_lsiq.v | **12** | Load/Store 地址 | pipe3 / pipe4 |
| `sdiq` | is_sdiq.v | **12** | Store 数据 | pipe5 |
| `viq0` | is_viq0.v | **8** | 向量/浮点 0 | pipe6 |
| `viq1` | is_viq1.v | **8** | 向量/浮点 1 | pipe7 |

> AIQ = ALU Issue Queue，BIQ = Branch IQ，LSIQ = Load/Store IQ，
> SDIQ = Store Data IQ，VIQ = Vector IQ。

### 6.2 唤醒-选择机制

每个发射队列 entry 内含若干**依赖项**（`dep_reg_entry` / `dep_vreg_entry`），
每个依赖项追踪一个源操作数：记录它等待的物理寄存器号，监听执行单元的结果广播，
命中时把该源标记为就绪。当 entry 的所有源就绪，该 entry 成为发射候选。
队列的选择逻辑（如 `aiq_lch_rdy`）从就绪候选中选一条 launch 到管线。

C910 把唤醒逻辑下沉到独立的 `dep_*` 模块复用，是值得学习的模块化设计。

### 6.3 创建 ROB 表项与 VMB

IS 阶段在分发指令的同时：
- 向 **RTU** 发送 ROB 创建请求（`is_ctrl` 的 "reorder buffer create" 逻辑），
  为每条指令在 ROB 中占一项，记录退休所需信息。
- 向 **LSU** 创建 VMB（访存相关缓冲）表项（"LSU VMB Create" 逻辑）。
- 维护 **PST**（Physical Register Status Table，物理寄存器状态/释放跟踪）。

**详见**：[11_is_ctrl](11_is_ctrl.md) · [12_is_dp](12_is_dp.md) · [13_is_aiq](13_is_aiq.md) · [14_is_biq](14_is_biq.md) · [15_is_lsiq](15_is_lsiq.md) · [16_is_sdiq](16_is_sdiq.md) · [17_is_viq](17_is_viq.md) · [22_dep](22_dep.md)

## 7. RF 阶段：读寄存器与前递

**模块**：`rf_ctrl`、`rf_dp`（含 `rf_pipe0-7_decd`）、`rf_fwd`（含 preg/vreg）、`rf_prf_*regfile`

### 7.1 读物理寄存器堆

指令从发射队列 launch 后，进入 RF 阶段，用重命名得到的物理寄存器号从 PRF
（Physical Register File，物理寄存器堆）读出操作数。当前整数/浮点 PRF 由大量门控
寄存器单元和组合读选择构成，不应笼统称为 SRAM；向量 PRF 在公开配置中还是常量输出
占位路径。

### 7.2 前递（Forwarding / Bypass）网络

如果某操作数对应的物理寄存器**刚刚被某条执行指令写出、还没写回 PRF**，
直接从执行单元的输出旁路过来（前递），避免等待写回再读，节省周期。
`rf_fwd` 实现了庞大的前递网络：针对每条管线的每个源、每个写回端口都有比较旁路逻辑
（rf_fwd.v 实例化了大量 `rf_fwd_preg`/`rf_fwd_vreg`）。

前递是 RAW 真依赖背靠背执行（back-to-back）的关键——例如 `add` 后紧跟用其结果的 `sub`，
靠前递可以让 sub 在 add 写回前就拿到值。

### 7.3 各管线最终译码

`rf_pipe0-7_decd` 为每条执行管线做最终的控制信号译码，
生成送给对应执行单元（IU/LSU/VFPU）的精确操作码和控制位。
注意 `rf_dp` 实例化了 pipe0/1/2/3/4/6/7 的译码（**没有 pipe5**），
因为 pipe5 是 store data 路径，只搬运数据、无需复杂译码。

**详见**：[18_rf_ctrl](18_rf_ctrl.md) · [19_rf_dp](19_rf_dp.md) · [20_rf_fwd](20_rf_fwd.md) · [21_rf_prf](21_rf_prf.md)

## 8. 执行管线与发射队列映射

```
发射队列          执行管线         功能单元              结果写回 PRF？
─────────         ─────────        ──────────────        ─────────────
aiq0      ──────▶ pipe0    ──────▶ ALU0 + 特殊(CSR)      是（整数 preg）
aiq1      ──────▶ pipe1    ──────▶ ALU1 + 乘法 MULT      是（整数 preg）
biq       ──────▶ pipe2    ──────▶ BJU（分支跳转）       否（只产生跳转/flush）
lsiq      ──────▶ pipe3    ──────▶ LSU Load / AGU        是（load 数据，整数+向量）
          └─────▶ pipe4    ──────▶ LSU Store 地址        否
sdiq      ──────▶ pipe5    ──────▶ Store 数据            否（数据送 LSU）
viq0      ──────▶ pipe6    ──────▶ VFPU0（向量/浮点接口）是（浮点/向量编号接口）
viq1      ──────▶ pipe7    ──────▶ VFPU1（向量/浮点接口）是（浮点/向量编号接口）
```

**写回端口**（从 top 接口确认）：
- `iu_idu_ex2_pipe0/pipe1_wb_preg` —— 整数 ALU 在 EX2 写回整数物理寄存器
- `lsu_idu_wb_pipe3_wb_preg / wb_vreg` —— LSU load 在 WB 接口写回整数或 vreg 编号空间
- `vfpu_idu_ex5_pipe6/pipe7_wb_vreg` —— VFPU 在 EX5 接口写回 vreg 编号空间

不同管线的执行延迟和可旁路时刻不同：整数路径暴露 EX1/EX2，VFPU 暴露多个
EX 阶段接口，LSU 还取决于命中、重放和存储次序。正因为生产者完成时间不一致，
调度器才需要分别追踪 ready、writeback 和当拍 forward 条件。

## 9. 物理寄存器与重命名机制

### 9.1 三类物理寄存器堆

| 寄存器堆 | 文件 | 用途 |
|----------|------|------|
| `rf_prf_pregfile` | 4052 行 | 整数物理寄存器（最大，多读写端口） |
| `rf_prf_fregfile` | 2229 行 | 浮点物理寄存器 |
| `rf_prf_vregfile` | 293 行 | 向量 PRF 接口；当前读数据均为常量 0，实例模板未激活 |
| `rf_prf_eregfile` | 911 行 | 32 项、每项 6 位的 EREG 数据文件；保存乱序 VFPU 操作产生的 `fflags` 等状态贡献，并在 RTU 许可后按位或送 CP0 |

配套 `rf_prf_gated_preg/vreg/ereg` 为各存储项生成局部时钟请求，目标是在无写入时减少
状态触发器的时钟活动。这里不能写成“空闲端口不耗动态功耗”：组合读 MUX、地址和
广播网络仍可能翻转；`gated_clk_cell` 的技术分支还受 global/module/scan 控制，且
未定义 `C910_USE_TSMC28_ICG` 时公开 RTL 直接令 `clk_out=clk_in`。实际停钟和功耗
收益应以编译配置、综合网表和功耗报告为准。

### 9.2 写回-唤醒-前递的协同

```
执行单元产生结果
   ├─▶ 写回 PRF（供后续指令读）
   ├─▶ 广播物理寄存器号 → 发射队列唤醒等待该号的指令
   └─▶ 前递给正在 RF 阶段的指令（绕过 PRF 写-读延迟）
```

这三条路径并行工作，共同支撑乱序核的高吞吐。

**详见**：[21_rf_prf](21_rf_prf.md)

## 10. 关键数据结构

### 10.1 ROB（Reorder Buffer，重排序缓冲）

**ROB 实体在 RTU 模块中**，不在 IDU。IDU 的 IS 阶段负责**创建** ROB 表项
（`is_ctrl` 输出 create enable 给 RTU）。ROB 按程序顺序记录所有在途指令，
保证它们**按序退休**——即使乱序执行，也按程序顺序提交结果、处理异常，实现精确异常。

`rtu_idu_alloc`（top 中接口最多的信号组）传递 ROB 分配信息：
RTU 告诉 IDU 当前 ROB 的空闲表项指针（IID）。

### 10.2 IID（Instruction ID）

每条指令分配一个 IID，作为它在 ROB 中的唯一标识。IID 贯穿整个乱序执行：
发射队列、执行单元、写回、退休都用 IID 关联同一条指令。
flush 时通过 IID 比较判断哪些指令需要冲刷（年龄比较）。

### 10.3 PST（Physical register Status Table）

跟踪物理寄存器的状态（是否已分配、是否可释放）。指令退休时，
其目的寄存器映射的旧物理寄存器可以释放回空闲列表，PST 管理这一回收。

### 10.4 flush 恢复

`rtu_idu_flush`（接口第二多）是 RTU 发起的冲刷信号。预测错误或异常时，
IDU 据此冲刷错误路径指令，并把重命名表恢复到 flush 点的正确状态。

## 11. 完整指令流串讲

以 `add x1, x2, x3`（一条普通整数加法）为例，走完 IDU 全程：

```
【ID 阶段】
  IBUF 送来 add 指令字
  → id_decd 译码：识别为 ALU 整数运算，目的 x1，源 x2/x3，无立即数运算
  → 非拆分指令，pipedown 1 条到 IR

【IR 阶段】
  → ir_rt 查表：x2→p20, x3→p25（当前映射）
  → ir_rt 分配：为 x1 分配新物理寄存器 p30
  → 更新 RAT：x1→p30
  → 指令变为：p30 = p20 + p25，归属 ALU，分发到 IS

【IS 阶段】
  → is_ctrl 选择队列：ALU 整数 → 进 aiq0（或 aiq1 负载均衡）
  → 在 aiq0 占一个 entry，两个源依赖项分别追踪 p20、p25
  → 同时向 RTU 创建 ROB 表项，得到 IID
  → 唤醒：等 p20、p25 都就绪（若已就绪则立即）
  → 两源就绪 → 成为候选 → 选择逻辑 launch 到 pipe0

【RF 阶段】
  → 用 p20、p25 从整数 PRF 读操作数
  → 若 p20/p25 是上一拍刚算出的，走 rf_fwd 前递拿最新值
  → rf_pipe0_decd 生成 ALU0 控制信号
  → 操作数 + 控制 → 送 pipe0（ALU0）执行

【执行（IU，IDU 之外）】
  → ALU0 计算 p20+p25，结果写 p30
  → EX2 写回 PRF；广播 p30 唤醒等待它的后续指令；前递给紧邻指令

【退休（RTU，IDU 之外）】
  → ROB 按序退休 add，x1 的旧物理寄存器释放
```

一条 load `lw x5, 0(x1)` 的关键差异：进 lsiq → pipe3 → AGU 算地址 → 访问 D-Cache →
若 miss 则延迟很多周期（此时乱序优势体现：后面无关指令照常执行）→ load 数据经 pipe3 写回。

一条向量指令的关键差异：在 ID 阶段被 `id_split_long` 拆成多个微操作 →
分别进 viq0/viq1 → pipe6/pipe7（VFPU，5 级 EX）→ 写回向量寄存器。

## 学习建议

IDU 比 IFU 抽象得多，建议：
1. **先吃透本总览第 2 节**（乱序原理），否则模块细节会失去脉络。
2. **重命名（IR）和发射（IS）是两大难点**，投入最多时间。
3. 把 `dep_*`（[22_dep](22_dep.md)）提前到发射队列之前读——它是唤醒机制的原子。
4. 对照 IFU 文档理解前后端衔接：IBUF 怎么把指令交给 ID。
