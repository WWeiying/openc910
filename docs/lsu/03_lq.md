# C910 Load Queue 详解（ct_lsu_lq）

> RTL 源文件：`ct_lsu_lq.v`（979 行）+ `ct_lsu_lq_entry.v`（380 行）×16
>
> LQ 是乱序访存正确性的监测结构：为仍在飞的 load 保存物理地址块、字节
> 有效掩码和 IID，供更老但后到达检查点的 store（RAW）或 load（RAR）反查
> 是否已有更年轻重叠 load 先执行。是否“已经拿到最终数据”还应结合创建/有效
> 条件和该 load 的完成路径判断，不能只由 entry `vld` 一个信号推断。

---

## 1. 为什么需要 LQ

C910 允许 load 乱序执行（只要 SQ 里没有发现重叠的老 store 就放行）。
两种赌局可能输：

| 违例 | 场景 | 后果 |
|------|------|------|
| **RAW**（load 越过老 store） | store 地址当时还没算出来，load 先跑了 | load 读到旧值 |
| **RAR**（load-load 顺序相关） | 更年轻的重叠 load 已先建立记录，较老 load 后到 DC 检查 | 在需要维护相关 load 顺序的配置下产生 spec fail；外部一致性写是其可能动机之一，但 LQ 比较器本身不观察 snoop 事件 |

输了的标志：**后到的老指令在 DC 级反查 LQ 时发现重叠的年轻项**。

## 2. 表项内容与比较逻辑（lq_entry.v）

每项记录：`PA[39:4]`、`bytes_vld[15:0]`、IID、第二段标志 `secd` 和有效位。
它不保存 load 数据、cache 命中位或“数据已返回”位。因而 LQ 能证明的是
某条满足创建条件的在飞 load 已建立地址范围记录，而不是单靠表项就证明该
load 已经取得最终体系结构数据。

### RAR 检查（lq_entry.v:290-322，由 ld_dc 的 load 发起）

```verilog
// 地址按 16B 粒度比较（PA_WIDTH-1:4）+ 字节位图相交
assign lq_entry_rar_addr_tto4_hit = (entry_pa[39:4] == ld_dc_pa[39:4]);
assign lq_entry_rar_do_hit  = |(lq_entry_bytes_vld & ld_dc_bytes_vld);   // L303
assign lq_entry_rar_spec_fail0 = lq_entry_newer_than_ld_dc    // 我(表项)比来查的更年轻
                              && ld_dc_inst_chk_vld
                              && addr_hit && do_hit;          // L307-310
```

`newer_than_ld_dc` 使用 RTU 的环形 IID 比较规则判断年龄，参见
[07_encode_compare.md](../rtu/07_encode_compare.md)。注意检查方向：
**表项是先跑的年轻 load，来查的是后到的老 load**——老 load 现在才执行，
说明两条相关 load 的执行顺序与程序年龄相反。RTL 命中条件只证明“年龄关系+
地址块相同+字节重叠”，并不直接证明两者之间真的发生过 snoop 写。
`cp0_lsu_corr_dis`会屏蔽该 RAR spec-fail 输出；是否应在某个单核系统关闭，
还取决于系统中是否存在 DMA/其他一致性主设备及软件内存模型要求，不能仅凭
core 数量决定。

非对齐双段访问有独立的 addr1 比较组（spec_fail1，L312-316）。

### RAW 检查（lq_entry.v:325 起，由 st_dc 的 store 发起）

同构：store 的 PA/bytes_vld 与每个**比它年轻**的 LQ 项相交 → raw_spec_fail。

## 3. 违例之后发生什么

LQ 命中只产生一个标记，处理链条很长：

```
lq_entry_raw/rar_spec_fail
  → 汇总到 ld_da/st_da 的完成信息 lsu_rtu_wb_pipe3/4_spec_fail
  → RTU 异常/恢复选择路径（../rtu/03_rob_expt.md，非普通 trap 的恢复原因）
  → 违例指令退休时 flush（spec_fail_flush + spec_fail_iid 通报 LSU）
  → 从 RTU 选定的精确恢复边界重取，相关 load 重新执行
  → 重放时可能由 SQ/WMB 前递，也可能等待依赖、访问 cache 或再次 restart
  → IFU/LSU 的 no-spec 相关机制可减少同类冲突再次发生
```

恢复边界和重放数据来源都不能由 LQ 单独决定。恢复代价不是固定“几十拍”：
它包含从检测到 RTU 精确恢复条件成立的等待、ROB 头距离、前端重定向后重新
供给，以及可能重新经历的 cache/TLB/依赖等待。评价影响时，应把当前运行的
spec-fail 次数与每次事件前后的退休断流周期关联，而不是使用另一轮测试的
固定次数和总周期估算。

还要区分两个机制层次：IFU 的 `ct_ifu_sfp`包含 PC 相关的 Store-Fetch
Prediction 状态；LSU 的 `ct_lsu_spec_fail_predict`只保存短期 store 地址、
字节掩码和 IID，围绕一次违例确认及重放产生 mark/hit。二者不能合并描述成
“LQ 训练一张 load-PC 表”。

## 4. 顶层逻辑（ct_lsu_lq.v）

- 16 项，具有 create0/create1 两组分配信号：create0选择从低编号方向找到的
  空项，边界访问需要第二记录时，create1从高编号方向选择另一空项；是否同拍
  创建第二项由 `ld_dc_lq_create1_vld`决定，且可用项少于 2 时会限制创建；
- 弹出：load 指令**退休即可释放**（它的"被反查窗口"= 在飞期）；flush 清
  推测项；
- `lq_ld_dc_full`（L966）：满则 load 在 DC restart——LQ 满是 load 密集代码
  的隐性瓶颈之一。

## 5. 与教科书的对照

经典 LSQ 把 load/store 放一个队列做 CAM；C910 拆成 LQ（监控）+ SQ（前递）
两个职责单一的结构：LQ 不存数据只存地址位图（窄），SQ 才存数据（宽）。
**比较被分解为 16B 块地址 + 16-bit 字节位图**：先比较 `PA[39:4]`，再对
`bytes_vld`求交。处于同一 16B 块但访问不同字节时，位图交集为 0，不会仅因
块地址相同而误报；跨块访问则拆成独立子访问/记录。这里的面积优势主要来自
LQ 不存 load 数据、只保留检测顺序违例所需的窄状态，而不是牺牲字节重叠
精度来制造假阳性。

## 6. Verdi 观察建议

层次：`...x_ct_lsu_top.x_ct_lsu_lq.x_ct_lsu_lq_entryN`

| 信号 | 看什么 |
|------|--------|
| `lq_entry_vld` ×16 | LQ 水位 |
| `lq_entry_raw_spec_fail_x / rar_spec_fail_x` | 违例抓现行 |
| 顶层 `lq_ld_dc_full` | 满反压 |
| 配合 `rtu_lsu_spec_fail_iid` | flush 归因到哪条 load |

构造违例时，可以让较老 store 的地址依赖长延迟结果，并让较年轻 load 访问
可能重叠的地址，以提高年轻 load 先执行的概率。但发射策略、已有 no-spec
标记、cache miss、编译器调度和实际地址都可能阻止该次越过，所以不能写成
“必抢跑、必抓到”。应同时确认 IID 年龄、两者 PA[39:4] 和 byte mask 相交，
再把 `raw_spec_fail`归因于目标场景。
