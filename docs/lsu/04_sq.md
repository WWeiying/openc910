# C910 Store Queue 详解（ct_lsu_sq）

> RTL 源文件：`ct_lsu_sq.v`（3967 行）+ `ct_lsu_sq_entry.v`（1532 行）×12
>
> SQ 保存仍处于推测域或已经提交但尚未转交 WMB 的 store/内存控制项：地址
> 来自 pipe4，普通 store data 来自 pipe5，提交后按队列次序转交 WMB。
> 它同时是 store→load 前递和依赖阻塞判断的数据源。

---

## 1. 表项生命周期

```
st_dc 创建(登记 PA/bytes_vld/iid/sdid)
  → sd_ex1 按 sdid 写入数据(64位) → 地址+数据齐 = 就绪
  → st_da 回写命中/way/dirty 预查信息
  → RTU 退休该 store → commit 位置 1（从推测态转提交态）
  → 按程序序弹出 → WMB（sq.v:3184 起 "pop entry"）
普通 `rtu_yy_xx_flush`: `!commit` 项由 `sq_entry_flush_pop_vld`清除；
已 commit 项保留，继续等待数据完整并转交 WMB
```

12 项的容量含义：最多 12 条 store 在"执行后~进 WMB 前"的窗口里。
更准确地说，SQ 也收容 fence/cache/atomic 等由同一路径管理的项，且非对齐
拆分会影响占用行为。store 密集代码中，SQ 满可能经 st_dc restart 向前形成
反压，但实际瓶颈还要区分是数据迟到、WMB 满、cache/BIU 写出慢，还是单纯
创建速率超过弹出速率。

## 2. store→load 前递（sq.v:2876-3124 + entry 内比较）

### 2.1 三步协议

```
① ld_dc 广播: load 的 PA[39:4] + bytes_vld[15:0] + iid
   每个 SQ 项并行比较: 我比 load 老? 地址 16B 相同? 字节相交? 数据就绪?
② sq 汇总各项结果 → 三种结论之一:
   - 可前递: 选择满足覆盖/数据条件的前递源；多项重叠时需保留程序序最近写者语义
   - 需 discard: 重叠但数据没到/部分覆盖/多项部分重叠拼不出来
   - 无关: 放行走 cache
③ ld_da 拍: case(ld_da_sq_fwd_id[11:0]) 独热选数（sq.v:3047-3076）
   sq_ld_da_fwd_data[63:0] 进 ld_da 的数据选择树（01_ld_pipeline.md 3.1）
```

### 2.2 为什么"部分覆盖"要 discard 而不是拼接

load 需要的字节可能一部分在 SQ、一部分在 cache（甚至跨两个 SQ 项）。
拼接逻辑需要在多个 SQ 项、WMB 和 cache 字节之间选择最新值，会扩大数据 mux
和验证状态空间。当前 RTL 对若干无法可靠单源前递的情况产生 discard/replay，
例如数据未到、覆盖关系不满足或多源依赖不适合当前前递通路。重发并不一定要
等该 store 已写进 cache；相关 SQ entry 数据到达后，唤醒队列就可能使 load
再次发射并成功前递。

`LSU SQ Discard / SQ Data Discard`的准确含义应以 testbench 对具体 RTL
事件的映射为准。某次 CoreMark 的低计数不能推广为“所有编译器排序都使它
罕见”；应按 workload 计算 discard/有效 load 比率，并检查 discard 后平均
等待和重发次数。

### 2.3 restart 唤醒队列（sq.v:3125-3183）

被 discard 的 load 不是都按固定周期盲目重发。这里有两类定向唤醒：

- **data dependency**：发生 data discard 时，SQ 选择造成阻塞的表项
  （优先同地址 newest 项，否则按候选编码选择），在该表项的数据依赖解除后，
  由各 entry 的 `data_depd_wakeup` 位图唤醒对应 LSIQ 项；
- **global dependency**：`sq_wakeup_queue[LSIQ_ENTRY-1:0]`记录 global
  discard 的等待者，相关依赖项从 SQ 向 WMB 转交并触发 `sq_pop_depd_ff`
  时，产生 `sq_global_depd_wakeup` 后清队列。

因此“唤醒队列”不是一个保存 load 全部信息的第二套发射队列，而是 LSIQ
entry 的等待位图与 SQ 表项内依赖状态配合使用。它的目标是让真正的解除依赖
事件触发重试，减少无效重发；flush 会清除全局等待位图。

## 3. 提交侧：弹出到 WMB（sq.v:3184-3685）

- 按队列顺序选择可转交项；接口在无阻塞时可连续工作，但“每拍必弹 1 项”
  不是保证，WMB 接受、数据有效、异常和屏障条件都会造成空拍；
- `wmb ce`（create entry,sq.v:3519/3606）：弹出项打包
  地址/数据/bytes_vld/命中预查信息给 WMB;
- **sync.i/fence 特殊处理**（L3597 注释）：屏障指令弹出时清掉 pfu 状态;
- dcwp 比较（L3686）：弹出与 dcache 写口的 index 冲突规避。

## 4. 表项内的依赖比较（sq_entry.v）

每项自带与 ld_dc 的地址块、字节掩码、IID 年龄、数据状态比较，以及与新
store 创建/数据配对相关的控制。它具有明显的 CAM 式并行比较和宽数据存储
成本，是 LSU 中值得重点关注的面积/时序结构之一；但不能仅凭 RTL 行数断言它
一定是 LSU 面积最大模块，最终面积排序需要综合报告。

## 5. Verdi 观察建议

层次：`...x_ct_lsu_top.x_ct_lsu_sq`

| 信号 | 看什么 |
|------|--------|
| 各项 vld/commit 位 | 推测→提交转换;flush 时只有未 commit 项消失 |
| `ld_da_sq_fwd_id[11:0]` + `sq_ld_da_fwd_data` | 前递命中与数据 |
| discard 相关输出 | 前递失败回放 |
| 弹出口与 WMB 创建握手 | 提交流 |

`store [addr]; load [addr]`可提高观察前递的概率；必须确认两条指令没有被
编译器删除/重排、访问地址和字节范围确实重叠，且 load 在 store 写出前执行。
让 store data 依赖长延迟指令可提高 data-discard 概率，但是否发生仍由实际
发射时序决定。
