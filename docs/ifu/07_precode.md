## 1. 模块概述

### 1.1 接口一览

```verilog
module ct_ifu_precode(
  inst_data,   // 输入：128 位指令数据（一个 16 字节预解码块）
  pre_code     // 输出：32 位预解码结果
);
input  [127:0] inst_data;
output [31:0]  pre_code;
```

这是整个 IFU 中接口最简单的模块：**一个 128 位输入，一个 32 位输出，纯组合逻辑，无时钟、无寄存器**。这里的 128 位对应 16 字节数据，也就是 8 个连续的 16 位 half-word；它是 I-Cache 一次读写的数据行宽度之一，而不是“一个 bank”。当前 I-Cache 的一条 64 字节 cache line 由 4 个这样的 16 字节块组成；每个 128 位数据阵列内部才进一步由 4 个 32 位 SRAM bank 拼接出该行数据。

### 1.2 为什么需要预解码？

#### 问题背景：RISC-V 的变长指令集带来的挑战

RISC-V 支持 RVC（Compressed 指令集，16 位）和 32 位指令混合使用。这导致一个 128 位的预解码块（8 个 half-word）中，指令边界是不确定的。下文的 `h1` 到 `h8` 按地址从低到高排列：`h1=inst_data[127:112]` 对应块内最低地址的 half-word，`h8=inst_data[15:0]` 对应块内最高地址的 half-word。这种“低地址数据位于向量高位”的排列由 IFU 数据通路的拼接方式决定，不能只凭 Verilog 位号推断地址顺序。

```
场景一：全是 32 位指令
┌───────┬───────┬───────┬───────┐
│ RVI 1 │ RVI 2 │ RVI 3 │ RVI 4 │  (每条 32 位 = 2 个 half-word)
└───────┴───────┴───────┴───────┘
  h1+h2   h3+h4   h5+h6   h7+h8

场景二：全是 16 位指令
┌────┬────┬────┬────┬────┬────┬────┬────┐
│RVC1│RVC2│RVC3│RVC4│RVC5│RVC6│RVC7│RVC8│
└────┴────┴────┴────┴────┴────┴────┴────┘
  h1   h2   h3   h4   h5   h6   h7   h8

场景三：混合，且块的第一个 half-word 延续前一块中的指令
┌────┬───────┬───────┬────┐
│后半│ RVI 2 │ RVI 3 │前半│  ← h1 是某 32 位指令的高半部分
└────┴───────┴───────┴────┘
  h1   h2+h3   h4+h5  h6
```

在 IF/IP 数据通路（`ct_ifu_ifdp.v`、`ct_ifu_ipdp.v`）处理指令时，需要知道每个
half-word 是否是分支指令。但只有先确定边界才能解码，先解码才能知道边界——
这是一个**鸡与蛋的问题**。注意 `ct_ifu_ipb.v` 中的 IPB 是 Instruction
Prefetch Buffer，它服务于 I-Cache refill/预取，不是“IP 流水级”。

#### 解决方案：预先计算两种假设下的结果

`ct_ifu_precode` 的核心思想是：**不等块入口边界确定，先把两种入口假设下的指令起点候选都计算出来，并把这些边界候选与静态直接控制流类型一起存入 Predecode Array；后续 IF/IP 控制逻辑再根据当前 VPC、跨块 half-word 状态和实际选中 cache way 选择或修正边界集合**。

这两种假设是：
- **bry1**：假设本 16 字节块的第一个 half-word（h1）是某条指令的**起始位置**
- **bry0**：假设本块的 h1 是前一块末尾启动的某条 32 位指令的**高 16 位**，也就是该指令在地址顺序上的第二个 half-word；此时 h2 才是下一条指令的起始位置

### 1.3 为什么在 Refill 时就做预解码而不在取指时做？

从 RTL 能直接确认的是：

1. `ct_ifu_precode` 实例位于 `ct_ifu_l1_refill`，输入是本次返回并经过变换后的 128 位 refill 数据。
2. 32 位 `pre_code_info` 与对应的 128 位指令数据一起写入 I-Cache 的 Predecode Array 和 Data Array。
3. 命中读取时，IF 数据通路直接取得阵列中保存的预解码位，不必再次对 128 位数据执行同一套 `br/ab_br/bry` 组合计算。
4. refill 正在服务当前取指时，way0 数据和预解码还可以直接选用 `l1_refill_ifdp_inst_data` 与 `l1_refill_ifdp_precode`，并非必须等数据先写入阵列、之后再重新命中读取。

这种组织的**设计意图**是把可提前完成的静态分类和边界候选生成放到 refill 路径，并让命中读路径消费已保存的结果。它可以减少命中读之后需要重复执行的逻辑，但不能仅凭 RTL 文本断言这些逻辑在物理实现中“免费”、refill 时一定有完整空闲周期，或预解码一定被完全移出最终关键路径；门级延迟、阵列读时序和关键路径归属需要结合综合及 STA 报告判断。

## 2. 预解码编码格式

### 2.1 输出格式总览

```
pre_code[31:0]:
 ┌──────────┬──────────┬──────────┬──────────┬──────────┬──────────┬──────────┬──────────┐
 │  h1[3:0] │  h2[3:0] │  h3[3:0] │  h4[3:0] │  h5[3:0] │  h6[3:0] │  h7[3:0] │  h8[3:0] │
 │ bits31:28│ bits27:24│ bits23:20│ bits19:16│ bits15:12│ bits11: 8│ bits  7:4│ bits  3:0│
 └──────────┴──────────┴──────────┴──────────┴──────────┴──────────┴──────────┴──────────┘
```

注意：**h1 对应最高有效位（bit[31:28]），h8 对应最低有效位（bit[3:0]）**。这与 inst_data 中 h1 在 `[127:112]`、h8 在 `[15:0]` 的安排一致——最先进入流水线的 half-word 放在高位。

### 2.2 每个 half-word 的 4 位编码

```verilog
// 第 299-306 行
assign h1_pre_code[3:0] = {h1_ab_br, h1_br, h1_bry1, h1_bry0};
```

| 位 | 字段名 | 含义 |
|---|---|---|
| bit[3] | `ab_br` | RTL 名为 `ab_br` 的直接无条件控制流候选：JAL 或 C.J |
| bit[2] | `br` | RTL 所识别的直接控制流候选：JAL、条件分支或 C.J；不包含 JALR/C.JR/C.JALR |
| bit[1] | `bry1` | 在“h1 为指令起点”假设下，本 half-word 是否为一条指令的起点 |
| bit[0] | `bry0` | 在“h1 不是指令起点”假设下，本 half-word 是否为一条指令的起点 |

**ab_br 与 br 的关系：**
- 按当前两组布尔方程，`ab_br = 1` 时同一 half-word 的 `br` 也为 1，因为 JAL 和 C.J 同时出现在两组检测式中
- `br = 1` 不要求 `ab_br = 1`，例如条件分支只有 `br` 为 1
- 上述包含关系是当前 RTL 方程的结果，不是由信号名本身自动保证的协议；修改检测集合时应同时复核两式

**为什么要区分 ab_br 和 br？**

JAL、C.J 都是直接、无条件且 PC-relative 的控制流：目标由当前 PC 与指令立即数组合得到，不依赖通用寄存器，也没有方向条件。这里应避免把 `ab_br` 解释成“绝对地址跳转”，因为其目标并不是编码中的完整绝对地址。IFU 将这类控制流与条件分支分开标记，使后续 IP 控制逻辑能够在 BHT 给出“不跳”方向时仍识别必须改变顺序流的直接无条件跳转；具体目标仍由 BTB/相关目标通路提供，并不是 `ct_ifu_precode` 自己计算。

## 3. 分支类型检测逻辑

### 3.1 br（分支指令）的识别

以 h1 为例，h2~h8 的 `br` 和 `ab_br` 类型比较式与 h1 同构，只是各自读取不同的 16 位切片；两套 `bry` 边界传播则具有位置相关的初始化条件，不能笼统说整个 h1~h8 逻辑完全相同：

```verilog
// 第 131-139 行
assign h1_br =
  (h1_data[6:0] == 7'b1101111)                          || // JAL
  ({h1_data[14:12], h1_data[6:0]} == 10'b000_1100011)   || // BEQ
  ({h1_data[14:12], h1_data[6:0]} == 10'b001_1100011)   || // BNE
  ({h1_data[14:12], h1_data[6:0]} == 10'b100_1100011)   || // BLT
  ({h1_data[14:12], h1_data[6:0]} == 10'b101_1100011)   || // BGE
  ({h1_data[14:12], h1_data[6:0]} == 10'b110_1100011)   || // BLTU
  ({h1_data[14:12], h1_data[6:0]} == 10'b111_1100011)   || // BGEU
  ({h1_data[15:14], h1_data[1:0]} == 4'b1101)            || // C.BEQZ / C.BNEZ
  ({h1_data[15:13], h1_data[1:0]} == 5'b10101);            // C.J
```

#### RISC-V 指令编码对照

| 指令 | 检测字段 | 编码 | 位宽 |
|---|---|---|---|
| JAL | opcode[6:0] | `1101111` | 32 位 |
| BEQ | funct3[14:12] + opcode[6:0] | `000_1100011` | 32 位 |
| BNE | funct3 + opcode | `001_1100011` | 32 位 |
| BLT | funct3 + opcode | `100_1100011` | 32 位 |
| BGE | funct3 + opcode | `101_1100011` | 32 位 |
| BLTU | funct3 + opcode | `110_1100011` | 32 位 |
| BGEU | funct3 + opcode | `111_1100011` | 32 位 |
| C.BEQZ / C.BNEZ | inst[15:14] + inst[1:0] | `11_01` | 16 位 |
| C.J | inst[15:13] + inst[1:0] | `101_01` | 16 位 |

**关键观察：为什么用 opcode + funct3 来识别，而不用完整的 opcode？**

- RVI 的 BRANCH 大类（BEQ/BNE/BLT 等）共用同一个 opcode `1100011`，通过 funct3（bits[14:12]）区分具体指令。
- 检测时用 `{funct3, opcode}` 共 10 位，可以精确区分每种分支指令，同时也能通过只检测 opcode=`1100011` 识别整个 BRANCH 大类。
- RISC-V 规定，32 位指令的 bits[1:0] 一定是 `11`，16 位压缩指令的 bits[1:0] 一定不是 `11`（可以是 `00/01/10`）。这是区分 RVI 和 RVC 的首要标志。

**C.BEQZ 与 C.BNEZ 的编码识别：**

```
C.BEQZ: inst[15:13] = 110, inst[1:0] = 01  →  {inst[15:14], inst[1:0]} = 4'b1101
C.BNEZ: inst[15:13] = 111, inst[1:0] = 01  →  {inst[15:14], inst[1:0]} = 4'b1101
```

注意 C.BEQZ 和 C.BNEZ 的 bits[15:14] 都是 `11`，bits[1:0] 都是 `01`，所以 `{inst[15:14], inst[1:0]} = 4'b11_01` 同时匹配两者，这是刻意的——对于预解码而言，只需要知道"是条件分支"，不需要区分是 BEQZ 还是 BNEZ。

**C.J 的识别：**

```
C.J:   inst[15:13] = 101, inst[1:0] = 01  →  {inst[15:13], inst[1:0]} = 5'b101_01
```

需要 5 位来唯一标识 C.J（因为 `inst[15:14]=10` 与 C.BEQZ/C.BNEZ 不同）。

### 3.2 ab_br（绝对跳转）的识别

```verilog
// 第 212-213 行
assign h1_ab_br =
  (h1_data[6:0] == 7'b1101111) ||              // JAL
  ({h1_data[15:13], h1_data[1:0]} == 5'b10101); // C.J
```

当前 `ab_br` 检测集合是当前 `br` 检测集合的子集，只包含 JAL（32 位）和 C.J（16 位）。JALR、C.JR 和 C.JALR 都未进入这两个检测集合：它们的目标依赖寄存器值，不能由当前 16 位切片中的立即数字段直接形成。它们可由 BTB 等目标预测结构覆盖，并在后续完整译码/执行阶段确认语义。因而本模块的 `br` 不能解释为 ISA 中“所有控制流指令”的总分类。

## 4. BRY 位设计原理

### 4.1 问题：为什么需要两套 BRY？

考虑 IF/IP 逻辑处理一个 128 位、16 字节数据块的场景。逻辑需要扫描 h1~h8，先确定哪些 half-word 是指令起点，再把这些起点与 `br/ab_br` 相与以筛出直接控制流候选。但块入口可能对应两种边界状态：

**情况 A（bry1 适用）：h1 是某条指令的起始位置**

```
 h1  h2  h3  h4  h5  h6  h7  h8
┌──┬──┬─────┬──┬─────┬──┬─────┐
│16│16│ 32  │16│ 32  │16│ 32  │ ← 各 half-word 的指令归属
└──┴──┴─────┴──┴─────┴──┴─────┘
 ↑h1是指令起点
分支指令在：h2（若为分支）、h3（若 32 位 h3+h4 为分支）、h5（若 16 位）...
```

**情况 B（bry0 适用）：h1 是某 32 位指令的后半部分，h2 才是指令起点**

```
 h1  h2  h3  h4  h5  h6  h7  h8
┌──┬──┬──┬─────┬──┬─────┬──┬──┐
│后│16│16│ 32  │16│ 32  │16│16│ ← h1 = 前条 32 位指令的高半部分
└──┴──┴──┴─────┴──┴─────┴──┴──┘
 ↑h1不是指令起点，h2才是
分支指令在：h2（若为分支）、h3（若为分支）、h4+h5（若为 32 位分支）...
```

预解码生成时并不知道未来将从块内哪个 VPC 开始消费，也不知道入口是否携带由前一块延续来的 32 位指令后半，因此提前保留两套 BRY。运行时，`ct_ifu_ifdp` 先用 `pcgen_ifdp_pc[2:0]` 生成当前 half-word 的 one-hot 位置并屏蔽 VPC 之前的候选；`ct_ifu_ipctrl` 再结合 `h0_vld`、当前位置在 bry0/bry1 下是否命中、选中的 cache way 以及边界重新解码结果选择/更新候选。这里不是一个脱离上下文的单独“bry0/bry1 选择位”。

### 4.2 bry1 的语义：假设 h1 是指令起点

```
bry1 = 1 表示：如果 h1 是指令起点，则本 half-word 是某个有效指令的起始位置
```

换言之，bry1 描述的是"在 bry1 假设下，本 half-word 是否位于某个有效指令的起始槽位"。

**注意**：bry 位本身不等于 br 位！bry 是"槽位有效性"位，br 是"分支类型"位。IP 级需要同时检查：
- `bry` = 1（本 half-word 是有效指令起点）
- `br` = 1（本 half-word 看起来是分支指令）

两者同时为 1，才能判定该 half-word 代表一条真正的分支指令。

### 4.3 bry0 的语义：假设 h1 不是指令起点

```
bry0 = 1 表示：如果 h1 是前一条 32 位指令的后半部分，则本 half-word 是某个有效指令的起始位置
```

h1 的 bry0 恒为 0（因为 h1 本身不是指令起点），h2 的 bry0 恒为 1（因为在此假设下 h2 必然是第一条指令的起点）。

## 5. 边界传播逻辑详解

### 5.1 理解传播的核心规则

在 RISC-V 中，判断 half-word Hk 是否是指令起点，取决于前一个 half-word Hk-1 的状态：

- 如果 Hk-1 是某条 **16 位指令** 的起点（RVC），则 Hk 是下一条指令的起点；
- 如果 Hk-1 是某条 **32 位指令** 的起点（RVI），则 Hk 是该 32 位指令的后半部分（不是指令起点）；
- 如果 Hk-1 是某条 32 位指令的后半部分，则 Hk 是下一条指令的起点。

判断一个 half-word 是 32 位指令起点的方法：`h_data[1:0] == 2'b11`（32 位指令的最低两位必然是 `11`）。

### 5.2 bry1 的传播逻辑

**h1_bry1（基准）：**

```verilog
// 第 237-238 行
assign h1_bry1_32 = (h1_data[1:0] == 2'b11);  // h1 是 32 位指令起点
assign h1_bry1    = 1'b1;                       // h1 本身恒为指令起点
```

在 bry1 假设下，h1 是指令起点，所以 `h1_bry1 = 1`（恒真）。同时计算 `h1_bry1_32` 供 h2 使用。

**h2_bry1（从 h1 传播来）：**

```verilog
// 第 240-242 行
assign h2_bry1_32 = (h2_data[1:0] == 2'b11) && !h1_bry1_32;
assign h2_bry1_16 = !(h2_data[1:0] == 2'b11) && !h1_bry1_32;
assign h2_bry1    = h2_bry1_32 || h2_bry1_16;
```

逻辑分析：
- `!h1_bry1_32`：h1 不是 32 位指令起点（h1 是 16 位指令，或不是起点），则 h2 是下一条指令的起点。
- 如果 `h1_bry1_32 = 1`（h1 是 32 位指令），则 h2 是 h1 的后半部分，不是起点，`h2_bry1 = 0`。
- `h2_bry1 = h2_bry1_32 || h2_bry1_16`：无论 h2 是 16 位还是 32 位指令起点，只要它是起点，bry1=1。

**注意**：`h2_bry1_32` 和 `h2_bry1_16` 只是标记了 h2 是 32 位还是 16 位指令的起点（供 h3 传播使用），两者的 OR 才是"h2 是否是指令起点"。

**h3_bry1（从 h2 传播来）：**

```verilog
// 第 244-246 行
assign h3_bry1_32 = (h3_data[1:0] == 2'b11) && !h2_bry1_32;
assign h3_bry1_16 = !(h3_data[1:0] == 2'b11) && !h2_bry1_32;
assign h3_bry1    = h3_bry1_32 || h3_bry1_16;
```

这里用的是 `!h2_bry1_32` 而不是 `h2_bry1`。含义：只有当 h2 不是 32 位指令起点时，h3 才可能是指令起点。这正确捕捉了传播规则：
- h2 是 16 位指令起点（`h2_bry1_16=1, h2_bry1_32=0`）→ h3 是下一条指令起点 → `!h2_bry1_32=1` → h3_bry1 计算有效
- h2 是 32 位指令起点（`h2_bry1_32=1`）→ h3 是 h2 的后半部分 → `!h2_bry1_32=0` → h3_bry1=0
- h2 不是指令起点（`h2_bry1=0, h2_bry1_32=0`）→ h3 是指令起点 → `!h2_bry1_32=1` → h3_bry1 计算有效

等等，最后一条——h2 不是指令起点，怎么 h3 还能是？这发生在：h1 是 32 位指令起点，h2 是其后半部分（非起点），那么 h3 就是下一条指令的起点。对应：`h1_bry1_32=1`，`h2_bry1=0`，`h2_bry1_32=0`（h2 不是 32 位指令起点，它不是任何指令的起点）。此时 `!h2_bry1_32=1`，h3_bry1 按 h3 自身的类型正确计算。

这个传播规则用一句话概括：**"前一个 half-word 是 32 位指令起点"意味着"我是它的后半部分，我不是指令起点"**，其余情况我都是起点。

### 5.3 bry0 的传播逻辑

bry0 假设 h1 不是指令起点（h1 是前一条 32 位指令的后半部分）：

```verilog
// 第 269-276 行
assign h1_bry0    = 1'b0;          // h1 不是指令起点（bry0 的假设前提）
assign h2_bry0_32 = (h2_data[1:0] == 2'b11);
assign h2_bry0    = 1'b1;          // 在此假设下，h2 一定是指令起点
```

`h2_bry0 = 1'b1` 是因为：h1 是 32 位指令的后半部分（假设），所以 h2 必然是下一条指令的起点。

```verilog
// 第 274-276 行
assign h3_bry0_32 = (h3_data[1:0] == 2'b11) && !h2_bry0_32;
assign h3_bry0_16 = !(h3_data[1:0] == 2'b11) && !h2_bry0_32;
assign h3_bry0    = h3_bry0_32 || h3_bry0_16;
```

从 h3 开始，bry0 与 bry1 使用相同形式的递推方程（都是“看本假设路径中
前一个 half-word 是否为 32 位指令起点”），但两条路径的状态值不一定相同：
它们的初始边界不同，差异可能继续向 h4~h8 传播。

### 5.4 传播规则总结表

| half-word | bry1 假设（h1 是指令起点） | bry0 假设（h1 不是指令起点） |
|---|---|---|
| h1 | 恒为 1（起点） | 恒为 0（非起点，是前条 32 位指令后半） |
| h2 | 若 h1 是 16 位起点则为 1；若 h1 是 32 位起点则为 0 | 恒为 1（h1 后半 → h2 是新起点） |
| h3 | 取决于 `h2_bry1_32` | 取决于 `h2_bry0_32` |
| h4~h8 | 沿 bry1 状态链递推 | 沿 bry0 状态链递推 |

**注意**：“方程同构”不等于“结果收敛”。例如 bry1 假设下 h1 是 32 位
起点时，h2 是后半字；bry0 假设下 h2 却是新指令起点。若 h2 的低两位恰为
`11`，两条路径在 h2 的 `_32` 状态不同，h3 的边界判断也会不同。预解码同时
保留两套结果，正是为了等上游给出窗口入口的真实边界后再选择。

### 5.5 为什么用链式传播而不用并行计算？

观察 bry1 的传播：h3_bry1 依赖 h2_bry1_32，h4_bry1 依赖 h3_bry1_32，依此类推。这是一个串行链式依赖。

**为什么不能并行？**

因为 hk 是否是指令起点，取决于从 h1 到 hk-1 的所有指令的长度，而指令长度本身也依赖位于其起始位置的数据（`bits[1:0]`）。这个依赖链是固有的，无法简单并行化。

RTL 中每一级只使用两个简单信号：
- `hn_bry1_32`：只需 `hn_data[1:0] == 2'b11` 和前一级的 `bry1_32` 做 AND。
- `hn_bry1`：一个 OR。

因此综合器看到的是一条有限长度的组合递推链。RTL 本身不能证明其门级深度、
时序裕量或是否属于最终关键路径；这些结论应以综合时序报告为准。体系结构上
值得注意的是：该实现用两套并行假设避免跨取指块保存复杂解析状态，但代价是
块内仍存在长度传播的组合依赖。

## 6. 完整数据流示例

### 6.1 示例：计算一个混合指令序列的预解码结果

假设一个 128 位、16 字节预解码块的内容如下：

```
h1[15:0] = 0x4185   → bits[1:0] = 01 → 16 位 RVC 指令（假设不是分支）
h2[15:0] = 0x8082   → bits[1:0] = 10 → 16 位 RVC 指令（假设不是分支）
h3[15:0] = 0x????   → bits[1:0] = 11 → 32 位 RVI 的低 16 位
h4[15:0] = 0x????   → 32 位 RVI 的高 16 位（与 h3 构成一条 JAL 指令，h3[6:0]=1101111）
h5[15:0] = 0xC885   → bits[1:0] = 01 → 16 位 C.BEQZ（h5[15:14]=11, h5[1:0]=01）
h6[15:0] = 0x4501   → bits[1:0] = 01 → 16 位 RVC 指令
h7[15:0] = 0xXXXX   → bits[1:0] = 11 → 32 位 RVI 的低 16 位
h8[15:0] = 0xYYYY   → 32 位 RVI 的高 16 位
```

**步骤1：计算 br 和 ab_br**

| half-word | br | ab_br |
|---|---|---|
| h1 | 0（非分支） | 0 |
| h2 | 0 | 0 |
| h3 | 1（JAL，bits[6:0]=1101111） | 1（JAL） |
| h4 | 0（JAL 的高半部分，看 h4 的 bits[6:0] 不匹配） | 0 |
| h5 | 1（C.BEQZ） | 0（条件分支非绝对跳转） |
| h6 | 0 | 0 |
| h7 | 0（假设 h7 是某 32 位非分支指令的低半） | 0 |
| h8 | 0（高半部分） | 0 |

**步骤2：计算 bry1（假设 h1 是起点）**

```
h1: bry1=1（起点），bry1_32=0（16位）
h2: !h1_bry1_32=1，bry1=1，bry1_32=0（16位）
h3: !h2_bry1_32=1，bry1=1，bry1_32=1（32位，bits[1:0]=11）
h4: !h3_bry1_32=0，bry1=0，bry1_32=0（h4是h3的后半，不是起点）
h5: !h4_bry1_32=1，bry1=1，bry1_32=0（16位）
h6: !h5_bry1_32=1，bry1=1，bry1_32=0（16位）
h7: !h6_bry1_32=1，bry1=1，bry1_32=1（32位）
h8: !h7_bry1_32=0，bry1=0（h8是h7的后半，不是起点）
```

bry1：1 1 1 0 1 1 1 0

**步骤3：计算 bry0（假设 h1 不是起点）**

```
h1: bry0=0（前提：h1是前条32位指令后半）
h2: bry0=1（起点），bry0_32=0（16位）
h3: !h2_bry0_32=1，bry0=1，bry0_32=1（32位）
h4: !h3_bry0_32=0，bry0=0（h4是h3的后半）
h5: !h4_bry0_32=1，bry0=1，bry0_32=0（16位）
h6: !h5_bry0_32=1，bry0=1，bry0_32=0（16位）
h7: !h6_bry0_32=1，bry0=1，bry0_32=1（32位）
h8: !h7_bry0_32=0，bry0=0（h8是h7的后半）
```

bry0：0 1 1 0 1 1 1 0

**步骤4：组装 pre_code**

```
h1: {ab_br=0, br=0, bry1=1, bry0=0} = 4'b0010
h2: {0, 0, 1, 1}                     = 4'b0011
h3: {1, 1, 1, 1}                     = 4'b1111  ← 这是 JAL 的起始 half-word！
h4: {0, 0, 0, 0}                     = 4'b0000  ← JAL 的后半，bry 均为 0
h5: {0, 1, 1, 1}                     = 4'b0111  ← C.BEQZ，非绝对跳转
h6: {0, 0, 1, 1}                     = 4'b0011
h7: {0, 0, 1, 1}                     = 4'b0011  ← 32 位非分支指令起点
h8: {0, 0, 0, 0}                     = 4'b0000  ← 32 位指令后半

pre_code[31:0] = 32'b0010_0011_1111_0000_0111_0011_0011_0000
              = 0x23F0_7330
```

### 6.2 IP 级如何使用预解码结果

IF 数据通路 `ct_ifu_ifdp.v` 将每个 4 位字段拆成 `bry0`、`bry1`、`br` 和
`ab_br` 四组 8 位向量，并根据当前 VPC 的块内 half-word 偏移屏蔽更低地址的
位置。`ct_ifu_ipctrl.v` 结合以下信息确定当前边界向量：

- `h0_vld`：当前窗口前部是否携带跨块拼接所需的前一 half-word；
- 当前 VPC one-hot 位置在 bry0/bry1 假设下是否命中；
- 实际命中的 I-Cache way；
- misaligned boundary 或多分支截断后重新形成的边界更新值。

选定边界向量后，逻辑再计算 `bry_selected & br` 和
`bry_selected & ab_br`。因此预解码给出的是**静态候选**，后续控制逻辑还会
屏蔽、选择和必要时重算；它本身不等同于最终确认的分支，也不负责验证该指令
是否会在架构上退休。

## 7. 与其他模块的协作关系

### 7.1 调用路径

```
l1_refill（从 L2 取回数据）
    │
    ├─→ ct_ifu_precode（传入 128 位数据）
    │       │
    │       └─→ 32 位 pre_code
    │
    └─→ ct_ifu_icache_if（同时写 data array 和 predecode array）
             │
             ├─→ ct_ifu_icache_data_arrayX（存储 128 位指令数据）
             └─→ ct_ifu_icache_predecd_arrayX（存储 32 位预解码结果）
```

注意：`ct_ifu_precode` 在 `l1_refill` 模块中被调用，而不是在 `icache_if` 中。`icache_if` 只是接收 `l1_refill` 计算好的 `pre_code` 并写入 SRAM。

### 7.2 为什么在 l1_refill 中调用而不在 icache_if 中？

从结构连接看，`l1_refill` 已经持有 `ipb_l1_refill_data_aft_v2trans[127:0]`，同一份数据既送入 `ct_ifu_precode`，也送往 I-Cache 写接口和当前 refill 的 IF 数据旁路。因此在这里生成 `pre_code_info`，可以让数据与预解码信息保持同一 refill 写入粒度，并直接复用到 refill 服务当前取指的旁路。至于“为什么”采用此层次，只能作为结构设计意图理解；RTL 连接本身不能证明它一定减少了多少门数、延迟或功耗。

### 7.3 预解码的局限性

预解码只检测了**当前 half-word 自身的编码**（16 位），对于 32 位 RVI 分支指令（如 JAL），预解码检测的是 JAL 指令的低 16 位（包含 opcode），这是足够的，因为 RISC-V 的 opcode 在指令的低 7 位。

但预解码**不能独立完成**的工作包括：

1. 确定一次实际取指从块内哪个 half-word 开始，以及入口是否携带跨 16 字节块的 32 位指令后半；这需要 VPC、`h0_vld` 和 IF/IP 边界状态共同判断。
2. 识别全部间接控制流。JALR、C.JR、C.JALR 不在当前 `br/ab_br` 静态检测集合中。
3. 判断分支方向、计算或验证最终目标、确认预测正确性。BHT、BTB、RAS、执行单元与恢复路径分别承担这些职责。
4. 完成指令合法性、权限、异常和精确退休判断；当前模块只看每个 16 位切片中少量编码位，可能对并非实际起点的位模式产生候选，必须由 `bry` 和后续流水线语义过滤。

### 7.4 与 IF/IP 数据通路的接口

```
icache_if_ifdp_precode0/1[31:0] ─┐
l1_refill_ifdp_precode[31:0]     ├→ ifdp → ipctrl/ipdp
                                  ┘
```

IP 级收到 pre_code 后，会并行检查一个 16-byte 块内的 8 个 half-word 位置。
这些位置可能组成 8 条 16-bit 指令、4 条 32-bit 指令或两者混合；不能固定称为
“每周期 4 条指令”。`bry+br` 用于找出有效分支位置并决定从何处截断指令流。

## 附录：预解码逻辑完整信号对照表

| 信号 | 含义 | 恒定值 |
|---|---|---|
| `h1_bry1` | bry1 假设下 h1 是起点 | 恒为 1 |
| `h1_bry0` | bry0 假设下 h1 是起点 | 恒为 0 |
| `h2_bry0` | bry0 假设下 h2 是起点 | 恒为 1 |
| `hn_bry1_32` | bry1 假设下 hn 是 32 位指令起点 | 视数据而定 |
| `hn_bry0_32` | bry0 假设下 hn 是 32 位指令起点 | 视数据而定 |
| `hn_br` | hn 的 16 位切片匹配当前 RTL 的直接控制流检测集合 | 视数据而定 |
| `hn_ab_br` | hn 的 16 位切片匹配 JAL/C.J 直接无条件控制流集合 | 视数据而定 |

**RISC-V 分支指令编码速查：**

| 指令 | opcode[6:0] | funct3[14:12] | 位宽 |
|---|---|---|---|
| JAL | 1101111 | — | 32 |
| JALR | 1100111 | 000 | 32 |
| BEQ | 1100011 | 000 | 32 |
| BNE | 1100011 | 001 | 32 |
| BLT | 1100011 | 100 | 32 |
| BGE | 1100011 | 101 | 32 |
| BLTU | 1100011 | 110 | 32 |
| BGEU | 1100011 | 111 | 32 |
| C.J | inst[15:13]=101, inst[1:0]=01 | — | 16 |
| C.BEQZ | inst[15:13]=110, inst[1:0]=01 | — | 16 |
| C.BNEZ | inst[15:13]=111, inst[1:0]=01 | — | 16 |

**JALR 类不在当前预解码检测集合中的边界：** JALR 的目标 `rs1 + imm` 依赖寄存器值，C.JR/C.JALR 也属于寄存器间接控制流。当前模块既不读寄存器，也不输出“间接跳转”类型位，因此这些指令不会被 `hn_br` 标记；取指阶段可依靠 BTB/RAS 提供预测目标，完整译码与执行阶段再确认实际行为。这是对当前 RTL 分工的描述，不表示间接跳转在整个 IFU 中没有预测支持。
