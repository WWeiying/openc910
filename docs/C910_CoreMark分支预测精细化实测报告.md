# C910 CoreMark 分支预测精细化实测报告

## 1. 测试目的与结论

本报告记录 OpenC910 RTL 在 **CoreMark 1 次迭代**上的分支预测精细化波形统计。测试的目的不是重新发布一个正式 CoreMark 分数，而是用短而完整的 CoreMark kernel，精确回答以下问题：

1. 程序实际退休了多少条件分支、Taken/Not-Taken 比例如何、架构可见误预测率是多少。
2. L0 BTB、IP 主预测、IB RAS、Addrgen 前端纠错和 BJU 后端纠错分别发生了多少次。
3. 每类 redirect 到正确目标进入 IF、进入 IDU、重新创建 ROB 项分别需要多久。
4. BJU 发现误预测后，分支退休、RTU flush、IDU/IFU 恢复各需要多久。
5. 正确预测时仍可能存在的多分支解析、RAS 晚转向等结构开销有多大。

本次结果的核心结论如下。

- CoreMark 共退休 **231,917** 条指令，其中 **47,305** 条是条件分支，占退休指令的 **20.397%**。这是一个控制流密度很高的工作负载。
- 条件分支方向预测准确率为 **93.056%**，方向误预测 **3,285** 次；加上 **7** 次 Return 目标误预测，总误预测为 **3,292** 次，即 **14.195 MPKI**。
- ROI 共执行到 **303 个静态条件分支 PC**，其中 **206 个**产生过架构可见方向误预测。Top 30 静态分支贡献 **2,095** 次错误，占全部方向误预测的 **63.775%**；只有 27 个静态分支恰好错 1 次，因此错误呈现“少数热点加长尾”，不是平均分布。
- 48,002 条执行级条件分支的 PCFIFO 预测上下文和 PID/payload 配对率均为 **100%**；47,999 条进入 EX2 的事件身份错误为 **0**，3,285 条方向错误全部与最终退休误预测严格配对。
- BJU 误预测恢复保护占 **14,103 周期，8.253%**。条件分支误预测从 BJU cancel 到 IDU/IFU 解除保护的中位数为 **3 周期**，P90 为 **6 周期**，最大为 **23 周期**。
- 条件分支误预测发生后，正确目标通常在 **1 周期**后重新进入 IF，目标指令进入 IDU 的中位数为 **3 周期**。这说明 C910 的典型路径是“前端很快重定向，后端等待退休和 RTU 恢复后再放行”。
- 多条件分支解析的 raw stall 占 **14,544 周期，8.511%**，其中真正推进剩余窗口的有效串行重放为 **13,174 周期，7.710%**，另有 1,370 周期只是被 IB/后端反压保持。它是本次 CoreMark 前端中与预测正确性不同、但同样重要的结构吞吐问题。
- raw 多分支 stall 与 BJU 恢复同时出现 **1,015 周期**，二者并集为 **27,632 周期，16.171%**。该并集表示“至少一种相关阻塞正在发生”，不能直接视为理想预测器可删除的周期数。
- 按“把已观测阻塞周期完全串行删除”的敏感性模型，只理想化预测准确率得到的全局性能提升为 **8.996%**；再删除多分支处理的 **13,174 个有效串行重放周期**得到 **18.995%**；继续加入 L0 覆盖、前端目标和 RAS 时延模型后，扩展包络为 **22.765%～24.627%**。这些是基于现有 trace 的反事实估算，不是 RTL A/B 实测结果。
- 极少数 `cancel→目标指令进入 IDU` 出现 65、71、81 周期长尾。波形抽查表明，这些样本的 BJU 恢复保护已经在 3 至 6 周期内解除，之后是目标侧长时间没有有效指令供给。因此最大值包含目标 I-cache/取指供给等叠加效应，不是纯分支预测恢复代价。

## 3. 统计口径

### 3.1 三种不能混用的事件层级

报告使用三类口径：

| 层级 | 代表信号/数据 | 可回答的问题 | 不能回答的问题 |
|---|---|---|---|
| 架构退休口径 | RTU 退休指令、条件分支、Taken、mispred 脉冲 | 最终真正执行了多少分支，准确率和 MPKI 是多少 | 不能直接看到被冲刷的投机执行 |
| 执行级口径 | BJU EX1 有效分支及实际/预测方向 | 方向错误由 `NT→T` 还是 `T→NT` 构成 | 不能作为退休分支准确率的分母 |
| 前端事件口径 | PCGEN 选中的 L0/IP/IB/Addrgen/BJU redirect | 各转向来源的频度和后续供给延迟 | 一个 redirect 事件不等于一条退休分支 |

正式准确率必须使用架构退休口径。执行级数据包含错误路径上后来被 flush 的分支，只能用来分析机制构成。前端 redirect 只在需要改变取指流时发生，正确 Not-Taken 分支不需要 redirect，因此 redirect 总数也不能作为全部分支的分母。

### 3.2 redirect 延迟的四个端点

每个 PCGEN 已选中的分支 redirect 从发起周期开始，匹配以下端点：

| 端点 | 定义 | 解释强度 |
|---|---|---|
| `to_target_if_valid` | 正确目标 PC 首次以有效取指块进入 IF | 最直接衡量 PCGEN 是否及时转到目标 |
| `to_exact_target_idu_accept` | 目标 PC 对应的具体指令首次被 IDU 接收 | 可观察目标路径真正进入后端；本次 CoreMark 代码范围内低 15 位半字 PC 足以唯一匹配 |
| `to_first_any_idu_accept_proxy` | redirect 后任意指令首次被 IDU 接收 | 供给恢复代理；可能是 IBUF 中较老指令，不能保证就是目标指令 |
| `to_first_any_rob_create_proxy` | redirect 后任意 ROB create 首次出现 | 后端活动恢复代理；不能单独证明目标指令已经创建 |

早期 redirect 的匹配窗口会在下一次硬 redirect 处截断，以免把后续控制流事件错误归因给当前事件。因此 L0/IP 的“精确目标 IDU 已观测数”较低不表示大量预测失败，而是短时间内又发生 redirect 后不再跨事件追踪。

BJU 误预测恢复是例外：属于同一次恢复的后续 RTU flush 不会截断目标路径，因而 **3,292 个架构退休误预测均成功配对**。

### 3.3 周期统计的含义

- `mean` 是平均值，容易被少量长尾拉高。
- `median` 是中位数，表示一半事件不超过该值，更适合描述典型延迟。
- `P90` 表示 90% 的事件不超过该值。
- `max` 用于定位异常事件，但不能代替典型惩罚。
- stall 周期可以与其他 stall 或有效工作重叠，不能把各项百分比直接相加。

## 4. 架构退休结果

### 4.1 分支密度、方向分布和准确率

| 架构指标 | 事件数 | 分母 | 比例/结果 |
|---|---:|---:|---:|
| 退休指令 | 231,917 | 231,917 | 100.000% |
| 退休控制流指令 | 50,292 | 231,917 | 21.685% |
| 退休条件分支 | 47,305 | 231,917 | 20.397% |
| 实际 Taken 条件分支 | 20,449 | 47,305 | 43.228% |
| 实际 Not-Taken 条件分支 | 26,856 | 47,305 | 56.772% |

### 4.4 每条动态分支携带的真实 BHT 状态

`ct_ifu_pcfifo_if.v` 把预测时状态编码进 25 位 `chk_idx`，该值随 PCFIFO 项一直传到 BJU。v3 逐条解码：

```text
chk_idx[21:0]       = 预测时 22 位 VGHR
chk_idx[23:22]      = bimode selector 的 2 位状态
{bht_pred,chk[24]}  = 实际选中的 2 位饱和计数器状态
```

同时按 `ct_ifu_bht.v` 的原公式重建更新位置：

```text
predict row = {GHR[13:10], GHR[9:4] XOR GHR[21:16]}
offset      = current_PC_index[3:0] XOR GHR[3:0]
bank        = selector[1] 选择 Taken/Not-Taken bank
select row  = current_PC_index[9:3]
select slot = current_PC_index[2:0]
```

在没有旧 BHT 写缓冲项占用更新口的 **38,230 次**直接更新中，重建出的 prediction row、selector row、更新后 prediction counter 和 selector counter 与 RTL 实际信号全部一致，错误为 **0**。这证明逐条 CSV 中的 BHT key、计数器强弱和 selector 状态不是离线猜测，而是对 RTL 编码的等价解码。

对 3,285 次架构方向误预测做互斥的“证据分类”得到：

| 单轨迹证据类别 | 架构误预测 | 含义 |
|---|---:|---|
| 该 predictor key 在 ROI 内首次出现 | 1,256 | 无法从 ROI 内看到它此前如何训练；可能与预热、ROI 前状态或新历史上下文有关，不能直接断言 cold miss |
| 相同 PC 与完整 22 位 GHR 曾对应相反结果 | 1,068 | 对当前可见上下文而言结果不可分，说明仅靠该全局历史上下文不足以唯一决定方向 |
| 所选 2 位计数器处于弱状态 | 736 | 预测状态接近翻转边界，常见于模式切换或训练不足 |
| 同一 prediction key 的前一次使用来自其他 PC 且结果相反 | 174 | 有明确的跨静态 PC 表项别名干扰证据 |
| 单次轨迹无法唯一归因 | 51 | 需要结构 A/B 或更长上下文才能判定 |
| 合计 | 3,285 | 与退休方向误预测完全守恒 |

这里必须区分“证据”和“因果证明”。例如 174 次具有直接跨 PC 别名证据，但不能据此断言扩大 BHT 必然全部消除；1,068 次相同 PC/GHR 结果不唯一，说明现有上下文不能区分，却不能单凭一次 trace 判定应增加全局历史、局部历史还是路径历史。严格因果归因仍需要分别改变表容量、索引哈希、历史长度和 predictor 组织做单变量 A/B。

### 4.5 动态分支身份链与正确预测开销

v3 同时抓取 IFU 送入 PCFIFO 的完整 payload、PCFIFO 实际写入 PID、BJU EX1/EX2 的 PID/IID/PC/`chk_idx` 以及 RTU 退休误预测。身份链定义为：

```text
IFU PCFIFO create payload
  → PCFIFO 实际写入并分配 PID
  → BJU EX1：PID + IID + PC + prediction + chk_idx
  → BJU EX2：PID + IID + halfword PC + chk_idx
  → BJU cancel
  → RTU retire mispred
  → RTU flush
  → IDU/IFU recovery release
```

48,002 条执行级条件分支的 IFU payload 上下文配对率为 **100%**，PCFIFO `PID+PC+prediction+chk_idx` 实际写入配对率也为 **100%**；47,999 条进入 EX2 的事件身份错误为 0，另有 3 条推测分支在 EX1 同周期遇到全局 flush，按 RTL 优先级被取消并未进入 EX2，未解释缺口为 0。3,285 条方向错误全部与最终退休误预测配对。后续 v3 运行会对 PID/payload 覆盖率设置 99% 的最低硬门槛，不满足时分析脚本直接失败，而不是生成残缺报告。

对可同时匹配“分支被 IDU 接收”和“正确目标被 IDU 接收”的 Taken 样本，可以直接计算两者之间的 IDU 空拍。当前低 15 位半字 PC 在 CoreMark 代码范围内无冲突，匹配覆盖率为 91.596%；结果如下：

| 正确 Taken 路径 | 动态事件 | 已匹配样本的平均 IDU 空拍 | P90 |
|---|---:|---:|---:|
| L0 BTB | 6,286 | 0.268 | 1 |
| IP 主预测 | 10,346 | 0.468 | 1 |
| L0 miss 后由 IP 预测 | 1,049 | 0.879 | 1 |

### 8.1 这个 stall 在 RTL 中究竟表示什么

C910 的 IP 级一次处理一个由 **8 个 half-word，也就是 16 字节**组成的取指窗口。`ct_ifu_ipdp.v` 用 `ipctrl_ipdp_hn_con_br[7:0]` 标出窗口内各指令起点上的条件分支，`con_br_more_than_one` 判断该向量是否既非全零也非 one-hot。`ct_ifu_ipctrl.v` 中真正触发多分支处理的条件是：

```verilog
masked_bry_update_vld = ip_data_vld
                      && !bht_result
                      && con_br_first_branch
                      && con_br_more_than_one;
br_more_than_one_stall = masked_bry_update_vld;
```

四个条件缺一不可：当前 IP 数据有效、窗口遇到的第一条控制流是条件分支、窗口内还有后续条件分支，并且第一条预测为 Not-Taken。第一条若预测 Taken，正确路径已经在该分支处结束，后面的指令和条件分支属于预测错误路径，因此直接在第一条处分割，不需要继续解析同一窗口。

`br_more_than_one_stall` 加入 `ipctrl_ifctrl_stall`，所以 IF 不能用新取指窗口覆盖当前窗口；但它没有加入 `ip_self_stall`，IP→IB 寄存器仍可在 IB 未反压时接收当前片段。与此同时，IFDP 不装入新窗口，而是用 `ipctrl_ifdp_vpc_onehot_updt` 和各组 `*_bry_updt_data` 把有效起点推进到第一条条件分支之后。下一周期，同一 16 字节窗口的剩余部分再次进入“找第一条分支”的逻辑。

可以把当前行为写成下面的伪代码：

```text
while 当前窗口还有条件分支:
    B = 当前剩余窗口中的第一条条件分支
    P = 用当前 VGHR 对 B 做一次方向预测
    把 B 以及 B 之前的有效指令送入 IB
    VGHR = append(VGHR, P)

    if P == Taken:
        在 B 处分割并转向 B 的目标
        break
    if B 后面没有其他条件分支:
        结束当前窗口
        break

    冻结 IF，新一拍从 B 后面继续处理当前窗口
```

因此它不是“IP 原地什么也不做的一拍”，而是**每拍最多形成一个条件分支预测上下文，并把对应前缀向后传递**。这也是后文不能把全部 active 周期直接当作性能损失的原因。

### 8.2 为什么当前设计必须逐条处理

逐条处理不是一个孤立的 stall 控制，而是由四层接口共同限定。

| 层次 | RTL 证据 | 对双分支处理的约束 |
|---|---|---|
| BHT 历史推进 | `ct_ifu_bht.v` 中 `vghr_reg <= {vghr_reg[20:0], ipctrl_bht_con_br_taken}` | 每周期只接收一条 IP 条件分支结果；第二条分支必须使用第一条预测之后的历史，而不是同一份旧 VGHR |
| BHT 预测存储 | 方向表是单端口同步 `ct_spsram_1024x64`，选择表是单端口同步 `ct_spsram_128x16` | 当前分支预测时才发起“下一历史状态”方向行读取，数据在下一拍供后续分支使用；同拍第二预测需要第二读口、镜像表或提前缓存 |
| IP→IB payload | `ct_ifu_ipdp.v` 只传一组 `bht_result`、`bht_pre_result`、`bht_sel_result`、`vghr` 和条件分支 PC/offset | 即使组合逻辑能算出第二个方向，也没有第二组独立预测快照可交给执行级校验和训练 |
| PCFIFO | `ct_ifu_pcfifo_if.v` 明确注释 `inst0 & inst1 has one con_br at most`，两个 create port 共享 `inst_bht_pre_result` 和 `inst_bht_sel_result` | 两个 PC operation create port 不等于支持两条条件分支；第二条若复用第一条 `chk_idx`，BJU 会校验和更新错误的 BHT 项 |

这里最容易误判的是 PCFIFO。它确实有 `create0` 和 `create1` 两个入口，也能在一个 IB 包中提取两个 PC operation；但当前代码建立在“二者至多一条条件分支”的前提上。`inst1_vghr` 在 `inst0_con_br` 时附加一个 0，只是为已有包格式构造历史位置，不会凭空生成第二条分支独立的 prediction counter、selector 和预测结果。两个 create 项继续共享同一个 `inst_bht_pre_result`，因此不能据此直接开放双条件分支。

此外，`ct_ifu_ipdp.v` 的 `tail_vld` 当前只围绕第一条条件分支形成一套 tail mask。双路设计还必须回答：第一条 Taken 时在第一条后截断；第一条 Not-Taken、第二条 Taken 时在第二条后截断；两条都 Not-Taken 且还有第三条时，在第二条后保留剩余窗口并重放。只改 stall 而不改这些 mask，会把预测 Taken 后的错误路径指令送入 IB。

### 8.3 raw stall、有效串行重放和 IB 保持必须分开

原始 `ifu_multi_branch_stall` 共拉高 14,544 周期，但该信号的组合条件没有排除 `ibctrl_ipctrl_stall`。当 IB、PCFIFO、误预测恢复或其他后端条件阻止 IP 前推时，同一个多分支窗口会保持，`br_more_than_one_stall` 也会重复为 1。此时既没有消费新的条件分支预测，也没有推进 IFDP 的剩余窗口。

因此新增分析使用：

```text
有效串行重放 = ifu_multi_branch_stall && !ifu_ip_pipeline_stall
IB 保持重叠  = ifu_multi_branch_stall &&  ifu_ip_pipeline_stall
```

其中 `ifu_ip_pipeline_stall` 直接对应 `ct_ifu_ibctrl/ibctrl_ipctrl_stall`。分解结果为：

| 口径 | 周期 | ROI 占比 | 含义 |
|---|---:|---:|---|
| raw 多分支 stall active | 14,544 | 8.511% | 信号为高的全部驻留周期 |
| 有效串行重放 | 13,174 | 7.710% | 本周期确实处理一条预测 NT 的条件分支，并准备继续处理后续分支 |
| 与 IB 保持重叠 | 1,370 | 0.802% | 当前多分支状态被其他 IB/后端阻塞保持；提高分支预测宽度不能单独删除这些周期 |

这也解释了原始连续段最大达到 14 周期的现象。16 字节窗口最多只有 8 个 half-word，不可能包含 15 条条件分支。最长的 14 周期段实际只有 **1 次有效重放和 13 个 IB 保持周期**，不能按“14 次连续分支预测”解释。

按每个 raw 连续段内真正发生的有效重放次数重新分类：

| 有效重放次数 | 连续段数 | 段占比 | raw active 周期 | 其中 IB 保持周期 | 对应最少预测数 |
|---:|---:|---:|---:|---:|---:|
| 0 | 2 | 0.017% | 5 | 5 | 0；状态在真正消费前已被取消或离开 ROI |

本次 CoreMark 没有观察到一个连续处理过程需要 3 次及以上有效重放。换句话说，绝大多数动态情况是“当前只能逐拍预测 2 条条件分支”，少数情况需要处理 3 条。这为首版设计宽度提供了直接依据。

### 8.4 stall 拉高不等于后端立即空转

由于当前周期的第一段仍可进入 IB，而且 IBUF、IDU、ROB 中还保存着先前指令，多分支 stall 周期多数仍有有效工作：

| 周期集合 | IDU 接收宽度均值 | IDU 非零供给率 | ROB create 宽度均值 | ROB 非零 create 率 | 退休宽度均值 | 非零退休率 |
|---|---:|---:|---:|---:|---:|---:|
| raw 多分支 active | 2.293 | 92.162% | 1.299 | 66.935% | 0.994 | 56.938% |
| 多分支 inactive | 2.353 | 86.271% | 1.254 | 60.688% | 1.054 | 57.452% |

这些数据不能解释成“stall 反而提高供给”。多分支事件集中在 CoreMark 的高控制流密度热点，前后周期本来就可能有大量指令；不同集合并非随机对照组。它能可靠说明的是：**14,544 个 active 周期不是 14,544 个零供给或零退休周期**。

以每段第一次有效重放为 0 点，IDU 非零供给率在第 0、1、2 周期仍为 90.555%、96.810%、93.248%，到第 3、4 周期下降到 73.596% 和 72.063%。这符合“前端分片先由缓冲吸收，供给影响若干拍后才传播”的流水线现象，但仍不能把第 3、4 周期的全部下降都归因于多分支处理。真实加速必须用 RTL A/B 比较总周期。

### 8.6 1 路、2 路和 3 路处理的结构模型

对每个连续处理过程，若当前实现发生 `E` 次有效重放，就至少顺序预测了 `E+1` 条条件分支。假设宽度为 `W` 的设计可按程序顺序每拍处理 `W` 条，且不改变方向预测结果，则剩余重放数建模为：

```text
residual(E, W) = max(ceil((E + 1) / W) - 1, 0)
```

模型结果如下。1,370 个 IB 保持周期始终保留，不再错误地算作分支宽度可消除的周期。

| 每拍条件分支预测宽度 | 剩余有效重放 | 消除有效重放 | 覆盖率 | 占 ROI 周期 | 串行删除模型全局提升 |
|---:|---:|---:|---:|---:|---:|
| 1（当前） | 13,174 | 0 | 0.000% | 0.000% | 0.000% |
| 2 | 1,106 | 12,068 | 91.605% | 7.062% | **+7.599%** |
| 3 | 0 | 13,174 | 100.000% | 7.710% | **+8.354%** |

2 路是更合理的第一版硬件目标。它覆盖 90.82% 的“一次重放”片段，并把需要三条预测的片段从两次重放降为一次；更重要的是，现有 PCFIFO 恰好只有两个 create port。3 路虽然在本次 trace 中多提供约 0.755 个百分点的模型收益，但必须继续加宽 PCFIFO、预测 payload 和相关优先级，代价明显高于收益增量。

PCFIFO 的两个端口承载的是全部 PC operation，不是专属于条件分支。开放两条条件分支后，若同一 IB 包中还存在 JAL、JALR 或其他需要 PCFIFO 记录的操作，`pcfifo_if_ibctrl_more_than_two` 仍可能触发 IB 侧分片。因此 1,106 个模型残余只是条件分支预测宽度的结果，真实 RTL 还可能出现新的 PCFIFO 吞吐残余；A/B 时必须同时观察 `ifu_pcfifo_multi_stall`，确认瓶颈是否只是从 IP 移到了 IB。

上述 +7.599% 和 +8.354% 仍是乐观的串行删除敏感度，不是预计 RTL 提速。有效重放周期也可能与已有 IBUF 指令、执行单元工作和退休重叠；双路预测还可能改变方向准确率、代码路径、I-cache 时序和时钟频率。它们只用于比较设计宽度，不用于验收性能。

### 8.7 可实施方案与推荐路线

| 方案 | 核心做法 | 可解决的问题 | 主要代价/边界 | 结论 |
|---|---|---|---|---|
| 直接清除 `br_more_than_one_stall` | 不再冻结 IF | 表面消除 raw stall | 第二条分支使用错误 VGHR/`chk_idx`，tail mask、PCFIFO 和 BHT 训练均不成立 | **禁止** |
| 编译器/代码布局 | 让条件分支跨 16 字节块分散，或用 if-conversion/控制流合并减少静态分支 | 可快速验证热点是否由代码布局触发 | 增大代码体积，可能恶化 I-cache；收益依赖编译器和 workload | 可做低成本 A/B，不是硬件最终方案 |
| 2 路独立预测上下文 | 同拍形成前两条条件分支的方向、目标、预测前 VGHR、counter 和 selector；最早 Taken 获胜 | 直接覆盖 91.6% 有效重放 | 需要第二预测读路径、第二套 payload/tail mask，增加面积和 IP 关键路径 | **首选微结构方案** |
| 下一历史行机会预取 | 单端口 BHT 空闲时提前缓存“当前历史再移一位”的方向行，命中时开放第二预测 | 少增加 SRAM，部分覆盖双分支 | 预取不保证及时；flush、写缓冲旁路和连续分支会降低覆盖率 | 可作为面积受限的备选实验 |
| IP 前增加剩余窗口队列 | IF 可继续取下一块，IP 仍逐拍排出分支片段 | 隐藏一部分 IF 冻结 | 没有提高每拍条件分支预测/PCFIFO 吞吐，持续高密度分支仍会填满队列 | 只能缓冲突发，不是根治 |
| 多分支 FTB/预测块 | 预测块直接保存多个分支位置和目标，并配套多方向预测 | 面向 SPEC 等复杂控制流的长期方案 | 改动 BTB、BHT、恢复、训练和验证协议，面积/功耗显著增加 | 长期重构方向 |

推荐的 2 路方案必须同时完成以下数据通路，不能只改 IPCTRL：

1. **第二分支定位**：IPDP 在第一分支后的剩余 `hn_con_br` 中找到第二分支，并生成“第一分支后”和“第二分支后”两套 mask。
2. **独立方向预测**：第二分支只在第一分支预测 Not-Taken 时可达，其预测前历史为 `{VGHR[20:0], 1'b0}`。需要读取该历史对应的方向表行，并形成独立 2-bit counter 和 selector。当前 1024×64 单端口方向表可通过增加第二读口、镜像一份约 64 Kbit 的预测存储，或可靠的提前缓存来实现。
3. **顺序 VGHR 更新**：第一分支 Taken 时只推进一次；第一分支 NT 且消费第二分支时按 `P0`、`P1` 顺序推进两次。flush 和 BJU 修复必须仍能恢复到每条分支预测前的历史。
4. **最早 Taken 优先**：`P0=T` 时忽略第二分支；`P0=NT, P1=T` 时选择第二目标；两条均 NT 且还有第三条时在第二条后重放。
5. **双预测 payload**：IPDP→IBDP→PCFIFO 为两条条件分支分别携带 `bht_pred`、`bht_pre_result`、`bht_sel_result`、预测前 VGHR、PC 和目标。
6. **PCFIFO/BJU 训练闭环**：两个 create port 生成不同的 `chk_idx`；BJU 对每条动态分支使用自己的上下文校验和更新，不能共享第一分支元数据。
7. **回退机制**：第二预测行、selector 旁路或下游资源不可用时，必须回退到当前单路重放，保证功能正确性先于性能。

组合时序的主要风险是 `P0 → 第二历史/第二方向选择 → P1 → earliest-taken mask → PC redirect`。因为第二分支仅在 `P0=NT` 时可达，可以提前并行计算“历史追加 0”对应的第二预测，再由 `P0` 做最终门控，避免把完整第二次 SRAM 读取串在 P0 后面。即便如此，第二分支定位、两个 counter mux 和 tail mask 仍可能成为 IP 关键路径，必须用综合时序而不是 RTL 仿真周期数判断可行性。

### 8.8 本次加入的代码原型和验收要求

`smart_run/experiments/branch_predictor/multi_branch/ct_ifu_multi_branch_resolver.v` 给出了尚未接入主核的可综合双路顺序解析原型。它固定了第一 Taken 优先、第二上下文无效时回退、两次 VGHR 顺序推进、第二 Taken 选目标和第三分支重放等控制规则。配套 testbench 已覆盖无分支、单分支 NT、第一分支 Taken、第二上下文缺失、双 NT、第二 Taken 和仍有第三分支七种情况。

该原型**不是已经完成的性能优化**：它要求上游先提供第二条分支独立且历史正确的预测上下文，尚未改动主 BHT SRAM、IPDP/IBDP payload 和 PCFIFO。这样安排是为了先把可验证的控制契约固化，避免用错误的共享预测元数据得到虚假的 CoreMark 提速。

后续真正接入主 RTL 后，最低验收条件是：

- 原生模式与双路模式使用相同 ELF、ROI 和 cache 初态；
- `effective_serial_replay_cycles` 应从 13,174 显著下降，2 路模型参考残余为 1,106，但不把该值当硬性等式；
- 48,002 条现有 PCFIFO 预测上下文配对必须继续保持 100%，并新增第二 create port 的独立上下文校验；
- BJU EX1→EX2 身份、BHT 更新公式、退休分支数和最终程序签名必须全部闭环；
- 同时比较总周期、IPC、方向误预测率、目标误预测、IFU/IDU 供给、I-cache 行为、综合频率、BHT/IFU 面积和功耗代理；
- 若 IPC 上升但综合频率下降，应以 `IPC × Fmax` 或固定工艺下的 CoreMark/s 评价，而不是只看周期数。

## 9. 如何解释“预测正确仍有开销”

正确预测不是统一的零开销事件，应按目标产生位置区分：

| 正确情形 | 本次可观察证据 | 解释 |
|---|---|---|
| 正确 Not-Taken | 不产生 redirect，执行级有 25,758 次 | 顺序 PC 已在取指，通常没有控制流转向气泡，但分支仍占 BJU/队列资源 |
| L0 正确 Taken | L0 redirect 的目标通常 1 周期进入 IF | 最早转向路径；目标进入 IDU 仍需经过后续前端级 |
| IP 正确 Taken | IP 主预测 19,629 次，目标通常 1 周期进入 IF | 比 L0 更晚获得预测信息，可能形成较小的前端间隙 |
| IB RAS 正确 Return | 251 次，精确目标进入 IDU 中位 6 周期 | Return 在更晚级产生目标，且前端缓冲中的任意供给不能代表 Return 目标已经到达 |
| 同一取指块有多个条件分支 | 14,544 raw active 周期，其中 13,174 次有效串行重放 | 即使每条分支方向都预测正确，前端解析吞吐限制仍会产生等待；IB 保持周期不能算成分支宽度收益 |

v3 已经把 PCFIFO payload、PID、BJU IID/PID 和 RTU 恢复串成逐动态分支身份链，并能对成功匹配的正确 Taken 样本计算“分支 IDU 接收→目标 IDU 接收”的空拍。它仍不是从 IF 首拍开始的全核硬件 transaction ID：IF/IP redirect 与具体分支的关联使用取指块 PC，IDU 使用低 15 位半字 PC。因此报告给出覆盖率和分布，不把样本均值宣传为固定的架构 penalty。若未来要在任意大程序上达到逐条 100% 的 IF→退休身份，需要专门增加跨 IF/IP/IB/IDU 的 debug tag。

## 10. 子机制理想化的全局性能收益评估

### 10.1 评估方法与公式

本节回答反事实问题：如果单独把某个分支预测子机制理想化，CoreMark 的全局性能可能改善多少。基线为：

```text
C = 170,876 cycles
I = 231,917 retired instructions
IPC = 1.3572
CoreMark/MHz = 5.852197
```

对可转化为周期数的事件，采用统一的“序列删除模型”：

```text
模型剩余周期     Cideal = C - ΔC
模型 IPC          IPCideal = I / Cideal
模型加速比        Speedup = C / Cideal
全局性能提升      Gain = (Speedup - 1) × 100%
```

其中 `ΔC` 是假设理想化后完全消失、且全部处于串行关键路径上的周期。这个模型用于比较优化机会，不等价于真实 RTL 性能预测，原因有两面：

1. 它可能偏乐观：某个 stall 拉高时，其他独立指令仍可能执行；不同 stall 可能重叠；删除一个事件后也不保证每个周期都能退休有效指令。
2. 它也可能漏算：现有波形从 BJU 已发现错误后开始统计恢复，没有计入错误分支从取指到 EX1 之间的错误路径取指、译码、发射和 cache 污染。

因此，下文的百分比是“把该机制映射成周期后的全局敏感度”，不是严格数学上界或下界。真正的性能收益仍应通过单变量 RTL A/B 仿真确认。

| 同一 fetch block 最多处理 3 条条件分支 | 本次 trace 的有效重放最多为 2 次，3 路模型消除全部 13,174 个 | 13,174 | 7.710% | 1.4706 | **+8.354%** | 3 路超出现有 PCFIFO 两个 create port，硬件代价明显更高 |

表中各行不能直接相加。例如，一个 L0 miss 事件可能处在多分支 stall 附近；把 L0 覆盖和多分支吞吐同时理想化时，两个单项模型可能试图删除同一个周期。组合收益必须先求逐周期事件并集，再套用加速公式。

### 10.3 条件方向预测理想化为何是约 8.9%，而不是 6.944%

`6.944%` 是每条条件分支的方向误预测率；`8.899%` 是把误预测后的恢复周期映射到全程序周期后得到的性能敏感度，二者的分母和物理意义不同。

对 3,285 个架构条件方向误预测：

```text
cancel→IDU/IFU 恢复总周期 = 13,964
恢复周期占全程序周期      = 13,964 / 170,876 = 8.172%
序列删除后的模型加速      = 170,876 / (170,876 - 13,964) - 1
                           = 8.899%
```

性能提升高于周期占比，是因为加速比的分母变成了更短的执行时间，而不是简单用删除周期除以原周期。

同时，`+8.899%` 不是完整的完美方向预测收益。方向预测正确还会避免 BJU 发现错误之前的错误路径工作，因此真实 A/B 可能得到更大收益；但恢复 stall 中也可能夹杂可并行完成的工作，因此真实 A/B 也可能更小。当前 trace 无法确定两种效应抵消后的净值。

### 10.4 误预测恢复链中每个子环节的理想化收益

3,292 个架构误预测的 `cancel→恢复` 可以分解成三个首尾相接的区间：

| 恢复子机制 | 周期总和 | 占 ROI 周期 | 单独序列删除后的模型 IPC | 模型全局提升 | 对应优化方向 |
|---|---:|---:|---:|---:|---|
| BJU cancel→误预测分支退休 | 7,457 | 4.364% | 1.4192 | **+4.563%** | 分支更早发射、减少分支前老指令长尾、缩短到 ROB Head 的等待，或使用不依赖退休的 checkpoint 恢复 |
| 误预测分支退休→RTU flush | 3,293 | 1.927% | 1.3839 | **+1.965%** | 缩短 RTU 状态机确认与 flush 生成路径 |
| RTU flush→IDU/IFU 保护解除 | 3,292 | 1.927% | 1.3839 | **+1.964%** | flush 同周期释放、减少固定恢复寄存级，或让正确路径在安全条件下更早放行 |
| 三段合计，仅架构配对事件 | 14,042 | 8.218% | 1.4787 | **+8.953%** | 完整理想化退休同步和恢复控制 |

三个子环节的模型收益不能按百分比直接相加，应先相加删除周期再计算总加速。三段周期 `7,457 + 3,293 + 3,292 = 14,042`，与 stall 表中的 14,103 个去重活跃周期相差 61 周期。逐事件区间还包含 17 个已选中但未作为架构误预测退休的事件，共 114 周期，以及 9 个被 PCGEN 高优先级来源遮蔽的 cancel 周期；所有事件区间相加为 14,165 周期，其中有 62 个周期因相邻或重叠恢复被重复计算。去重后满足 `14,042 + 114 + 9 - 62 = 14,103`。因此，14,042 是架构误预测恢复区间之和，14,103 是硬件 stall 信号的全 ROI 周期并集，二者口径不同。

这张表说明，在现有 C910 恢复协议中，最大的后确认开销不是 `retire→flush` 那一个固定周期，而是 BJU 已经知道正确目标后仍要等待误预测分支达到可退休状态。若目标是缩短误预测惩罚，研究 checkpoint/rename map 快速恢复、允许未退休分支触发精确恢复，通常比只压缩 RTU 内部一个寄存级更有潜力，但验证复杂度也显著更高。

### 10.5 全局分支预测器理想化

为了避免“理想分支预测器”定义不清，本报告给出三个层级。

| 全局理想化层级 | 包含的机制 | 删除周期 `ΔC` | 模型周期 | 模型 IPC | 模型 CoreMark/MHz | 模型全局提升 |
|---|---|---:|---:|---:|---:|---:|
| 基线 RTL | 当前全部机制 | 0 | 170,876 | 1.3572 | 5.8522 | 0.000% |
| A：完美准确率，保留现有前端吞吐与转向时延 | 删除全部 14,103 个 BJU 恢复 stall 活跃周期 | 14,103 | 156,773 | 1.4793 | 6.3786 | **+8.996%** |
| B：完美准确率 + 无限多分支处理吞吐 | 删除 14,103 个 BJU 恢复周期和 13,174 个有效串行重放周期；后者已排除 IB/BJU 保持，因此二者不重叠 | 27,277 | 143,599 | 1.6150 | 6.9638 | **+18.995%** |
| C：扩展的理想零延迟预测前端 | B 的删除周期，再加入 L0 纠错、L0 覆盖、Addrgen 目标和 IB RAS 时延模型 | 31,687～33,766 | 139,189～137,110 | 1.6662～1.6915 | 7.1845～7.2934 | **+22.765%～24.627%** |

层级 A 是最接近现有硬件事件的“完美准确率”估算，但仍只覆盖 BJU 已发现错误后的恢复。层级 B 进一步假设预测器每周期可以处理 fetch block 中的全部条件分支，它更接近“准确且高吞吐”的理想预测前端。

层级 C 是敏感性包络，不是严格周期并集。其附加周期来自：

```text
L0 错误早预测纠正         792
L0 Taken/Target 纠正提前   211～422
L0 miss 覆盖提前           2,354～3,420
Addrgen 直接目标纠正提前   551～1,102
IB RAS 提前到 L0           502～753
附加机会合计               4,410～6,489 cycles
```

这些附加机会没有完整的逐周期互斥信息，可能与层级 B 的 stall 重叠，所以 `22.765%～24.627%` 只能用作“如果各项提前量都落在串行关键路径上，可能接近什么量级”的乐观包络，不能作为最终设计目标验收值。

### 10.6 应如何使用这些提升数字

从工程决策角度，建议把数字分成三种用途：

1. **RTL A/B 的近期目标**：优先验证条件方向准确率和恢复协议。`+8.996%` 是现有恢复 stall 对全局性能的直接敏感度，适合判断是否值得投入。
2. **前端吞吐的结构目标**：排除 IB 保持后，多分支有效串行重放的 2 路单项模型为 `+7.599%`，3 路/无限宽模型为 `+8.354%`。准确率改进和多分支吞吐改进可能互相影响，必须分别 A/B 后再组合。
3. **理想上层参考**：`+18.995%` 是 BJU 恢复和有效多分支重放的组合模型，`+22.765%～24.627%` 是加入级间提前量后的乐观包络。实际可实现设计通常只能获得其中一部分，并需付出面积、时序和功耗成本。

后续真实实验至少应建立以下四个可独立开关的 RTL 配置：

```text
native
perfect_direction_and_target_accuracy_with_native_latency
native_accuracy_with_two_conditional_branches_per_cycle
perfect_accuracy_plus_two_conditional_branches_per_cycle
```

每个配置必须保持相同 ELF、相同 ROI、相同 cache 初态和相同随机输入，并比较总周期、退休指令、BJU recovery stall、多分支 stall、前端供给宽度和目标侧 I-cache 行为。只有这样得到的加速比才能称为“理想化子机制带来的实测全局性能提升”。

## 11. 性能瓶颈判断

本次数据支持以下优先级。

### 11.1 第一优先级：条件分支方向准确率与误预测恢复

条件分支占退休指令 20.397%，方向误预测率 6.944%，总误预测 14.195 MPKI。每个架构误预测不仅触发 BJU redirect，还使 IDU/IFU 恢复保护典型持续 3 周期、P90 持续 6 周期，并浪费发现错误前已经进入流水线的错误路径工作。因此降低方向误预测仍有较高价值。

不过，不能用 `14,103 / 170,876 = 8.253%` 直接宣称理想预测器会提升 8.253%。这些周期可能与其他阻塞重叠，部分周期前端或其他单元仍有有效活动；预测器改变也会改变 cache、队列和指令时序。精确性能收益必须通过 RTL A/B 实验测量。

### 11.2 第二优先级：多分支取指块处理吞吐

raw 多分支 stall 为 14,544 周期，其中 13,174 周期是真正推进剩余窗口的有效串行重放，1,370 周期是 IB 保持重叠。12,070 个连续片段中，90.82% 只发生 1 次有效重放，9.16% 发生 2 次，因此首版应优先实现两条条件分支的独立预测上下文，而不是追求无限宽。修正后的 2 路模型收益为 +7.599%，3 路上限为 +8.354%，略低于现有 BJU 恢复 stall 的 +8.996%，所以它应排在方向准确率/恢复之后，但仍是第二个高价值单项。详细 RTL 链路、宽度模型、热点和方案比较见第 8.1～8.8 节。

### 11.3 Return 路径样本少，但单次恢复更长

239 次退休 Return 中有 7 次目标误预测。样本数很小，但它们的 cancel→恢复中位数为 12 周期，明显长于条件方向错误的 3 周期。后续可用专门的深调用、非规则返回和 RAS 溢出测试，分开验证 RAS 容量、push/pop 时机、L0 RAS 快路径和异常恢复一致性。

### 11.4 本次不能评价 Indirect BTB

本次 `indirect_btb_checks=0`，因此 CoreMark 这一 ROI 不能说明间接分支预测器好坏。不能把 0 miss 解释成 100% 命中。应使用函数指针、虚调用、解释器 dispatch 或专门 JALR target pattern benchmark 补足。

### 12.2 必须保留的限制

1. 本次只有 1 次 CoreMark 迭代，适合波形机制研究，不适合正式分数稳定性评估。
2. IFU→IDU 精确目标 PC 使用低 15 位半字地址匹配。本次 CoreMark 代码地址范围允许唯一匹配；匹配覆盖率为 91.596%，更大程序需要重建高位或增加 debug tag。
