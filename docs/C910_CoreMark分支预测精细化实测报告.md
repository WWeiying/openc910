# C910 CoreMark 分支预测精细化实测报告

## 1. 测试目的与结论

本报告记录 OpenC910 RTL 在 **CoreMark 1 次迭代**上的分支预测精细化波形统计。测试的目的不是重新发布一个正式 CoreMark 分数，而是用短而完整的 CoreMark kernel，精确回答以下问题：

1. 程序实际退休了多少条件分支、Taken/Not-Taken 比例如何、架构可见误预测率是多少。
2. L0 BTB、IP 主预测、IB RAS、Addrgen 前端纠错和 BJU 后端纠错分别发生了多少次。
3. 每类 redirect 到正确目标进入 IF、进入 IDU、重新创建 ROB 项分别需要多久。
4. BJU 发现误预测后，分支退休、RTU flush、IDU/IFU 恢复各需要多久。
5. 正确预测时仍可能存在的多分支解析、RAS 晚转向等结构开销有多大。

本次结果的核心结论如下。

- CoreMark 共退休 **231,917** 条指令，其中 **47,305** 条是条件分支，占退休指令的 **20.397%**。这是一个控制流密度很高的工作负载。
- 条件分支方向预测准确率为 **93.056%**，方向误预测 **3,285** 次；加上 **7** 次 Return 目标误预测，总误预测为 **3,292** 次，即 **14.195 MPKI**。
- ROI 共执行到 **303 个静态条件分支 PC**，其中 **206 个**产生过架构可见方向误预测。Top 30 静态分支贡献 **2,095** 次错误，占全部方向误预测的 **63.775%**；只有 27 个静态分支恰好错 1 次，因此错误呈现“少数热点加长尾”，不是平均分布。
- 48,002 条执行级条件分支的 PCFIFO 预测上下文和 PID/payload 配对率均为 **100%**；47,999 条进入 EX2 的事件身份错误为 **0**，3,285 条方向错误全部与最终退休误预测严格配对。
- BJU 误预测恢复保护占 **14,103 周期，8.253%**。条件分支误预测从 BJU cancel 到 IDU/IFU 解除保护的中位数为 **3 周期**，P90 为 **6 周期**，最大为 **23 周期**。
- 条件分支误预测发生后，正确目标通常在 **1 周期**后重新进入 IF，目标指令进入 IDU 的中位数为 **3 周期**。这说明 C910 的典型路径是“前端很快重定向，后端等待退休和 RTU 恢复后再放行”。
- 多条件分支解析 stall 占 **14,544 周期，8.511%**，略高于 BJU 误预测恢复占比。它是本次 CoreMark 前端中与预测正确性不同、但同样重要的结构吞吐问题。
- 多分支 stall 与 BJU 恢复同时出现 **1,015 周期**，二者并集为 **27,632 周期，16.171%**。该并集表示“至少一种相关阻塞正在发生”，不能直接视为理想预测器可删除的周期数。
- 按“把已观测阻塞周期完全串行删除”的敏感性模型，只理想化预测准确率得到的全局性能提升为 **8.996%**；再理想化多分支处理吞吐得到 **19.290%**；继续加入 L0 覆盖、前端目标和 RAS 时延模型后，扩展包络为 **23.079%～24.950%**。这些是基于现有 trace 的反事实估算，不是 RTL A/B 实测结果。
- 极少数 `cancel→目标指令进入 IDU` 出现 65、71、81 周期长尾。波形抽查表明，这些样本的 BJU 恢复保护已经在 3 至 6 周期内解除，之后是目标侧长时间没有有效指令供给。因此最大值包含目标 I-cache/取指供给等叠加效应，不是纯分支预测恢复代价。

## 3. 统计口径

### 3.1 三种不能混用的事件层级

报告使用三类口径：

| 层级 | 代表信号/数据 | 可回答的问题 | 不能回答的问题 |
|---|---|---|---|
| 架构退休口径 | RTU 退休指令、条件分支、Taken、mispred 脉冲 | 最终真正执行了多少分支，准确率和 MPKI 是多少 | 不能直接看到被冲刷的投机执行 |
| 执行级口径 | BJU EX1 有效分支及实际/预测方向 | 方向错误由 `NT→T` 还是 `T→NT` 构成 | 不能作为退休分支准确率的分母 |
| 前端事件口径 | PCGEN 选中的 L0/IP/IB/Addrgen/BJU redirect | 各转向来源的频度和后续供给延迟 | 一个 redirect 事件不等于一条退休分支 |

正式准确率必须使用架构退休口径。执行级数据包含错误路径上后来被 flush 的分支，只能用来分析机制构成。前端 redirect 只在需要改变取指流时发生，正确 Not-Taken 分支不需要 redirect，因此 redirect 总数也不能作为全部分支的分母。

### 3.2 redirect 延迟的四个端点

每个 PCGEN 已选中的分支 redirect 从发起周期开始，匹配以下端点：

| 端点 | 定义 | 解释强度 |
|---|---|---|
| `to_target_if_valid` | 正确目标 PC 首次以有效取指块进入 IF | 最直接衡量 PCGEN 是否及时转到目标 |
| `to_exact_target_idu_accept` | 目标 PC 对应的具体指令首次被 IDU 接收 | 可观察目标路径真正进入后端；本次 CoreMark 代码范围内低 15 位半字 PC 足以唯一匹配 |
| `to_first_any_idu_accept_proxy` | redirect 后任意指令首次被 IDU 接收 | 供给恢复代理；可能是 IBUF 中较老指令，不能保证就是目标指令 |
| `to_first_any_rob_create_proxy` | redirect 后任意 ROB create 首次出现 | 后端活动恢复代理；不能单独证明目标指令已经创建 |

早期 redirect 的匹配窗口会在下一次硬 redirect 处截断，以免把后续控制流事件错误归因给当前事件。因此 L0/IP 的“精确目标 IDU 已观测数”较低不表示大量预测失败，而是短时间内又发生 redirect 后不再跨事件追踪。

BJU 误预测恢复是例外：属于同一次恢复的后续 RTU flush 不会截断目标路径，因而 **3,292 个架构退休误预测均成功配对**。

### 3.3 周期统计的含义

- `mean` 是平均值，容易被少量长尾拉高。
- `median` 是中位数，表示一半事件不超过该值，更适合描述典型延迟。
- `P90` 表示 90% 的事件不超过该值。
- `max` 用于定位异常事件，但不能代替典型惩罚。
- stall 周期可以与其他 stall 或有效工作重叠，不能把各项百分比直接相加。

## 4. 架构退休结果

### 4.1 分支密度、方向分布和准确率

| 架构指标 | 事件数 | 分母 | 比例/结果 |
|---|---:|---:|---:|
| 退休指令 | 231,917 | 231,917 | 100.000% |
| 退休控制流指令 | 50,292 | 231,917 | 21.685% |
| 退休条件分支 | 47,305 | 231,917 | 20.397% |
| 实际 Taken 条件分支 | 20,449 | 47,305 | 43.228% |
| 实际 Not-Taken 条件分支 | 26,856 | 47,305 | 56.772% |

### 4.4 每条动态分支携带的真实 BHT 状态

`ct_ifu_pcfifo_if.v` 把预测时状态编码进 25 位 `chk_idx`，该值随 PCFIFO 项一直传到 BJU。v3 逐条解码：

```text
chk_idx[21:0]       = 预测时 22 位 VGHR
chk_idx[23:22]      = bimode selector 的 2 位状态
{bht_pred,chk[24]}  = 实际选中的 2 位饱和计数器状态
```

同时按 `ct_ifu_bht.v` 的原公式重建更新位置：

```text
predict row = {GHR[13:10], GHR[9:4] XOR GHR[21:16]}
offset      = current_PC_index[3:0] XOR GHR[3:0]
bank        = selector[1] 选择 Taken/Not-Taken bank
select row  = current_PC_index[9:3]
select slot = current_PC_index[2:0]
```

在没有旧 BHT 写缓冲项占用更新口的 **38,230 次**直接更新中，重建出的 prediction row、selector row、更新后 prediction counter 和 selector counter 与 RTL 实际信号全部一致，错误为 **0**。这证明逐条 CSV 中的 BHT key、计数器强弱和 selector 状态不是离线猜测，而是对 RTL 编码的等价解码。

对 3,285 次架构方向误预测做互斥的“证据分类”得到：

| 单轨迹证据类别 | 架构误预测 | 含义 |
|---|---:|---|
| 该 predictor key 在 ROI 内首次出现 | 1,256 | 无法从 ROI 内看到它此前如何训练；可能与预热、ROI 前状态或新历史上下文有关，不能直接断言 cold miss |
| 相同 PC 与完整 22 位 GHR 曾对应相反结果 | 1,068 | 对当前可见上下文而言结果不可分，说明仅靠该全局历史上下文不足以唯一决定方向 |
| 所选 2 位计数器处于弱状态 | 736 | 预测状态接近翻转边界，常见于模式切换或训练不足 |
| 同一 prediction key 的前一次使用来自其他 PC 且结果相反 | 174 | 有明确的跨静态 PC 表项别名干扰证据 |
| 单次轨迹无法唯一归因 | 51 | 需要结构 A/B 或更长上下文才能判定 |
| 合计 | 3,285 | 与退休方向误预测完全守恒 |

这里必须区分“证据”和“因果证明”。例如 174 次具有直接跨 PC 别名证据，但不能据此断言扩大 BHT 必然全部消除；1,068 次相同 PC/GHR 结果不唯一，说明现有上下文不能区分，却不能单凭一次 trace 判定应增加全局历史、局部历史还是路径历史。严格因果归因仍需要分别改变表容量、索引哈希、历史长度和 predictor 组织做单变量 A/B。

### 4.5 动态分支身份链与正确预测开销

v3 同时抓取 IFU 送入 PCFIFO 的完整 payload、PCFIFO 实际写入 PID、BJU EX1/EX2 的 PID/IID/PC/`chk_idx` 以及 RTU 退休误预测。身份链定义为：

```text
IFU PCFIFO create payload
  → PCFIFO 实际写入并分配 PID
  → BJU EX1：PID + IID + PC + prediction + chk_idx
  → BJU EX2：PID + IID + halfword PC + chk_idx
  → BJU cancel
  → RTU retire mispred
  → RTU flush
  → IDU/IFU recovery release
```

48,002 条执行级条件分支的 IFU payload 上下文配对率为 **100%**，PCFIFO `PID+PC+prediction+chk_idx` 实际写入配对率也为 **100%**；47,999 条进入 EX2 的事件身份错误为 0，另有 3 条推测分支在 EX1 同周期遇到全局 flush，按 RTL 优先级被取消并未进入 EX2，未解释缺口为 0。3,285 条方向错误全部与最终退休误预测配对。后续 v3 运行会对 PID/payload 覆盖率设置 99% 的最低硬门槛，不满足时分析脚本直接失败，而不是生成残缺报告。

对可同时匹配“分支被 IDU 接收”和“正确目标被 IDU 接收”的 Taken 样本，可以直接计算两者之间的 IDU 空拍。当前低 15 位半字 PC 在 CoreMark 代码范围内无冲突，匹配覆盖率为 91.596%；结果如下：

| 正确 Taken 路径 | 动态事件 | 已匹配样本的平均 IDU 空拍 | P90 |
|---|---:|---:|---:|
| L0 BTB | 6,286 | 0.268 | 1 |
| IP 主预测 | 10,346 | 0.468 | 1 |
| L0 miss 后由 IP 预测 | 1,049 | 0.879 | 1 |

这些数值支持“L0 正确 Taken 最接近无气泡，IP 正确 Taken 通常不超过 1 个 IDU 空拍”的结构判断，但平均值只对成功身份匹配的样本成立。正确 Not-Taken 共 25,758 次，不产生 redirect；它的控制流转向开销通常为零，但仍占用 BIQ/BJU 执行资源，不能把该资源成本从本 trace 中直接换算为独立 IPC 损失。

## 5. PCGEN 转向来源

### 5.1 各级 redirect 的事件量

共识别 **43,911** 个分支相关 redirect：

| 转向来源 | 事件数 | 占全部 redirect | 微结构含义 |
|---|---:|---:|---|
| IP | 22,739 | 51.784% | 主 BTB/BHT 预测、L0 miss 后预测及 L0 早预测纠错 |
| L0 BTB | 17,061 | 38.854% | 最早的快速 Taken/Return 转向 |
| BJU | 3,309 | 7.536% | 执行级发现真实方向或目标错误后的恢复转向 |
| Addrgen | 551 | 1.255% | 前端重算直接分支/JAL 目标后纠错 |
| IB | 251 | 0.572% | 本次全部为 IB 级 RAS 转向 |

L0 BTB 与 IP 合计承担 90.638% 的 redirect，说明 CoreMark 的大多数取指流改变在前端早期解决。BJU redirect 占比只有 7.536%，但它会伴随错误路径取消、退休同步和后端恢复，单次代价明显高于 L0/IP 正确转向。

这个表揭示了三个不同层面的事实。

第一，绝大多数 redirect 在下一周期就能让正确目标进入 IF。L0、IP、IB 和典型 BJU 的 `目标进 IF` 中位数均为 1 周期，表明 PCGEN 选中转向后本身没有长组合延迟。

第二，正确目标进入 IF 不等于目标指令已经进入后端。L0/IP 精确目标进入 IDU 的典型值约为 3 周期；IB RAS 的精确目标中位数为 6 周期；BJU 条件误预测的典型值也是 3 周期，但会同时受后端恢复状态约束。

第三，`任意 IDU/ROB` 是供给恢复代理，不一定是目标指令。比如 IB RAS 后任意 IDU 供给中位数为 1 周期，而精确目标是 6 周期，这表示缓冲区内可能仍有较老或同一取指块中的其他指令在流动，不能把前者解释成 Return 目标已经到达。

通过“IP mistaken 事件向前匹配最近 L0 redirect，并要求 L0 lookup PC 与 IP VPC 完全一致”，得到 **545 对** L0→IP 纠正事件，身份匹配率为 100%。

| L0 到 IP 纠正延迟 | 事件数 | 比例 |
|---|---:|---:|
| 1 周期 | 307 | 56.330% |
| 2 周期 | 229 | 42.018% |
| 3 周期 | 9 | 1.651% |

平均延迟为 **1.453 周期**，中位数 1，P90 为 2，最大 3。这类事件是前端小纠错：L0 用更早但信息较少的预测换取低延迟，IP 随后用更完整的信息校验。它会浪费少量错误路径取指，但与 BJU 级误预测的全核投机恢复不是同一级代价。

典型条件方向误预测的恢复链可概括为：

```text
BJU EX2 cancel / PCGEN redirect
    ├─ 约 1 周期：正确目标重新进入 IF
    ├─ 中位 1 周期：误预测分支到达退休点
    ├─ 再 1 周期：RTU 发出 flush
    └─ 中位 3 周期：IDU/IFU 解除误预测保护
```

这不是说“完整误预测代价只有 3 周期”。BJU cancel 已经发生在分支经过 IF、IP、IB、ID、IR、IS、RF 和 BJU 执行之后；在 cancel 之前，错误路径已经占用了前端与后端资源。此表量的是 **BJU 已确认错误之后的恢复链**，不包含分支从取指到执行发现错误之前的时间，也不等价于 IPC 损失。

Return 目标误预测只有 7 个样本，不能据此稳定估计总体分布；但它们一致显示分支退休明显更晚，cancel 到恢复中位数达到 12 周期。这符合“Return/JALR 目标错误发现后，仍需等待该分支及更老指令满足退休恢复条件”的机制。

## 9. 如何解释“预测正确仍有开销”

正确预测不是统一的零开销事件，应按目标产生位置区分：

| 正确情形 | 本次可观察证据 | 解释 |
|---|---|---|
| 正确 Not-Taken | 不产生 redirect，执行级有 25,758 次 | 顺序 PC 已在取指，通常没有控制流转向气泡，但分支仍占 BJU/队列资源 |
| L0 正确 Taken | L0 redirect 的目标通常 1 周期进入 IF | 最早转向路径；目标进入 IDU 仍需经过后续前端级 |
| IP 正确 Taken | IP 主预测 19,629 次，目标通常 1 周期进入 IF | 比 L0 更晚获得预测信息，可能形成较小的前端间隙 |
| IB RAS 正确 Return | 251 次，精确目标进入 IDU 中位 6 周期 | Return 在更晚级产生目标，且前端缓冲中的任意供给不能代表 Return 目标已经到达 |
| 同一取指块有多个条件分支 | 14,544 stall 周期 | 即使每条分支方向都预测正确，前端解析吞吐限制仍会产生等待 |

v3 已经把 PCFIFO payload、PID、BJU IID/PID 和 RTU 恢复串成逐动态分支身份链，并能对成功匹配的正确 Taken 样本计算“分支 IDU 接收→目标 IDU 接收”的空拍。它仍不是从 IF 首拍开始的全核硬件 transaction ID：IF/IP redirect 与具体分支的关联使用取指块 PC，IDU 使用低 15 位半字 PC。因此报告给出覆盖率和分布，不把样本均值宣传为固定的架构 penalty。若未来要在任意大程序上达到逐条 100% 的 IF→退休身份，需要专门增加跨 IF/IP/IB/IDU 的 debug tag。

## 10. 子机制理想化的全局性能收益评估

### 10.1 评估方法与公式

本节回答反事实问题：如果单独把某个分支预测子机制理想化，CoreMark 的全局性能可能改善多少。基线为：

```text
C = 170,876 cycles
I = 231,917 retired instructions
IPC = 1.3572
CoreMark/MHz = 5.852197
```

对可转化为周期数的事件，采用统一的“序列删除模型”：

```text
模型剩余周期     Cideal = C - ΔC
模型 IPC          IPCideal = I / Cideal
模型加速比        Speedup = C / Cideal
全局性能提升      Gain = (Speedup - 1) × 100%
```

其中 `ΔC` 是假设理想化后完全消失、且全部处于串行关键路径上的周期。这个模型用于比较优化机会，不等价于真实 RTL 性能预测，原因有两面：

1. 它可能偏乐观：某个 stall 拉高时，其他独立指令仍可能执行；不同 stall 可能重叠；删除一个事件后也不保证每个周期都能退休有效指令。
2. 它也可能漏算：现有波形从 BJU 已发现错误后开始统计恢复，没有计入错误分支从取指到 EX1 之间的错误路径取指、译码、发射和 cache 污染。

因此，下文的百分比是“把该机制映射成周期后的全局敏感度”，不是严格数学上界或下界。真正的性能收益仍应通过单变量 RTL A/B 仿真确认。

| 同一 fetch block 的多条件分支可同周期处理 | 14,544 个 `ifu_multi_branch_stall` 活跃周期 | 14,544 | 8.511% | 1.4835 | **+9.303%** | 这是预测吞吐理想化，不是准确率理想化；部分周期可能仍有其他有效工作 |

表中各行不能直接相加。例如，一个 L0 miss 事件可能处在多分支 stall 附近；把 L0 覆盖和多分支吞吐同时理想化时，两个单项模型可能试图删除同一个周期。组合收益必须先求逐周期事件并集，再套用加速公式。

### 10.3 条件方向预测理想化为何是约 8.9%，而不是 6.944%

`6.944%` 是每条条件分支的方向误预测率；`8.899%` 是把误预测后的恢复周期映射到全程序周期后得到的性能敏感度，二者的分母和物理意义不同。

对 3,285 个架构条件方向误预测：

```text
cancel→IDU/IFU 恢复总周期 = 13,964
恢复周期占全程序周期      = 13,964 / 170,876 = 8.172%
序列删除后的模型加速      = 170,876 / (170,876 - 13,964) - 1
                           = 8.899%
```

性能提升高于周期占比，是因为加速比的分母变成了更短的执行时间，而不是简单用删除周期除以原周期。

同时，`+8.899%` 不是完整的完美方向预测收益。方向预测正确还会避免 BJU 发现错误之前的错误路径工作，因此真实 A/B 可能得到更大收益；但恢复 stall 中也可能夹杂可并行完成的工作，因此真实 A/B 也可能更小。当前 trace 无法确定两种效应抵消后的净值。

### 10.4 误预测恢复链中每个子环节的理想化收益

3,292 个架构误预测的 `cancel→恢复` 可以分解成三个首尾相接的区间：

| 恢复子机制 | 周期总和 | 占 ROI 周期 | 单独序列删除后的模型 IPC | 模型全局提升 | 对应优化方向 |
|---|---:|---:|---:|---:|---|
| BJU cancel→误预测分支退休 | 7,457 | 4.364% | 1.4192 | **+4.563%** | 分支更早发射、减少分支前老指令长尾、缩短到 ROB Head 的等待，或使用不依赖退休的 checkpoint 恢复 |
| 误预测分支退休→RTU flush | 3,293 | 1.927% | 1.3839 | **+1.965%** | 缩短 RTU 状态机确认与 flush 生成路径 |
| RTU flush→IDU/IFU 保护解除 | 3,292 | 1.927% | 1.3839 | **+1.964%** | flush 同周期释放、减少固定恢复寄存级，或让正确路径在安全条件下更早放行 |
| 三段合计，仅架构配对事件 | 14,042 | 8.218% | 1.4787 | **+8.953%** | 完整理想化退休同步和恢复控制 |

三个子环节的模型收益不能按百分比直接相加，应先相加删除周期再计算总加速。三段周期 `7,457 + 3,293 + 3,292 = 14,042`，与 stall 表中的 14,103 个去重活跃周期相差 61 周期。逐事件区间还包含 17 个已选中但未作为架构误预测退休的事件，共 114 周期，以及 9 个被 PCGEN 高优先级来源遮蔽的 cancel 周期；所有事件区间相加为 14,165 周期，其中有 62 个周期因相邻或重叠恢复被重复计算。去重后满足 `14,042 + 114 + 9 - 62 = 14,103`。因此，14,042 是架构误预测恢复区间之和，14,103 是硬件 stall 信号的全 ROI 周期并集，二者口径不同。

这张表说明，在现有 C910 恢复协议中，最大的后确认开销不是 `retire→flush` 那一个固定周期，而是 BJU 已经知道正确目标后仍要等待误预测分支达到可退休状态。若目标是缩短误预测惩罚，研究 checkpoint/rename map 快速恢复、允许未退休分支触发精确恢复，通常比只压缩 RTU 内部一个寄存级更有潜力，但验证复杂度也显著更高。

### 10.5 全局分支预测器理想化

为了避免“理想分支预测器”定义不清，本报告给出三个层级。

| 全局理想化层级 | 包含的机制 | 删除周期 `ΔC` | 模型周期 | 模型 IPC | 模型 CoreMark/MHz | 模型全局提升 |
|---|---|---:|---:|---:|---:|---:|
| 基线 RTL | 当前全部机制 | 0 | 170,876 | 1.3572 | 5.8522 | 0.000% |
| A：完美准确率，保留现有前端吞吐与转向时延 | 删除全部 14,103 个 BJU 恢复 stall 活跃周期 | 14,103 | 156,773 | 1.4793 | 6.3786 | **+8.996%** |
| B：完美准确率 + 无限多分支处理吞吐 | 删除 BJU 恢复与多分支 stall 的逐周期并集 27,632；已扣除 1,015 个重叠周期 | 27,632 | 143,244 | 1.6190 | 6.9811 | **+19.290%** |
| C：扩展的理想零延迟预测前端 | B 的并集，再加入 L0 纠错、L0 覆盖、Addrgen 目标和 IB RAS 时延模型 | 32,042～34,121 | 138,834～136,755 | 1.6705～1.6959 | 7.2028～7.3123 | **+23.079%～24.950%** |

层级 A 是最接近现有硬件事件的“完美准确率”估算，但仍只覆盖 BJU 已发现错误后的恢复。层级 B 进一步假设预测器每周期可以处理 fetch block 中的全部条件分支，它更接近“准确且高吞吐”的理想预测前端。

层级 C 是敏感性包络，不是严格周期并集。其附加周期来自：

```text
L0 错误早预测纠正         792
L0 Taken/Target 纠正提前   211～422
L0 miss 覆盖提前           2,354～3,420
Addrgen 直接目标纠正提前   551～1,102
IB RAS 提前到 L0           502～753
附加机会合计               4,410～6,489 cycles
```

这些附加机会没有完整的逐周期互斥信息，可能与层级 B 的 stall 重叠，所以 `23.079%～24.950%` 只能用作“如果各项提前量都落在串行关键路径上，可能接近什么量级”的乐观包络，不能作为最终设计目标验收值。

### 10.6 应如何使用这些提升数字

从工程决策角度，建议把数字分成三种用途：

1. **RTL A/B 的近期目标**：优先验证条件方向准确率和恢复协议。`+8.996%` 是现有恢复 stall 对全局性能的直接敏感度，适合判断是否值得投入。
2. **前端吞吐的结构目标**：多分支 stall 单项模型为 `+9.303%`，与预测准确率同等重要。准确率改进和多分支吞吐改进可能互相影响，必须分别 A/B 后再组合。
3. **理想上层参考**：`+19.290%` 是基于两个实测 stall 的组合模型，`+23.079%～24.950%` 是加入级间提前量后的乐观包络。实际可实现设计通常只能获得其中一部分，并需付出面积、时序和功耗成本。

后续真实实验至少应建立以下四个可独立开关的 RTL 配置：

```text
native
perfect_direction_and_target_accuracy_with_native_latency
native_accuracy_with_unlimited_multi_branch_throughput
perfect_accuracy_plus_unlimited_throughput
```

每个配置必须保持相同 ELF、相同 ROI、相同 cache 初态和相同随机输入，并比较总周期、退休指令、BJU recovery stall、多分支 stall、前端供给宽度和目标侧 I-cache 行为。只有这样得到的加速比才能称为“理想化子机制带来的实测全局性能提升”。

## 11. 性能瓶颈判断

本次数据支持以下优先级。

### 11.1 第一优先级：条件分支方向准确率与误预测恢复

条件分支占退休指令 20.397%，方向误预测率 6.944%，总误预测 14.195 MPKI。每个架构误预测不仅触发 BJU redirect，还使 IDU/IFU 恢复保护典型持续 3 周期、P90 持续 6 周期，并浪费发现错误前已经进入流水线的错误路径工作。因此降低方向误预测仍有较高价值。

不过，不能用 `14,103 / 170,876 = 8.253%` 直接宣称理想预测器会提升 8.253%。这些周期可能与其他阻塞重叠，部分周期前端或其他单元仍有有效活动；预测器改变也会改变 cache、队列和指令时序。精确性能收益必须通过 RTL A/B 实验测量。

### 11.2 同等重要：多分支取指块处理吞吐

多分支 stall 为 14,544 周期，略高于 BJU 恢复 stall，而且 12,070 个连续片段的中位数为 1 周期。这说明问题不是少量灾难性长停顿，而是高频、短促的前端吞吐损失。应重点研究：

- IP 对同一 fetch block 多个条件分支为何需要分拍处理；
- 能否并行完成更多分支位置、方向和目标选择；
- PCFIFO/预测上下文是否支持更高的每周期分支处理能力；
- 增强后是否引入新的关键路径、面积或错误优先级问题。

### 11.3 Return 路径样本少，但单次恢复更长

239 次退休 Return 中有 7 次目标误预测。样本数很小，但它们的 cancel→恢复中位数为 12 周期，明显长于条件方向错误的 3 周期。后续可用专门的深调用、非规则返回和 RAS 溢出测试，分开验证 RAS 容量、push/pop 时机、L0 RAS 快路径和异常恢复一致性。

### 11.4 本次不能评价 Indirect BTB

本次 `indirect_btb_checks=0`，因此 CoreMark 这一 ROI 不能说明间接分支预测器好坏。不能把 0 miss 解释成 100% 命中。应使用函数指针、虚调用、解释器 dispatch 或专门 JALR target pattern benchmark 补足。

### 12.2 必须保留的限制
