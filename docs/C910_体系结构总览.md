## 1. 一句话定位与设计目标

**C910 是一颗 RV64GC 指令集、12 级流水、3 发射译码 / 8 端口执行的乱序超标量
（out-of-order superscalar）高性能应用级处理器**，对标 ARM Cortex-A72/A73 量级，
目标是跑得动 Linux、追求高 IPC 与高频率的折中。

设计上贯穿三条主线，理解它们就理解了 C910 的全部取舍：

| 主线 | 含义 | 教科书对应 |
|------|------|-----------|
| **挖掘 ILP** | 乱序执行 + 寄存器重命名 + 推测执行，让无关指令并行跑 | H&P 第 3 章「指令级并行」 |
| **隐藏访存延迟** | 多级 cache + 非阻塞 cache（MLP≈8）+ 硬件预取 + store 缓冲 | H&P 第 2 章「存储层次」 |
| **保证正确性** | 顺序退休（ROB）+ 精确异常 + 缓存一致性 + 访存顺序违例检测 | Smith&Sohi「精确中断」 |

而 C910 作为一颗**商用核而非教科书核**，处处可见"在正确的前提下尽可能省面积/省功耗/
收时序"的工程取舍——下文会反复点出这些"非教科书"的聪明做法。

## 2. ISA 与编程模型

| 项目 | C910 |
|------|------|
| 基础 ISA | RV64GC = RV64 **I**MAFD**C**（64 位整数 + 乘除 + 原子 + 单/双精度浮点 + 压缩指令） |
| 自定义扩展 | **XIE**（XuanTie 指令扩展，即 `xtheadc`：addsl/ext/extu/ff1/rev/mveqz/tstnbz 等）、**XMAE**（内存属性扩展，给页表项加属性位） |
| 向量 | 早期私有向量扩展（非最终 RVV 1.0），与浮点共享寄存器堆 |
| 特权级 | M / S / U 三级，特权规范 v1.10，可跑完整 Linux |
| 虚拟内存 | Sv39（39 位虚地址，三级页表） |
| 兼容性 | 通过 RVA22 兼容性测试 |
| 浮点 | IEEE 754-2008，**不产生浮点异常**（用 fflags 标志位，不 trap）——简化了精确异常逻辑 |

**为什么自定义 XIE 扩展很关键？** RISC-V 基础指令集为了简洁，缺少一些复合操作
（如带移位的加法 `addsl`、位段提取 `ext`、找首一 `ff1`）。这些在编译热点（CoreMark
的状态机、字符串处理）里很常见。C910 用硬件直接支持它们：实测 CoreMark 从 4.4
（关闭 xtheadc）涨到 6.1（开启）——**约 40% 的提升来自 ISA 扩展**。这是"ISA 是体系结构
最重要部分"的活生生例子（H&P 第 1 章观点）。

**"G"和"C"各自的分量，以及 C 的隐藏代价**：G = IMAFD（整数 + 乘除 + 原子 + 单/双精度浮点），
是跑通用 OS/应用的底盘；**C（压缩指令）**用 16/32 位混合编码，平均省约 25~30% 代码体积、
顺带提升 I-Cache 命中率。但 **C 扩展不是免费的**——它让指令边界变成**动态的**（一条指令可能
16 或 32 位、甚至跨 cache 行），逼着前端做预解码（§4.3 的 predecode 阵列、§4.4 的 BRY 边界位）
来提前算边界。**这是一处典型的"ISA 决策溢出到微架构"**：指令集为省代码做的选择，前端就得
多花硬件来消化——体系结构的取舍常常跨层传导，读这份文档时要时刻留意这种因果链。

**"浮点不 trap、只置 fflags"为什么是一笔好买卖**：IEEE 异常（除零/上溢/无效…）在 C910 里
不产生陷入，只在 `fflags` 累加标志位，软件想知道再去读。**对乱序核这是一大简化**：若浮点会
trap，乱序窗口里每条在飞的浮点指令都可能在中途"诈"出异常，精确异常逻辑（§9.3）就得为它们
额外保留可回滚现场；改成"不 trap 只置位"后，浮点指令和普通运算一样"不会失败"，§6.4 的
"推定完成"才能成立。**用 ISA 层一个约定，换后端精确异常逻辑的大幅简化**——又一个跨层取舍。

**模块化 ISA 的思想**：RISC-V 是"小而稳的基座（RV64I）+ 可选扩展（MAFDC…）"的搭积木式
指令集。C910 在标准之上叠加私有的 XIE/XMAE，正是吃到了这种可扩展性的红利——既与标准工具链
兼容，又能针对自己的热点加专用指令。这与 x86/ARM"大一统巨型 ISA"是两条不同路线（H&P 第 1 章
ISA 设计原则）。

## 3. 总体流水线：12 级乱序超标量

### 3.1 流水级总览

C910 整数主流水线官方称 **12 级**（向量/浮点更长）。按功能可分为**顺序前端**、
**乱序执行**、**顺序退休**三段——这正是教科书里超标量乱序核的标准三段式
（Shen & Lipasti 称为 in-order front-end / out-of-order core / in-order retirement）：

```
┌──────────────── 顺序前端 (in-order) ────────────────┐┌─── 乱序 (OoO) ───┐┌─ 顺序退休 ─┐
                                                                                          
  PCGEN → IF → IP → IB →│ ID → IR → IS →│ RF →│ EX1 EX2 ...    →│   退休/提交
  ───────IFU───────  IBUF  ──────IDU──────      ───执行单元───      ────RTU────
  取指/分支预测      缓冲   译码/重命名/发射  读寄存器  ALU/LSU/FPU      ROB 按序退休

  ◄──────────────────── 顺序 ─────────────────►◄─── 乱序窗口 ───►◄── 顺序 ──►
```

| 阶段 | 流水级 | 单元 | 关键动作 |
|------|--------|------|----------|
| 取指 | PCGEN / IF / IP / IB | IFU | PC 生成、I-Cache 访问、预测、预解码、打包进 IBUF |
| 译码 | ID | IDU | 3 路并行译码、复杂指令拆分 |
| 重命名 | IR | IDU | 架构寄存器→物理寄存器，消除假依赖 |
| 发射 | IS | IDU | 分发到 7 个发射队列，唤醒-选择乱序发射 |
| 读寄存器 | RF | IDU | 读 PRF + 前递网络旁路 |
| 执行 | EX1~EX5 | IU/LSU/VFPU | 各功能单元，延迟不一 |
| 退休 | — | RTU | ROB 按程序序提交，精确异常 |

### 3.2 关键宽度参数（决定 IPC 上限）

| 维度 | 宽度 | 说明 |
|------|------|------|
| 取指宽度 | 128 bit / 拍（最多 4 条指令） | I-Cache 一次取半行 |
| 译码宽度 | **3 条 / 拍** | 3 个并行译码器 |
| 派遣宽度 | **4 微操作 / 拍** | 拆分后可多于译码数 |
| 发射端口 | **8 条执行管线** | pipe0~7 |
| 退休宽度 | **3 项 / 拍**（折叠后峰值 9 条 / 拍） | ROB 退休口 |

**为什么"译码 3、发射 8、退休 3"不对称？** 这是经典的"漏斗"设计（H&P 称 issue
是超标量瓶颈）：执行端口多（8）是为了吸收瞬时爆发和不同类型指令并行；译码/退休窄
（3）是因为它们是顺序段，加宽的时序与面积代价陡增、收益递减。平均 IPC 受限于最窄
的顺序段≈3，但乱序窗口让突发并行度短时冲到 8，整体逼近 3 这个上限。

**为什么是 12 级，不是更深或更浅？** 这是另一道经典权衡——**流水深度**（H&P 第 3 章
「流水线深度的代价」）。把同样的工作切成更多级，每级逻辑更少→**时钟更快**；但更深要付三笔账：
- **误预测惩罚线性增大**：分支预测错时要冲刷在途指令，流水越深冲得越多（§4.1 估过 12 级
  一次误预测冲约 5~8 条）；Pentium 4 那种 20+ 级就是被误预测惩罚拖累的反面教材。
- **相关指令的转发/唤醒更难**：生产者与消费者隔得越远，背靠背依赖越难做到 1 拍（§6.2 的
  EX1 前递正是为对抗这点）。
- **锁存器面积/功耗增加**：每多一级就多一排触发器。

更浅（如经典 5 级 RISC）则反过来：误预测便宜、转发简单，但每级塞太多逻辑、频率上不去。
**12 级是"够高频 + 误预测惩罚可控"的甜点**——而它敢用 12 级的前提，正是 §4 那套重金堆砌的
分级分支预测把误预测率压得足够低，让深流水的主要代价被摊薄。**这条因果链值得记住：
要高频就要深流水 → 深流水放大误预测代价 → 所以必须强分支预测**。前端投入与流水深度是一体两面。

## 4. 取指前端 IFU 与分支预测

### 4.1 为什么前端这么重视分支预测

12 级流水意味着一次分支预测失败要冲刷约 5~8 条在途指令。按"每 5 条指令一个分支"
估算，没有预测时 CPI 会从 1 恶化到 2 左右——**性能直接减半**。所以 C910 在前端堆了
一整套分级分支预测器，这是它面积/功耗投入最值的地方之一（H&P：分支预测是高 ILP 的前提）。

### 4.2 分级分支预测器（精度 vs 延迟的权衡）

| 预测器 | 容量 | 延迟 | 负责 | 设计动机 |
|--------|------|------|------|----------|
| **L0-BTB** | 16 项（纯寄存器） | **0 拍** | 热点跳转目标 | SRAM BTB 有 1 拍延迟，16 项寄存器表做"零延迟旁路"，让最热的分支不付预测延迟 |
| **BTB** | 1024 项 × 4 路组相联 | 1 拍 | 大多数跳转目标 | 主力目标预测器，4 路相联减少冲突 |
| **BHT** | 64K bits，**Bi-Mode** | 2 拍 | 条件分支方向 | Bi-Mode 把"偏跳/偏不跳"分两张表，解决 2-bit 计数器的别名污染 |
| **RAS** | 18 项（IFU 12 + RTU 6） | 0 拍 | 函数返回地址 | call/ret 配对模式，专用栈预测精度近 100% |
| **Loop Buffer** | 循环体缓冲 | — | 小循环 | 循环期间完全不访问 I-Cache，省功耗 + 免延迟 |

**两个最值得记的设计：**

1. **Bi-Mode BHT（方向预测）**：经典 2-bit 饱和计数器有"别名"问题——两条不相关分支
   映射到同一表项互相污染。Bi-Mode 用一张"选择表"把分支分流到"taken 倾向表"和
   "not-taken 倾向表"，同类分支聚在一起，干扰大减。配合 **22 位全局历史 GHR 折叠**
   成 10 位索引，捕捉历史相关性。这是 McFarling/Bi-Mode 学派的工业实现（H&P 第 3 章
   "相关预测器"）。

2. **投机 GHR + 退休 GHR 双历史**：取指时用投机更新的 VGHR（可能错）；RTU 退休时用
   精确的 RTUGHR。预测错时 `VGHR ← RTUGHR` 一键恢复。**以精度换吞吐**的典型手法。

### 4.3 取指数据通路要点

- **I-Cache**：64KB / 2 路 / 64B 行 / **VIPT** / FIFO 替换。VIPT（虚索引物理标签）让
  index 用虚地址、与 MMU 翻译并行，省一个周期；FIFO 替换只需 1 bit 而非 LRU 计数器，
  省面积（命中率损失很小）。
- **Predecode 阵列**：refill 时顺手预解码（标出指令边界、分支类型），存进 cache。
  因为 RVC 压缩指令让指令边界是动态的（16/32 位混合），预解码避免 IP 级重复算边界。
- **Way Predict + Bank 精确激活**：预测访问哪一路、哪个 bank，只唤醒目标 SRAM，
  分别省约 50% / 75% 的 Data 阵列读功耗。
- **IBUF（32 项，每项一个 16 位 half-word）**：解耦取指与译码的弹性缓冲（`ENTRY_NUM=32`；
  因 RVC 让指令边界按 16 位对齐，故按 half-word 而非整指令组织，向译码每拍排出最多 3 条指令）；
  空且下游不堵时支持
  **bypass** 直通 IDU 省一拍。

### 4.4 取指三级流水 IF / IP / IB（控制 + 数据通路）

§4.2 讲"预测谁"，这里讲"取指三级怎么走"。C910 把取指拆成 **IF→IP→IB** 三级，每级一对
**控制(ctrl) + 数据通路(dp)** 模块，把 SRAM 访问、解码/预测、分支解析三件事流水开，
维持每拍 4 指令吞吐：

| 级 | 控制 ctrl | 数据通路 dp |
|----|-----------|-------------|
| **IF** | stall 汇聚（refill / way-pred 失败 / 预测器无效化）；`fence.i` 的 I-Cache 无效化状态机 | 4 段 tag 比较定命中/路；切出 **BRY 指令边界位**；打包 L0/L1 BTB 数据 |
| **IP** | **分支碰撞检测**（一组里多个分支则 stall）；BHT 读写冲突管理；BTB/BHT/RAS 目标仲裁；生成 **chgflw** | Way0/Way1 并行解码 H1~H8 半字（分支类型/偏移）；BHT 方向与 BTB 目标**融合**；H0 跨行残留缓冲 |
| **IB** | IBUF/LBUF 仲裁；**RAS push(call)/pop(ret)** 门控；间接跳转 BTB 状态机 | 算 RAS 压栈 PC 与间接目标；after-head 重排 / after-tail 截断；选 bypass/merge/写缓冲 |

**关键机制**：
- **BRY 半字对齐**：RVC 让指令可能从半字中间起；两套 bry 位（假设 H1 在低半 / 在新起点）由 ipctrl 按 H0 有效性选择。
- **chgflw 分层**：IP 级预测 taken 即拉高转向；IB 级再叠加更晚才知道的转向，优先级 **LBUF 回边 > RAS-pop > 间接 BTB > L0-BTB 纠正**。
- **RAS push/pop 仅在 IB 不 stall 时进行**——防止误预测恢复期破坏返回栈。
- **投机/精确**：GHR、vtype 在 IP 级投机更新，误预测由 RTU 恢复（呼应 §4.2 双历史）。

**为什么拆 3 级**：单级取指要一拍内做完 SRAM 读 + tag 比较 + 多分支解码 + 预测融合 + 缓冲，
关键路径太长收不了高频；拆三级各司其职、用流水深度换频率（代价是误预测多冲几级，§6.2 用
前端早重定向补偿）。

> 细节见 `doc/ifu/`（17 篇）与 `doc/branch_prediction.md`。

## 5. 乱序引擎 IDU：译码 / 重命名 / 发射

IDU 是全核最大单元（56 个 RTL 文件，约 10.4 万行），它是**顺序→乱序的转换点**。

### 5.1 IR 重命名：消除假依赖（乱序的前提）

乱序执行必须先解决三类数据冒险中的两类"假依赖"：

```
RAW（真依赖）：写后读 —— 无法消除，靠唤醒+前递加速
WAR（假依赖）：读后写 ┐
WAW（假依赖）：写后写 ┘ 源于"架构寄存器只有 32 个"被反复复用 → 重命名消除
```

**寄存器重命名原理**：给每次写入分配一个全新的物理寄存器（physical register），
架构寄存器 x0-x31 只是"别名"。重命名表 RAT 记录"每个架构寄存器当前映射到哪个 preg"。
这样两条写同一个 x1 的指令用不同 preg，WAW/WAR 自动消失（Tomasulo 算法的现代物理寄存器实现，
H&P 第 3 章；对比 R10000/Alpha 21264 的统一物理寄存器堆方案）。

C910 有**三套独立 RAT**（整数 / 浮点 / 向量），因为三类寄存器互不干扰，分开管理更省端口。

| 物理寄存器堆 | 规模 | 备注 |
|--------------|------|------|
| 整数 PRF | **96 项**（= 32 架构正身 + 64 重命名额度） | 决定整数乱序窗口大小 |
| 浮点 / 向量 PRF | **64 项** | 浮点与向量共享空间 |
| ereg | 扩展状态寄存器 | vsetvl 配置组重命名 |

> **为什么 96 项整数 preg？** 它必须 ≥ 在途整数指令数。ROB 64 项 + 发射队列在途，
> 96 项是窗口大小与寄存器堆端口面积（读写端口随容量平方增长）的平衡点。

### 5.2 IS 发射：7 个发射队列 + 唤醒-选择

C910 用**分布式发射队列**（distributed reservation stations，对比 Intel P6 的集中式
RS），每类功能单元一个队列，深度 **8~12 项**（访存/分支队列更深，见下表）：

| 队列 | 深度 | 服务单元 | 目标管线 |
|------|------|----------|----------|
| AIQ0 | **8** | ALU0 + DIV + SPECIAL | pipe0 |
| AIQ1 | **8** | ALU1 + MULT | pipe1 |
| BIQ | **12** | BJU 分支 | pipe2 |
| LSIQ | **12** | Load / Store 地址 | pipe3 / pipe4 |
| SDIQ | **12** | Store 数据 | pipe5 |
| VIQ0 | **8** | VFPU0 | pipe6 |
| VIQ1 | **8** | VFPU1 | pipe7 |

> 队列深度并非一刀切：**BIQ/LSIQ/SDIQ 为 12 项、AIQ0/AIQ1/VIQ0/VIQ1 为 8 项**
> （总容量 8+8+12+12+12+8+8 = **68 项**）。分支与访存指令既多发又长延迟（cache miss、
> 顺序违例重发），更深的队列能多容纳在途项、减少因队列满而 stall——把缓冲投到最易
> 堵的地方，是分布式队列"按需配深度"的典型做法。

**唤醒-选择（wakeup-select）**是乱序调度的心脏：每个队列项里的"依赖项"（`dep_*` 模块）
追踪一个源操作数等待的 preg 号；执行单元产生结果时**广播 preg 号**，所有依赖项比对，
命中则把该源标记就绪（唤醒）；一项所有源就绪即成发射候选，仲裁逻辑按年龄选一条发射
（select）。C910 把唤醒逻辑下沉成可复用的 `dep_reg_entry` 原子模块，是漂亮的模块化。

**分布式 vs 集中式队列的权衡**：分布式队列每个小、端口少、时序好（适合高频），代价是
负载不均（某队列满了即使别处空也得停）。集中式利用率高但端口多、难收时序。C910 选
分布式是高频导向的选择。

> 细节见 `doc/idu/`（23 篇）。

## 6. 执行单元 IU / VFPU

### 6.1 8 条执行管线分工

```
pipe0  ALU0 + DIV + SPECIAL   整数运算 / 除法 / CSR / vsetvl   ┐
pipe1  ALU1 + MULT            整数运算 / 乘法·乘累加           ├ IU 整数单元
pipe2  BJU                    分支跳转 / 误预测判定            ┘
pipe3  LSU Load               load 地址生成 + 数据返回         ┐
pipe4  LSU Store-addr         store 地址生成                  ├ LSU 访存单元
pipe5  LSU Store-data         store 数据                      ┘
pipe6  VFPU0                  浮点 / 向量（5 级 EX）           ┐
pipe7  VFPU1                  浮点 / 向量（5 级 EX）           ┘ VFPU
```

### 6.2 IU 的关键设计

**两条对称 ALU + 长延迟单元搭车**：
- pipe0/pipe1 是**完全相同的两个 ALU**（同一 RTL 模块例化两次），保证最常见的整数运算
  每拍双发射。
- **长延迟单元挂在 ALU 管线上搭便车**：DIV 挂 pipe0、MULT 挂 pipe1，共享发射端口和写回
  端口省面积。代价是 div/mult 发射那拍对应 ALU 不能再发 ALU 指令（由 AIQ 仲裁保证）。

**前递（forward）与写回（writeback）分离**——乱序核实现"1 拍 ALU 延迟"的标准做法：
- ALU 在 **EX1** 就把结果**前递**回前递网络，让 back-to-back 依赖指令下一拍即可发射；
- **EX2** 才**写回** PRF 并通知 RTU 完成。
- 但前递总线是全核时序最紧的网络，所以只有"短指令"（add/逻辑/移位）走 EX1 前递；
  "长指令"（max/min/addsl，走独立选择树到达晚）不进前递、消费者等 EX2 写回（2 拍）。

**乘法器（MULT，4 拍）**：65×65 统一有符号乘法器处理四种符号组合（窄一位换统一）。
**EX3 发 preg 预告、EX4 出数据**——发射队列提前一拍唤醒消费者，数据恰好对齐。乘累加
（MLA）有私有前递链，背靠背 MLA 2 拍一条。

**除法器（DIV，变延迟 6~22 拍）**：SRT 基-16 每拍出 4 位商，延迟随操作数有效位宽变化；
有 2 项结果缓存——`a/b; a%b` 成对出现时第二条必命中（一次迭代同时得商和余数）。

**分支单元（BJU）—— "早重定向 + 晚清理"**（全核最重要的时序机制之一）：

```
EX1 判断误预测（方向错 = 实际 ^ 预测；jalr 目标错 = PCFIFO预存值 ≠ src0）
EX2 同时发三枪：
  ① iu_ifu_chgflw   → IFU 立即从正确目标取指（前端抢跑，抢回延迟）
  ② iu_yy_xx_cancel → 杀死 IU 各级错误路径指令
  ③ mispred_stall   → 新路径指令最远只到 ID 级等待
…后端继续跑老指令（错误路径被 cancel 压住）…
分支退休 → RTU flush → rtu_yy_xx_flush（后端清空、重命名表恢复）→ 放行新指令
```

为什么后端要等退休才 flush？因为后端混着无法逐条精确杀死的错误路径指令、重命名表是
污染态，必须由顺序退休级统一恢复。**前端早重启抢回取指延迟，后端按序刷新保证精确状态**。

**PCFIFO（32 项）** 是这套机制的数据载体，也是一处精彩的面积优化：ROB 为省面积不存
完整 PC，跳转指令的真实 PC/目标存在 PCFIFO。IFU 创建项（存预测现场）、BJU 执行时读出
对比、RTU 退休时按序弹出拿到精确退休 PC。

### 6.3 VFPU 详细架构（pipe6 / pipe7）

VFPU 由四个子单元组成，两条管线（pipe6/pipe7）结构完全对称，每条各有一套：

| 子单元 | 缩写 | 操作 | 管线深度 | 延迟（拍） |
|--------|------|------|----------|------------|
| Float ALU | **vfalu** | fadd/fsub、fmin/fmax/fcmp/fclass（fspu）、浮点转换（fcnvt） | 3 级（EX1→EX2→EX3） | **3** |
| Float MAU | **vfmau** | fmul、fmadd/fmsub/fnmadd/fnmsub | 5 级（EX1→EX5） | **5** |
| Float DSU | **vfdsu** | fdiv、fsqrt | SRT-16 迭代，见下 | 变延迟 |
| （向量通路） | vfalu 宽路 | 半精度向量算术（SIMD on vfalu） | 同 vfalu | **3** |

**vfalu 三类算子分工**：`dp_vfalu_ex1_pipex_sel[2:0]` 的 bit0/bit1/bit2 分别选中
FSPU（比较类）/ FADD（加减类）/ FCNVT（转换类），三者共用同一条 EX1→EX3 管线，
ex3_pipedown 时写回 PRF（RTL：`ct_fadd_ctrl.v`、`ct_fspu_ctrl.v`）。

**vfmau 五级 FMA 流水**：控制寄存器 `ctrl_ex5_fma_wb_vld` 在 EX5 拍触发写回。
对半精度（dp_xx_ex*_half）有独立的"half 管线"——从 EX1 到 EX5 每级都有
`mult*_half_pipedown` 旁路，复用一半硬件实现 SIMD F16（RTL：`ct_vfmau_ctrl.v`）。

**vfdsu 变延迟**：SRT 基-16 每拍产出 4 位有效商，延迟严格由操作数精度决定：

| 精度 | SRT 轮数（srt_cnt 从 N 倒计到 0） | SRT 拍数 | 总延迟估算 |
|------|----------------------------------|----------|------------|
| 半精度（f16） | 3 → 0 | **4** 拍 | ~8 拍 |
| 单精度（f32） | 6 → 0 | **7** 拍 | ~11 拍 |
| 双精度（f64） | 13 → 0 | **14** 拍 | ~18 拍 |
| fsqrt（double，需 2 轮 SRT） | 13×2 | **~28** 拍 | ~30+ 拍 |

`srt_cnt_ini` 的取值直接来自 RTL（`ct_vfdsu_ctrl.v:246`）：
`= ex1_double ? 5'b01101 : ex1_single ? 5'b00110 : 5'b00011`。
总延迟 = RF(1) + EX1(1) + EX2_SRT(N 拍) + EX3~EX4(2 拍) + WB。

**pipe6 独享 vfdsu**，pipe7 没有除法器——两条管线**不完全对称**：
fdiv/fsqrt 只能发往 VIQ0→pipe6，VIQ1→pipe7 不接除法。这是面积优化：
除法器一次只能用一个，共享 pipe6 不影响吞吐，但 fdiv 与 fadd 同拍必须错开
（由 VIQ0 仲裁保证）。

**MTVR（move-to-vector-register）**：IU pipe0/pipe1 执行的整数→浮点/向量搬运指令
（`iu_vfpu_ex1_pipe0_mtvr_vld/inst`）注入 VFPU ctrl 的 EX1 入口，旁路 VIQ0/VIQ1
调度直接改变 VFPU pipe6/pipe7 的 eu_sel，无需经 IDU 重调度。

### 6.4 完成 / 写回双轨制：CBUS 与 RBUS

IU 用两条独立总线汇报结果，这是 Smith&Sohi "结果总线 + 完成报告分离"的工业实现：

| | **RBUS（结果总线）** | **CBUS（完成总线）** |
|---|---|---|
| 传什么 | **数据**：64 位结果 + preg 号 | **状态**：cmplt + iid + 异常 |
| 去哪 | IDU 前递网络/PRF 写口、RTU 的 PST | RTU 的 ROB |
| 按什么组织 | 按 **preg**（谁要数据） | 按 **iid**（哪条按序完成） |

**推定完成（presumed complete）**：ALU/MULT/DIV 无异常、不会失败，所以在发射拍就被
CBUS 推定"将完成"，提前报 ROB，让它早进入可退休态；数据何时真写回由 PST 单独跟踪。
完成与写回彻底解耦。

> 细节见 `doc/iu/`（9 篇）。

## 6.5 指令执行延迟速查表

这是体系结构分析和代码优化最常用的参考。C910 的延迟定义：
**"发射拍到最早能被后继指令消费的拍数"**（含 forwarding 的有效延迟）。

### 整数执行延迟

| 操作 | 管线 | 延迟（拍） | 前递路径 | 备注 |
|------|------|------------|---------|------|
| add/sub/and/or/xor/sll/srl/sra 等 | pipe0/1 ALU | **1** | EX1 前递 | 短指令走 EX1 forward 网络 |
| max/min/addsl/ext/extu/ff1/rev 等 | pipe0/1 ALU | **2** | EX2 写回 | 长选择树晚一拍，无 EX1 forward |
| mul/mulh 系列 | pipe1 MULT | **4** | EX3 广播 preg（EX4 出数据） | EX3 提前一拍唤醒消费者 |
| mulh+mul（MLA 背靠背） | pipe1 MULT | **2**（成对） | EX3 私有前递 | MLA 专属前递链 |
| div（64÷64，典型） | pipe0 DIV | **~20** | — | SRT-16，变延迟；有 2 项结果缓存 |
| rem | pipe0 DIV | **~20** | — | 与 div 同时完成，配对免费 |
| 分支（BEQ/BNE/JAL/JALR 等） | pipe2 BJU | **EX1 预测、EX2 重定向** | — | 误预测总延迟 = 管线深度 |
| CSR read/write | pipe0 SPECIAL | 见注 | — | CSR 读写可能需要 flush 后端 |
| vsetvl | pipe0 SPECIAL | flush | — | 改向量配置需 flush + 重命名 ereg |

### 访存延迟

| 操作 | 延迟（拍） | 条件 |
|------|------------|------|
| load L1 命中 | **4**（AG→DC→DA→WB） | 正常 cache 命中，完整 4 级流水 |
| load L1 命中 + store 前递 | **4** | SQ 前递与 cache 命中同延迟 |
| load store 重发（discard） | **4 × 2 ≈ 8**+ | 部分覆盖/数据未就绪时重发 |
| load L1 miss，关键字优先 | **L1 miss + L2 hit ≈ 12~20** | 关键字先交付，load 不等整行 |
| store（退休后落 cache） | 退休后异步 | store 不在管线中写 cache，由 WMB 写 |

### 浮点/向量延迟

| 操作 | 延迟（拍） | 管线 | 备注 |
|------|------------|------|------|
| fadd/fsub | **3** | pipe6 或 7 vfalu | EX1→EX2→EX3 |
| fmul | **5** | pipe6 或 7 vfmau | EX1→EX5 |
| fmadd/fmsub/fnmadd/fnmsub | **5** | pipe6 或 7 vfmau | 单操作完成融合乘加 |
| fmin/fmax/fcmp/fclass | **3** | pipe6 或 7 fspu | 与 fadd 同流水 |
| float 类型转换（fcvt 系列） | **3** | pipe6 或 7 fcnvt | 同流水 |
| fdiv（f64 双精度） | **~18** | pipe6 vfdsu | SRT-16 × 14 轮 |
| fdiv（f32 单精度） | **~11** | pipe6 vfdsu | SRT-16 × 7 轮 |
| fdiv（f16 半精度） | **~8** | pipe6 vfdsu | SRT-16 × 4 轮 |
| fsqrt（f64） | **~30+** | pipe6 vfdsu | 需 2 轮 SRT |
| fsqrt（f32） | **~15** | pipe6 vfdsu | |
| 向量 F16 SIMD | **3 或 5** | pipe6+7 并行 | fadd=3，fmul=5 |

**延迟数字记忆口诀**：ALU-1，MUL-4，DIV-20，FADD-3，FMUL-5，FDIV-18。
加载命中-4；fadd 3 和 load 4 是"背靠背无气泡"的基准。

## 6.6 向量扩展（XuanTie 私有 vector，pre-RVV-1.0）

C910 的向量是**玄铁私有的早期向量扩展**（约 2019 年，早于 RISC-V Vector 1.0 定稿，
风格接近 vector-0.7.1），不是最终 RVV。它复用浮点的 VFPU 管线与寄存器，是"在浮点之上
长出向量"的工程路线。

### 6.6.1 向量寄存器与数据宽度

| 项目 | C910 | RTL 证据 |
|------|------|----------|
| **VLEN** | **128 bit** | `ct_vfpu_dp.v: parameter VLEN=128`；`cp0: vlenb=16 字节` |
| 架构向量寄存器 | 32 个（v0~v31） | RISC-V 向量 ABI |
| 元素宽度（SEW） | **8 / 16 / 32 / 64 bit** | vsew 编码，ELEN=64 |
| LMUL | ×1 / ×2 / ×4 / ×8 | vlmul 2 bit |
| 掩码寄存器 | v0（谓词） | split 逻辑 |
| vstart | 支持（6 bit，可从中途元素重启） | `cp0_idu_vstart` |

**向量与浮点共享物理寄存器堆**：物理寄存器堆由 `vregfile_fr` + `vregfile_vr0` +
`vregfile_vr1` 三个实例构成——**标量浮点 fN 就是向量寄存器 vN 的低 64 位（fr 部分）**，
向量的高位元素放 vr0/vr1。这正是 §5.1"浮点与向量共享空间, 64 项"的物理实现：FP 与
向量不抢两套寄存器，省了一大块面积（T-Head vector-0.7.1 的典型设计）。

### 6.6.2 配置重命名：vl / vtype 也要进重命名表

向量指令的行为取决于当前 `vl`（向量长度）和 `vtype`（SEW/LMUL）。**但乱序执行下，
一条向量指令必须知道"它发射时的 vl/vtype 是什么"**，而 vsetvl 可能还没退休。C910 的
解法：把 vl/vtype 配置当成一种"寄存器"，用 **ereg（扩展状态寄存器）重命名**——
物理 ereg **32 个**（`eregfile: ereg0~ereg31`）。每条 vsetvl 分配一个新 ereg，后续向量
指令引用对应 ereg，于是它们能在乱序窗口里各自携带正确的配置。**这是把"配置依赖"也纳入
重命名/唤醒体系的精彩一笔**——否则 vsetvl 后的向量指令只能串行等待。

**为什么 vl/vtype 不能当普通源操作数依赖处理？** 因为它是**隐式的、且影响每一条向量指令**
的全局配置——它不写在指令的源寄存器字段里，但每条向量指令都"暗中"读它。这类隐式全局状态
天生制造串行化：不处理的话，唯一办法就是"vsetvl 之后的所有向量指令串行等它退休"，乱序
窗口里一出现 vsetvl 就堵死。

**可迁移的通用方法——"把隐式全局状态显式化成一个可重命名的寄存器"**：一旦把 vl/vtype
变成 ereg，它就能套用现成的重命名 + 唤醒机制，像普通数据依赖一样在乱序窗口里流动，多组
不同配置可以同时在飞。**同一个套路能解一大类问题**：浮点的舍入模式 `frm`、向量的 vl/vtype
这些"隐式控制状态"，都可以用"配置寄存器重命名"来打破串行化。C910 用 32 个物理 ereg 实现，
存储代价极小，换来的是向量代码不被 vsetvl 串住——**用一点重命名资源，买乱序自由度**。

### 6.6.3 向量执行与访存

- **双发射向量**：VIQ0→pipe6、VIQ1→pipe7，每条 VFPU 管线 128-bit 数据通路，
  **两条独立向量指令可同拍并行**（一条不能同时占两管线）；依赖的 vmla 有跨管线前递
  （`ctrl_viq0_rf_pipe7_vmla_vreg_fwd_vld`）。
- **VMB（向量访存缓冲，8 项）**：向量 load/store 进入 `ct_lsu` 的 VMB，由它把一条向量
  访存**拆成多个标量/段访问**（按 vl、vsew、unit_stride 迭代）下发到访存管线——
  相当于向量访存的"微码引擎"。这是向量比标量访存复杂的根源。
- **mtvr**（整数→向量搬运，见 §6.3）旁路 VIQ 直接注入 VFPU EX1。

### 6.6.4 与 RVV 1.0 的关系

这是**早期私有向量**：有 LMUL、掩码 v0、vstart、widening/narrowing、规约等经典向量
特性，但**编码与最终 RVV 1.0 不兼容**。理解它的价值在于看 C910 如何用"浮点寄存器
别名 + ereg 配置重命名 + VMB 访存拆分"三件套，以最小增量把乱序浮点核扩成向量核。

## 7. 访存子系统 LSU

访存是高性能核最难的部分——它要同时做到：乱序执行 load/store、保证内存顺序语义、隐藏
cache miss 延迟。C910 LSU 用一组队列家族解决。

### 7.1 三条访存管线，4 级流水

| 级 | load (pipe3) | store-addr (pipe4) | store-data (pipe5) |
|----|--------------|--------------------|--------------------|
| AG | 算虚地址 VA + MMU 翻译得 PA + 生成 `bytes_vld` | 同左 | 接收 store 数据 |
| DC | 读 tag、查 SQ/WMB 依赖、创建 LQ 项 | 读 tag、创建 SQ 项、反查 LQ | 按 sdid 写进 SQ |
| DA | tag 比较定命中、数据多路选择、符号扩展、miss 申请 RB | 命中判定、更新 dirty | — |
| WB | 数据写回 PRF + 报 RTU 完成 | 仅报完成（store 不在此写存储器） | — |

**为什么 store 拆地址(pipe4)/数据(pipe5)两条管线？** 地址早算让后续 load 尽早做依赖
判断（地址未知的 store 会挡住所有更年轻 load）；数据晚到无害——store 反正要等退休才
真正写。地址/数据解耦是高性能核标配。

### 7.2 队列家族（每个数字都有讲究）

| 队列 | 项数 | 域 | 职责 |
|------|------|-----|------|
| **LQ** Load 队列 | 16 | 推测 | 记录在途 load，检测 RAW/RAR 顺序违例 |
| **SQ** Store 队列 | 12 | **推测域** | 已执行未提交的 store，向 load 前递数据 |
| **WMB** 写合并缓冲 | 8 | **已提交域** | 退休后的 store，合并相邻写后落 cache/总线 |
| **RB** miss 请求缓冲 | 8 | — | 登记 cache miss，发 BIU 请求；**决定 MLP≈8** |
| **LFB** 行填充缓冲 | addr 8 / data 2 | — | 接收 refill 数据写回 cache |
| **VB** 逐出缓冲 | 2 | — | 暂存被替换的脏行 |
| **PFU** 硬件预取 | PMB/SDB/PFB(8 流) | — | 检测访存流，提前取数 |
| **SNQ** 侦听队列 | 6 | — | 处理外核一致性侦听 |

### 7.3 三大正确性机制

**① store→load 前递（forwarding）**——三步协议：
```
ld_dc 广播 PA+bytes_vld+iid → SQ 12 项并行比：比我老？同 16B？字节相交？数据就绪？
三种结论：
  可前递（唯一最年轻的重叠老 store）→ ld_da 拍独热选数，与 cache 命中同延迟
  重叠但数据没到 / 部分覆盖    → discard：load 回 LSIQ 重发
  无关                          → 走 cache
```
其中 `bytes_vld[15:0]`（16 字节窗口字节位图）是 LSU 内一切依赖比较的"通用语言"——比
地址区间比较更精确且便宜。**部分覆盖为什么不拼接而是丢弃重发？** 拼接 mux 代价高、
验证难，用偶发重发换数据通路简单（实测 discard 仅个位数，编译器排序已让它罕见）。

**② 顺序违例检测**——load 乱序执行越过了更老的 store，读到旧值（RAW）。store 到达时
反查 LQ，发现"比我年轻 + 同 16B + 字节相交 + 已拿到数据"的 load → 违例 → 进 RTU 异常
擂台 → 该 load 退休时 flush 重执行。同时**训练 `spec_fail_predict` 预测器**：该 load
的 PC 下次保守执行（等所有老 store 地址已知）。一次 flush 几十拍，预测器把"反复跌倒"
压成一次——这是 Memory Dependence Prediction（H&P/Alpha 21264 的 store-set 思想）的实现。

**③ 推测域 / 提交域分离**——SQ 是推测域（flush 可清），WMB 是已提交域（flush 不可清，
体系结构已承诺必须写完）。这正是 RTU flush 状态机等待 `lsu_all_commit_data_vld` 的对象。
**这是精确异常在访存侧的体现：已提交的写不能回滚，未提交的写必须能撤销**。

### 7.4 非阻塞 cache 与延迟隐藏

```
load miss → RB(8项)登记 → BIU AXI 读：
  ├─ 关键字优先(critical word first)：首拍数据直接交付 ld_wb（load 延迟只到首字！）
  └─ 整行 → LFB → refill 写 cache → 被替换脏行 → VB → AXI 写回
```

- **MLP（内存级并行）≈ RB 8 项**：同时可有 8 个未完成 miss 在飞，后续无关访问继续跑
  （非阻塞 cache，H&P 第 2 章 "hit under miss / miss under miss"）。
- **关键字优先**：不等整行 64B 到齐，先把 load 要的那个字交付，大幅缩短 miss 延迟。
- **LFB addr 多(8)/data 少(2)**："账多本、钱少柜"——同时跟踪的 miss 多（便宜），同时
  正在收 64B 数据的少（贵的缓冲省着用）。
- **硬件预取 PFU**：PMB（按 PC 配对算 stride）→ SDB（确认流）→ PFB（8 条活跃流），
  L1/L2 双状态机分别领先 demand 近/远距离。机会主义低优先级，资源紧张直接丢。

> 细节见 `doc/lsu/`（11 篇）。

## 7.5 内存顺序模型（RVWMO）与 fence / AMO 的微架构实现

### 先理解"内存一致性模型"在说什么

这是体系结构最烧脑、也最容易被略过的概念，先把它讲透。单核看自己的内存访问，总是符合
程序序（有数据依赖就等）。**但多核下，一个核的 store，别的核"什么时候、以什么顺序"看到，
就成了大问题**。"内存一致性模型"就是**硬件给软件的一份契约：在没有显式同步时，跨核访存
最多能被重排到什么程度**。两条路线：
- **强一致（如 x86 TSO）**：对外几乎按程序序可见，软件省心，但硬件要时刻压制重排、损失性能；
- **弱一致（RVWMO / ARM）**：默认放开重排（store 可晚落、load 可早跑），**只在你用 fence
  或原子指令显式要求时才保证顺序**——把"要不要顺序"的决定权交给软件。

**为什么高性能核几乎都选弱序**：§7 讲的全部乱序访存（load 越过 store、store buffer 延迟
落盘、非阻塞 miss 乱序返回）本质都在**重排内存访问**。强序要时刻压制这些重排，等于自废武功；
弱序让硬件放手乱序、把"保证顺序"的责任甩给少数几条 fence——**性能默认优先，正确性按需购买**。
代价是程序员/编译器必须在该同步的地方正确插 fence（否则并发 bug），这也是 §7.3 顺序违例检测
与本节 fence 排空协议存在的根本原因：**前者保证"单核看着像顺序"，后者提供"跨核按需同步"**。

### RVWMO 基本约束

RISC-V 采用**RVWMO（RISC-V Weak Memory Ordering）**——宽松内存序，只保证：
同一线程内，有显式依赖（同地址 / fence 分隔）的操作才有序。其余乱序可见。

C910 对 RVWMO 的实现要点：

| 场景 | C910 保证 | 机制 |
|------|-----------|------|
| 同一 Hart 内的 RAW（同地址） | 有序 | LQ-RAW 违例检测 + 重发 |
| 同一 Hart 内的 WAW（同地址 store） | 有序 | SQ FIFO + WMB 顺序落盘 |
| 跨 Hart 的普通 load/store | **不保证**顺序 | 乱序执行；外核需 fence |
| fence rw,rw（全序屏障） | 屏障前所有访存对屏障后不可见 | ctrl 模块排空协议（见下） |
| fence.i（指令 cache 一致性） | 屏障后能看到屏障前所有 store 的最新指令 | 排空 + I-Cache 全无效 |
| sfence.vma | TLB 刷新 + dcache VIPT 别名清理 | mcic + MMU PTW 停止 |

### fence 指令的执行流程

**fence 是最"昂贵"的指令之一**，因为它等价于"把所有在途访存都排光"：

```
fence 进入 SDIQ（store-data IQ）→ 退休出 SQ → 进 WMB 标记 fence 标志
↓
LSU ctrl 模块广播查询，等待全部满足：
  ① SQ 空（所有年轻于 fence 的 store-addr 已退出 SQ 进 WMB）
  ② WMB 空（所有 store 数据已落 D-Cache 或发出 BIU AXI 写）
  ③ RB 空（没有在飞的 miss 请求）
  ④ LFB 空（没有待 refill 的行填充）
  ⑤ VB 空（没有待逐出的脏行）
↓
`lsu_has_fence` 拉高 → lsu_idu_wait_fence 通知 IDU → LSIQ 全卡死（不发射）
↓
全空后 ctrl 放行 → fence 在 RTU 退休 → 后续指令解锁
```

**fence.i 额外步骤**：还要通过 IFU 接口发送 I-Cache 全无效（flush）信号。
完成后，IFU 从正确 PC 重取指，保证取到 dcache 已提交的新指令内容。

**sfence.vma 额外步骤**：mcic 模块（MMU Cache Invalidate Channel）
对 D-Cache 做地址相关的清理（VIPT 索引可能有别名），同时 MMU 的
I/D-uTLB + JTLB 按范围刷新（rs1=0 全刷，rs1≠0 按地址，rs2 按 ASID）。

**代价**：fence stall 期间，`idu_hpcp_backend_stall` 计数器累计，
PMU 的 `Sync Stall` 事件即来源于此。fence 在访存密集 + miss 多的代码里代价极大。

### AMO 与 LR/SC 的本地监视器（Local Monitor）

C910 的原子指令通过 `ct_lsu_lm.v` 中的**状态机 lm_state** 实现：

```
IDLE                        // 空闲
 ↓ lr.d/lr.w               // load-reserved 发射，登记保留地址和大小
WAIT_REQ                    // 等待 cache 响应：行必须在 EX（独占）状态
 ↓ cache 返回 E 态行       // 命中可缓存行
EX_WAIT_LOCK                // 持有保留，等待 sc 或超时
 ↓ sc.d/sc.w 发射
  → 成功：rd=0, 写入新值，→ AMO_LOCK → WMB 提交后 IDLE
  → 失败（snoop 干扰 / 行被逐出 / flush）：rd=1，→ IDLE
```

**SC 失败的三种原因**（`lm_sq_sc_fail` 为真）：
1. `snq_req_dcache_same_addr_for_inv`：外核 snoop 使保留地址失效（同一地址被抢占）
2. `lm_already_evict`：保留行被本核替换策略驱逐（不大会但可能）
3. `rtu_yy_xx_flush`：全核 flush（异常/分支恢复）重置 lm

**amo（amoadd/amoswap 等）** 走 AMO_LOCK 路径：
lm 先发 `lr`（read exclusive），得到独占行后立即在管线内完成 modify，
再发 `sc`（write back exclusive），整个序列对外原子。

**SMP 下的注意**：LR/SC 是"弱原子"——RISC-V 保证在有限步内一个线程
必能成功（no starvation），但不保证 CAS 语义。锁实现必须容忍 SC 随机失败并重试。

## 8. 存储层次：Cache 与 MMU

存储层次的全部哲学是一句话：**用小而快的层吸收绝大多数访问，用大而慢的层兜底**
（H&P 第 2 章「存储层次」）。C910 是 L1（I/D 分离）→ L2（统一共享）→ 主存三级，
地址翻译则是 uTLB → JTLB → 硬件 PTW 三级——**TLB 体系本身就是"cache 思想在地址
翻译上的复刻"**。下面逐层把每个阵列的几何、替换、保护、以及"为什么这么取舍"讲透。

### 8.1 三级 Cache 总览

| 层级 | 容量 | 组织 | 行 | 索引 | 替换 | 保护 | 备注 |
|------|------|------|-----|------|------|------|------|
| L1 I-Cache | 64KB | 2 路 / 512 组 | 64B | **VIPT** | FIFO | 可选 ECC | Predecode 阵列、way-predict、per-bank 门控 |
| L1 D-Cache | 64KB | 2 路 / 512 组 | 64B | **PIPT** | FIFO | — | 双 tag 阵列、8 data bank、cache_buffer |
| L2 Cache | 1MB | 16 路 / 1024 组 | 64B | PIPT | FIFO | tag SECDED | 2 sub-bank 并行、可编程延迟、I/TLB 预取、≤4 核共享 |

**贯穿三级的一致取舍——替换一律用 FIFO，不用 LRU**：L1/L2 全部用 FIFO（每组一个
轮转指针），而非教科书首选的 LRU/PLRU。原因是 LRU 要为每路维护访问时间戳、每次命中
都要更新，面积与时序代价随路数上升；FIFO 每组只需 ⌈log₂(路数)⌉ bit、refill 时翻一下，
命中率仅小幅下降。这是 C910"在可接受命中率下极致省面积"工程哲学在 cache 上的体现
（H&P 第 2 章替换策略权衡；对比 Intel/Apple 大核普遍用 PLRU/树形伪 LRU）。

**I-Cache 用 VIPT、D-Cache 用 PIPT——两类访问不同权衡的经典对照**：
- 取指是顺序流、对延迟极敏感，VIPT 让 index 用虚地址、与 MMU 翻译**并行**省一周期；
  代价是可能别名，但取指只读、不写脏数据，别名风险可控。
- 访存有 store、会写脏，PIPT 用物理地址做 index+tag，**根除别名**（同一物理地址经不同
  虚地址映射也落同一行），正确性优先。

### 8.2 L1 I-Cache 内部（RTL: `ifu/rtl/ct_ifu_icache_*`）

**Tag 阵列（59 bit / 组，开 ECC 时 61 bit）**：一个表项同时存两路 + 替换位：
```
tag_entry[58:0] = { fifo(1) , way1: valid(1)+ptag(28) , way0: valid(1)+ptag(28) }
                    ▲替换指针   ▲————29 bit————▲       ▲————29 bit————▲
```
- **物理 tag 28 bit**（PA[38:11]）——VIPT 故 tag 用物理位。
- **fifo 1 bit/组**就是替换指针：refill 后翻转，指向下次要替换的路。
- 开 `L1_CACHE_ECC` 时每行加 2 bit ECC（SRAM 从 59→61 bit）。

**Predecode 阵列——为 RVC 变长边界预付出的代价**（详见 §4.3）：refill 时对每个
16-bit 槽预解码出 **4 bit**：`{绝对跳转(JAL/C.J)、是否分支、指令边界 bry1、bry0}`，
存进 cache。因为 RVC 让指令边界是动态的（16/32 位混排），不预解码就得在每个 IP 级
重算边界、还要跨拍。预解码把这件事一次性在 refill 时做完（组合逻辑现算现存），
**用 refill 时的一点功耗换取每拍取指的关键路径**（Shen & Lipasti「预解码」思想）。

**数据阵列 + per-bank 门控**：每路数据 = 4 个 32-bit bank，一路读出恰好 128 bit
（= 一个取指组）。每个 bank 有独立 `cen/clk_en`，配合 way-predict 只唤醒**目标那一路、
目标那几个 bank** 的 SRAM——这就是 §4.3 说的省功耗来源的 RTL 落点。

**way-predict 是 2-bit 即时信号、不是表**：`{way1_有效预测, way0_有效预测}`，
取指那拍现算（来自 L0-BTB/分支现场或行内顺序推断），不存独立 SRAM：
- `2'b10/2'b01`：只读预测命中的那一路 → 省一半 Data 阵列读功耗；
- `2'b00`：无法预测 → **way_pred_stall 停 1 拍**，下一拍两路全读。
误预测惩罚仅 1 拍，是"赌赢省功耗、赌输停一拍"的低风险下注。

**refill 路径**：从 L2 每拍 128 bit、**4 拍**填满一个 64B 行（WFD1~WFD4 状态），
最后一拍翻 fifo 位、置 valid。

### 8.3 L1 D-Cache 内部（RTL: `lsu/rtl/ct_lsu_dcache_*`）

**双 tag 阵列——load/store 同拍并行的物理基础**：
| 阵列 | 宽度 | 服务 |
|------|------|------|
| `ld_tag_array` | 54 bit / 组 | load 管线（pipe3）查命中 |
| `st_tag_array` | 52 bit / 组 | store 管线（pipe4）查命中 + 替换 |

两份 tag 是**同一份信息的物理副本**，让 load 与 store 同一拍各查各的、互不抢端口——
**用一份 tag 阵列的面积换访存双发射带宽**（对比单 tag 阵列必须分时复用、损失吞吐）。

**8 个 data bank（每 bank 2048×32 bit）**：64B 行横跨 8 bank，由 PA[5:3] 选 bank。
一次访问取 128 bit——低半（bank0~3）或高半（bank4~7）。多个访问命中不同 bank 可并行，
是 D-Cache 吞吐的来源。

**dirty 阵列（512×7 bit）独立于 tag**，每组 7 bit 一次给出两路的全部元数据 + 替换位：
```
dirty_entry[6:0] = { way_ptr(1) , way1{dirty,share,valid} , way0{dirty,share,valid} }
```
替换时读 `way_ptr` 定受害路、读对应 `dirty` 定要不要写回。把 dirty/valid/share 单独
成阵列（不挤进 tag）是为了**替换决策一次读全**、且 store 更新脏位不必动 tag SRAM。

**cache_buffer（1 行 128-bit 微缓冲）**：登记最近一次 miss 的数据与地址。当同一地址被
反复 hammer（紧循环里连续 miss 同一行）时，直接从 buffer 命中，**省掉重复的 L2 往返**。

**dcache 仲裁优先级**（`ct_lsu_dcache_arb.v`，从高到低）：
```
serial(续作) > LFB(refill) > VB(逐出) > SNQ(侦听) > ICC(维护) > WMB(写合并) > PTW > AG(普通load)
```
**正确性/一致性相关的请求一律压过普通 load**：refill、逐出、外核侦听必须及时，
普通 load 即使被插队、大不了多等几拍重发——这是"正确性 > 吞吐"在仲裁器上的硬编码。

### 8.4 L2 Cache 内部（RTL: `l2c/rtl/ct_l2c_*`）

**几何：1MB / 16 路 / 64B / 1024 组，物理上拆成 2 个 sub-bank**——每 bank 512 组、
独立流水（`x_ct_l2c_sub_bank_0/1`）。落到哪个 bank 由一位地址决定，两 bank 并行处理
不同地址的请求，**翻倍 L2 吞吐**。验证：16 路 × 1024 组 × 64B = 1MB；每 bank tag
index = 9 bit（512 组）。

**5 级流水**：`tag(读 tag SRAM) → cmp(比较定命中/选路) → data(读数据 SRAM) → wb(组织
响应/更新victim) → icc(维护类操作旁路)`。

**可编程访问延迟——一份 RTL 适配不同速度的 SRAM**：tag/data 阵列的访问拍数由 CIU 寄存器
`ciu_l2c_tag_setup + tag_latency[2:0]`、`data_setup + data_latency[2:0]` 配置（tag 最多
~5 拍、data 最多 ~9 拍）。这让同一套 L2 RTL 能配合不同工艺/频率下不同时序的 SRAM 编译宏，
是商用 IP 的典型可配置性。

**tag SECDED ECC，data ECC 本 build 关闭**（`ct_l2c_tag_ecc.v`，16 路并行纠错）：
tag/dirty 受单纠双检 ECC 保护——**tag 位翻转会导致误命中/误失效（错读到别的地址的数据），
是数据完整性灾难，必须保护**；data 阵列的 ECC 逻辑存在但在开源配置里关闭（面积/时序取舍）。

**FIFO 替换**：每组一个 16-bit 轮转指针 `l2c_way_fifo[15:0]`，allocate 时推进——与 L1
一致的省面积选择。

**状态位 status[7:0] = {cp[3:0], valid, shared, dirty, pend}**：这正是 §10.2 详述的
MOESI 编码所在；`cp[3:0]` 是最多 4 核的 presence 位图，让 L2 兼任侦听过滤器（snoop
filter），CIU 据此只侦听真正持有副本的核（详见 §10.3）。

**预取与写回**：L2 自带**指令预取（iprf）+ TLB 预取（tprf）**两类预取（`ct_l2c_prefetch.v`），
与 LSU 的数据预取（§7.4 PFU）分工互补。L2 的 wb（写回/响应）级用一个 **3 项 rfifo**
（每项 14 位 = resp+cp+sid，`ct_l2c_wb.v`）缓存"无数据的纯响应"（写完成/维护完成等），
与带数据的响应在输出端二选一——把"慢数据"和"快响应"解耦。

**共享范围**：cp 位图支持至多 4 核；开源默认 2 核/cluster 共享这一个 L2，L2 是两核
一致性的汇聚点（与 CIU 的关系见 §10.3）。

### 8.5 MMU 内部（Sv39，RTL: `mmu/rtl/ct_mmu_*`）

**虚拟内存仅单阶段 Sv39**（39 位虚地址、三级页表、4K/2M/1G 三种页）——无 H 扩展的
两阶段（G-stage）翻译。三级 TLB 把"翻译"也做成存储层次：

| 结构 | 规格 | 替换 | 表项内容 | 备注 |
|------|------|------|----------|------|
| **I-uTLB** | 32 项，全相联 | tree-PLRU | valid+VPN(27)+pgs(3)+PPN(28)+flag(14) | entry0 为 fast entry（快路径） |
| **D-uTLB** | 16 普通 + **1 huge** = 17，全相联 | tree-PLRU（仅 16 普通） | 同上 | huge 项专存 2M/1G 大页 |
| **JTLB** | **1024 = 256 组 × 4 路** | **FIFO** | valid+VPN(27)+**ASID(16)**+pgs(3)+global(1) / PPN(28)+flag(14) | SRAM 实现（tag 256×196、data 256×84） |
| **PTW** | 单发遍历 | — | — | 3 级 Sv39、~20 态 FSM、走 LSU 访存 |

**为什么 uTLB 用 tree-PLRU，JTLB 却用 FIFO？** uTLB 小（17/32 项）、全相联、命中在
关键路径上，PLRU 树状态只几 bit、能显著提升命中率，值得；JTLB 大、是 **SRAM**，若用
PLRU 要在 SRAM 里多存可观状态、每次命中回写，FIFO 每组只需 4 bit（存在 tag 阵列里，
`tc_jtlb_fifo[11:0]`）。**小表用 PLRU 拼命中率、大表用 FIFO 省存储**——同一颗核里按
代价/收益分别选替换策略，是很讲究的一笔。

**ASID 16 位只存在 JTLB，uTLB 不存 ASID——一个漂亮的上下文切换优化**：进程切换换
ASID 时，小小的 uTLB 直接整体作废（便宜），而**大的 JTLB 因为每项带 16 位 ASID 标签，
不同进程的翻译可以共存**、切回来无需重填（贵的东西保住）。再加 global 位标记内核公共
映射、跨 ASID 永远命中。这是"ASID 避免每次切换全清 TLB"经典思想（H&P 第 2 章）的精确
分层实现。

**D-uTLB 为何单列一个 huge 项？** 2M/1G 大页匹配只比对高位 VPN（位宽与 4K 不同）。
若让 16 个普通项每个都支持变宽比较，比较器成本翻倍；**专设一项处理大页**，既让 16 个
普通项保持简单 4K 比较，又保证大页一定有位置可放、不会被 4K 项挤占。

**PTW 走 LSU、无独立 PTE cache**：uTLB/JTLB 全 miss 时，PTW 状态机（~20 态：
FST→SCD→THD 三级 + PMP 检查 + 大页跨界处理）发起页表读，**请求经 `mmu_lsu_data_req`
走正常 LSU/cache 层次**（故页表本身也享受 D-Cache/L2 缓存），一次只跑一个遍历。
I 侧 / D 侧 / sfence 操作经 `ct_mmu_arb.v` 仲裁共享 JTLB 与 PTW。

**XMAE 内存属性（14-bit flag/项）**：除标准 V/R/W/X/U/A/D 权限位外，C910 在 flag 里
额外携带 **SO（strong-order 强序）、CA（cacheable）、BUF（bufferable）、SEC（安全）、
SH（shareable）** 等属性位——这就是 XMAE（XuanTie Memory Attribute Extension）对
RISC-V PMA 的私有增强：**把"这段内存能不能缓存/能不能合并写/是否强序"直接编进页表项**，
比纯靠物理地址区间判定更灵活。

**sysmap（硬连线 PMA 映射）**：`ct_mmu_sysmap.v` + `sysmap.h` 定义 8 个物理地址区间
及其默认属性（5-bit flag/区）。当 MMU 关闭（如机器态裸跑）或页表未覆盖时，由 sysmap
按物理地址兜底给出 cacheable/strong-order 等属性——相当于一张内建的、地址区间式的 PMA 表。

### 8.6 存储层次设计权衡小结

| 设计点 | C910 选择 | 取舍 / 动机 | 教科书坐标 |
|--------|-----------|-------------|-----------|
| 三级 cache 替换 | 一律 FIFO | 命中率小降，换面积/时序 | H&P 2 章替换策略 |
| I/D 索引 | VIPT / PIPT 分用 | 取指省周期 / 访存避别名 | H&P 2 章 cache 别名 |
| I-Cache 预解码 | refill 时预解码 4bit/槽 | 解决 RVC 变长边界、卸下取指关键路径 | Shen&Lipasti 预解码 |
| I-Cache way-predict | 2-bit 即时预测 + 1 拍惩罚 | 省一半 Data 读功耗，低风险 | H&P way prediction |
| D-Cache tag | 双副本 tag 阵列 | 面积换 load/store 同拍并行 | 端口 vs 副本权衡 |
| L2 结构 | 2 sub-bank × 512 组 | 双 bank 并行翻吞吐 | 多 bank 交织 |
| L2 延迟 | 可编程 tag/data 拍数 | 一份 RTL 适配多种 SRAM | 商用 IP 可配置 |
| L2 保护 | tag SECDED，data 关 | tag 错=数据完整性灾难，优先保 | H&P 可靠性 / SECDED |

| PTW | 走 LSU、无 PTE cache | 页表也享 cache、省一套结构 | 硬件页表遍历 |
| 内存属性 | XMAE 编进页表项 | 比纯物理区间判定灵活 | RISC-V PMA 增强 |

## 9. 退休与精确异常 RTU

乱序核把指令打乱执行，但体系结构状态必须表现得像顺序执行——这是 RTU 的使命，也是
精确异常（precise exception）的实现（Smith&Sohi 的经典议题）。

### 9.1 IID：贯穿全核的指令身份证

**7 位 IID = 1 位 wrap + 6 位 ROB 索引**。低 6 位是 ROB 表项号（64 项）；最高位是
"圈数奇偶"标志。**年龄比较**靠 wrap 位：相同比大小、不同则反过来——环形空间中只要
在途指令 < 64，任意两个 IID 可以**就地**比出老幼，无需知道 ROB 头尾指针。这让远离 ROB
的 BJU、LSU、发射队列都能本地判断年龄。

### 9.2 ROB：64 项瘦表项（"只管序，不管值"）

C910 的 ROB 是**面积优化的范本**：64 项 × 仅 40 位。教科书 ROB 该存的三样东西全被外包：

| 教科书 ROB 存 | C910 放哪 |
|---------------|-----------|
| 完整 PC | 不存，只存 3 位 pc_offset，退休时增量重建；跳转目标在 IU 的 PCFIFO |
| 结果数据 | PRF（物理寄存器堆，写回即入） |
| 异常向量 / mtval | 单独 1 项异常缓冲 |

**ROB 只管"序"，不管"值"——这是 RTU 全部设计的纲。**

- **退休 PC 增量重建**：维护一个退休游标 `rob_cur_pc`，非跳转项退休 `cur_pc += pc_offset`，
  跳转项 `cur_pc = PCFIFO 弹出的目标`。**一个加法器替代了 64×39 位 PC 存储**——这就是
  ROB 敢不存 PC 的底气。
- **指令折叠**：一项最多装 3 条相邻简单指令，`cmplt_cnt[1:0]` 跟踪剩余完成数。退休口
  3 项/拍 × 3 条/项 = 峰值 9 条/拍。
- **完成端口零译码**：7 条管线的 iid 低 6 位各自 expand 成 64 位独热位图，第 N 位直连
  entryN——"端口"就是 7 个位图按位或，没有译码器。

### 9.3 异常单项擂台 + flush 状态机

**精确异常只需要"最老的未退休异常"**，所以异常现场（70 位）只存**一项**。4 条能报
异常的管线（IU pipe0、BJU、LSU pipe3/4）每次异常完成都来"挑战擂主"：10 个 compare_iid
两两比较，比现任老才换人。误预测、LSU 顺序违例、vsetvl flush **复用同一套擂台**——
都需要"最老者退休时触发恢复"的语义。

**flush 状态机**是全核恢复的总指挥：
```
触发A 异常/中断/CSR副作用 → FLUSH_FE（前端要转向 trap 入口）
触发B 误预测分支退休       → FLUSH_IS（IFU 已被 BJU 重定向过，只清 IS/RF，更轻）

IDLE → FLUSH_FE/IS → [WF_EMPTY 等待] → FLUSH_BE → IDLE
```
**FLUSH_BE 必须等 pipeline empty**（`pst_retired_reg_wb && lsu_all_commit_data_vld`）：
已退休指令的写回（慢除法、store 提交）还在途中时不能回滚——"该留的先落定，再清该清的"。
FLUSH_BE 这一拍发出全核最重要的单 bit **`rtu_yy_xx_flush`**：重命名表恢复、PST/发射
队列/执行单元的推测态全部蒸发。

### 9.4 PST：物理寄存器生命周期与回收

PST（Physical register Status Table）管理 preg 的分配与回收，每项一个 5 态状态机：
```
DEALLOC(空闲) → WF_ALLOC(预取) → ALLOC(已派给指令,推测) → RETIRE(生产者已退休,是某逻辑寄存器正身)
            → RELEASE(下任写者退休,等写回确认) → DEALLOC
```
三条铁律：
1. **flush 时 ALLOC/WF_ALLOC 回 DEALLOC，RETIRE 纹丝不动**——重命名表恢复不需要 walk
   ROB 或 checkpoint：每个 RETIRE 态项输出"我是逻辑寄存器 X"的位图，flush 拍 RAT 整表
   重写即可。**这是 C910 重命名恢复的精髓**（对比 Alpha 21264 的 checkpoint 方案，
   C910 用状态表直接重建更省存储）。
2. **旧 preg 在"下一任写者退休"时才释放**——每项记着前任 preg（rel_preg），保证旧值
   一直可读到新映射安全提交。
3. **没写回不回收**——否则新主人可能读到撕裂值。

**重命名恢复的三条路线（理解 C910 RTU 的关键，也是乱序核的经典考点）**：误预测/异常后，
架构 RAT（逻辑→物理映射）被推测指令污染了，必须恢复到"最后一条已退休指令"的映射。业界三招：

| 方法 | 怎么做 | 代价 |
|------|--------|------|
| **Checkpoint 快照**（Alpha 21264） | 每条分支处存一份完整 RAT 快照，恢复即回滚 | 快，但每个快照要一整份 RAT 存储，数量有限——分支密集时快照不够用 |
| **ROB-walk 倒带** | 从 ROB 尾逐条撤销重命名直到出错点 | 省存储，但**慢**（要走很多拍） |
| **C910 位图重建** | 不存快照、不倒带 | 单拍恢复 + 几乎零额外存储 |

**C910 这招的关键洞察**：架构 RAT 本质上**就等于"当前所有已退休映射的集合"**，而 PST 的
**RETIRE 态恰好就在记录这件事**——每个 RETIRE 态项常驻输出一个位图"我是逻辑寄存器 X 的当前
正身"。flush 那一拍，把所有 RETIRE 项的位图一汇聚，就**一次性重写出整张架构 RAT**，无需快照、
无需倒带。**精髓在于：它没有为"恢复"单独花存储，而是复用了"寄存器生命周期管理"本来就维护
的状态**——一份数据干两件事。这正是 C910"在正确前提下极致省面积"工程哲学最漂亮的一例，
也呼应 §9.2 ROB"只管序不管值"的瘦身思路：**让已有结构兼职，胜过新增专用结构**。

> 细节见 `doc/rtu/`（8 篇）。

## 9.5 流水线 Stall 条件系统化

这是 IPC 分析和瓶颈定位的核心知识。C910 的 stall 分布在两个顺序段（前端/后端
顺序转换点），乱序段本身不 stall（发射队列里等着就行）。

### 前端 stall（ID 级停流 → IFU 停取）

| Stall 原因 | 信号 | RTL 位置 | 常见触发场景 |
|-----------|------|---------|------------|
| **IR 级误预测等待** | `iu_idu_mispred_stall` | ct_idu_ir_ctrl.v | BJU EX1 发现误预测，ID/IR 等新指令到来 |
| **RTU flush 等待** | `rtu_idu_flush_stall` | ct_idu_ir_ctrl.v | 精确异常/分支退休 flush 期间，IR 禁止放行 |
| **整数 preg 耗尽** | `ctrl_ir_preg_stall` | ct_idu_ir_ctrl.v:1024 | 64 个重命名 preg 全被占用（窗口满 64 条整数指令） |
| **浮点 freg 耗尽** | `ctrl_ir_freg_stall` | ct_idu_ir_ctrl.v:1036 | 浮点 PRF 32 个重命名位置用完 |
| **向量 vreg 耗尽** | `ctrl_ir_vreg_stall` | ct_idu_ir_ctrl.v:1030 | 向量 PRF 用完 |
| **ereg 耗尽** | `ctrl_ir_ereg_stall` | ct_idu_ir_ctrl.v:1042 | vsetvl 配置重命名耗尽 |
| **fence 屏障** | `fence_ctrl_id_stall` | ct_idu_id_ctrl.v | fence 到达 ID 级，等 LSU 排空 |
| **复杂指令拆分** | `ctrl_split_long_id_stall` | ct_idu_id_ctrl.v | 复杂指令（如向量）拆多微操，下一拍 ID 继续完成拆分 |

**关键规律**：`ctrl_ir_stage_stall = preg_stall | vreg_stall | freg_stall | ereg_stall | flush_stall | mispred_stall`。
IR 级是"乱序窗口的门"——任何物理寄存器分配失败都在这里阻塞，而**不会等到发射**。

### 后端 dispatch stall（IS 级停派遣）

| Stall 原因 | 信号 | 触发条件 |
|-----------|------|---------|
| **ROB 满** | `ctrl_is_rob_full` | ROB 64 项全部被占用（64 条指令在途） |
| **任一发射队列满** | `ctrl_is_iq_full` | AIQ0/AIQ1/BIQ/LSIQ/SDIQ/VIQ0/VIQ1 任意一个满 8 项且有新指令派遣该队列 |
| **VMB 满** | `ctrl_is_vmb_full` | 向量内存缓冲满（向量 load/store 特有） |

等式：`ctrl_is_dis_stall = ctrl_is_rob_full | ctrl_is_iq_full | ctrl_is_vmb_full`

**分布式发射队列的 stall 特性**：如果只有 FDIV 在飞（pipe0 ALU 同时闲着），
AIQ0 可能满（8 条 DIV 排队），但 AIQ1 空着——这时派遣 add 指令到 AIQ1 没问题，
**派遣 div 就卡**。这是分布式队列"独立满"的典型表现。

### 访存相关 stall

| Stall 来源 | 信号 | 触发 |
|-----------|------|------|
| **LQ 满** | `lsu_idu_lq_full` | Load 队列 16 项全满，新 load 无法进入 LSIQ |
| **SQ 满** | `lsu_idu_sq_full` | Store 队列 12 项满，新 store-addr 无法派遣 |
| **RB 满** | `lsu_idu_rb_full` | miss 请求缓冲 8 项满，新 miss 无法登记 |
| **TLB busy** | `lsu_idu_tlb_busy` | TLB miss 期间 PTW 占用管线，LSIQ 发射项卡在 DC 级 |
| **fence 排空等待** | `lsu_idu_wait_fence` | 屏障指令等 SQ/WMB/RB/LFB/VB 全空 |
| **顺序违例重发** | `lsu_idu_secd` | load 重发（spec fail / discard），占用 LSIQ 槽 |

### stall 瓶颈定位方法（PMU 事件）

```
高 preg_stall   → 整数窗口满：乱序窗口被长延迟指令（FDIV/cache miss load）塞满
高 rob_full     → ROB 满：同上，或者退休端 flush 太频（误预测/异常）
高 iq_full (AIQ0)  → FDIV/MULT 堆积；考虑 software pipeline 展开
高 iq_full (LSIQ)  → 访存密集 + miss 多（load 慢返回）
高 fence_stall  → fence 太频；考虑减少 acquire/release 语义的 fence
高 Spec Fail    → 顺序违例频繁；考虑 store 优先、数据相关分析
```

## 10. 多核与缓存一致性

### 10.1 系统拓扑

| 项目 | C910 |
|------|------|
| 多核 | 每 cluster **2 核**，同构 SMP |
| 一致性协议 | **MOESI** —— M/O/E/S/I 五态 |
| 一致性互联 | **CIU**（Coherence Interconnect Unit），集中式侦听 + 侦听过滤器（snoop filter） |
| 核间传输 | **cache-to-cache transfer（CTC）**：被侦听核直接把脏行交给请求核，绕过主存 |
| 内存总线 | AXI4-128，CIU 到 DDR 控制器 |
| 原子指令 | LR/SC + AMO，由 LSU lm 模块保证（见 §7.5） |

### 10.2 MOESI 协议五态与 RTL 编码

L2 Cache 每个 cache line 的状态由 **status[7:0]** 字段的 4 位描述（来自 `ct_l2c_cmp.v`）：

```
status_set_din[7:0] = { cp[3:0],  valid,  shared,  dirty,  pend }
                        ████████   █       █        █       █
                        4位cp位图  有效    共享      脏      待定
```

| state | valid | dirty | shared | 含义 | cp[3:0] |
|-------|-------|-------|--------|------|---------|
| **I**（Invalid） | 0 | × | × | 无效，不存在副本 | 0000 |
| **S**（Shared） | 1 | 0 | 1 | 多核共享干净副本 | 多位置 1 |
| **E**（Exclusive） | 1 | 0 | 0 | 唯一干净副本 | 单位置 1 |
| **M**（Modified） | 1 | 1 | 0 | 唯一脏副本 | 单位置 1 |
| **O**（Owned） | 1 | 1 | 1 | 某核持有脏副本，**其他核可读旧值** | 多位置 1 |

**O 态的意义**：这是 MOESI 比 MESI 的关键扩展。当 core0 有 M 态行，core1 发起读请求时：
- MESI：core0 先写回内存（dirty→clean→S），浪费内存带宽
- MOESI：core0 直接把脏行发给 core1（CTC），core0 降为 O，core1 升 S，**内存不更新**
  数据只存在于两个核的 cache + CIU，等真正被替换才写内存

`cp[3:0]` 是 **presence/copy-set bitmap**，每 bit 对应一个 PIU 接口（最多 4 核）。
CIU 的 snoop filter 靠这 4 个 bit 决定"要不要侦听哪些核"，避免广播所有核。

### 10.3 CIU 架构与 SNB 侦听总线

CIU 内部关键子模块：

```
         核0 PIU ──┐
         核1 PIU ──┤        ┌── L2 Cache bank 0/1
                   SNB ─────┤
         外部 EBIU ─┤        └── 外存 AXI4
         （共 4 个 PIU 接口 + 1 个外部接口）
         snoop filter (SAB): 每项追踪 1 个地址的状态 + cp 位图
         CTCQ: cache-to-cache 数据传输队列
         VB:   CIU 侧逐出缓冲
         NCQ:  non-cacheable 请求队列
```

**SNB（Snoop Broadcast）的完整流程**（以 core0 M 态，core1 读请求为例）：

```
① core1 发 AXI AR 请求（ARSNOOP=ReadShared/ReadUnique）到 CIU
② CIU 查 snoop filter → cp[0]=1（core0 有副本）→ 只侦听 core0
   （如 sf_dis=1 则降级为广播所有核）
③ SNB 向 core0 发 AC（snoop address）请求
④ core0 LSU 的 SNQ（6 项）接收 → 借 load 管线读 D-Cache tag
   → 命中（M/E 态）→ 读数据
⑤ core0 发 CD（cache data，64 字节）直接到 CTCQ，
   同时发 CR（cache response，CRRESP 表示已处理）
⑥ CIU 把数据从 CTCQ 直接转发给 core1（cache-to-cache transfer），
   不经过 DDR
⑦ core0 cache 行状态：M/E → S（如果 O 态，则变成 S）
   core1 cache 行状态：I → S（或 E，视 ARSNOOP）
   L2 status[shared]=1, dirty=1 → O 态（若 core0 原来是 M）
```

**SNQ 与本核在飞操作的互锁**：
- SNQ 到来时，若 LFB 正在 refill 同一地址 → 等 refill 完再侦听
- WMB 有同地址写在飞 → 先让 WMB 写完（内存可见），再侦听
- LQ 中已完成的 load 若与侦听地址重叠 → **触发 RAR 违例**（LQ 检测），
  该 load 之后的依赖指令需重执行（这是多核下 RAR 违例的根本来源）

### 10.4 一致性请求类型（ARSNOOP/AWSNOOP 编码）

CIU 通过 AXI ACE（AXI Coherency Extensions）总线与核通信：

| 请求类型 | ARSNOOP | 含义 | 典型触发 |
|---------|---------|------|---------|
| ReadShared | `0001` | 读，允许共享副本 | 普通 load miss |
| ReadUnique | `0111` | 读并独占，其他核无效化 | 写前需读的 store miss |
| CleanUnique | `1011` | 独占但不取数据（已有副本） | AMO 取独占权 |
| MakeUnique | `1100` | 仅驱逐其他核副本 | 整行 store（写分配优化） |
| WriteBack | （AW） | 脏行写回 | M→I 替换 |
| Evict | （AW） | 干净行失效通知 | E/S→I 替换，维护 snoop filter 准确 |

**Evict（驱逐通知）是 snoop filter 准确性的代价**：即使替换干净行（S/E→I），
也必须发 Evict 通知 CIU 更新 cp 位图。否则 snoop filter 以为该核还有副本，
会发出不必要的侦听（伪侦听，浪费 SNQ 和管线资源）。

### 10.5 多核常见性能陷阱

| 现象 | 根本原因 | 微架构对应 |
|------|---------|-----------|
| 锁竞争下 load 命中率下降 | 持锁核反复 M→S，锁变量在核间乒乓（false sharing） | L1 D-Cache miss 率飙升，CTC 频繁 |
| AMO/LR-SC 严重变慢 | 多核竞争同地址，lm_state 反复 WAIT_REQ→IDLE（sc 失败重试） | 见 PMU lm_fail 事件 |
| fence 串行化 | 高频 fence 排空所有队列，stop-the-world | Sync Stall 计数爆高 |
| RAR 违例突然增多 | 多线程访问同一 cache 行，snoop 导致 LQ-RAR | LSU Spec Fail 计数异常 |

### 10.6 BIU：每核 AXI/ACE 主端口（RTL: `biu/rtl/ct_biu_*`）

前面反复出现"发 BIU 请求""BIU AXI 读"，这里交代 BIU 到底是什么。**完整的访存外出路径**是：
```
核内 (IFU refill / LSU RB / PTW)  →  BIU (每核 ACE 主端口)  →  CIU (一致性互联+侦听过滤)
                                      →  共享 L2  →  外部 AXI4  →  DDR
```
**BIU 是每个核唯一的对外端口，CIU 是把多个核的 BIU 汇到一起做一致性的互联**——分工清晰：
BIU 管"本核怎么上总线"，CIU 管"多核之间怎么保持一致"（§10.3）。

**协议与位宽**：ACE（AXI Coherency Extensions），数据 **128 bit**、地址 40 bit、
AXI ID **5 bit**。通道齐全：读 AR/R、写 AW/W/B、**侦听 AC/CR/CD**（ACE 一致性三通道）。

| 子模块 | 职责 | 关键数字 |
|--------|------|----------|
| **read_channel** | 读请求上 AR、读数据经 R 返回 IFU/LSU | AR 输出双缓冲；outstanding 按 AXI ID 跟踪（IFU 用 0x10/0x11，LSU 用 0x00~0x0F 共 16 个），实际在飞 miss 数由 RB 8 项上限决定（§7.4 MLP≈8） |
| **write_channel** | store 写与脏行逐出 | **写数据 FIFO 12 项**；store(ST) 与 victim(VICT) 两条独立 AW 路径，**优先级 VICT > ST**（逐出要及时让位给一致性） |
| **snoop_channel** | 外部侦听 AC 进、CR/CD 出 | AC/CR/CD 各双缓冲；转发给 LSU 的 SNQ（§10.3） |
| **req_arbiter** | 读总线仲裁 | **优先级 LSU > IFU**（数据 miss 比取指更急） |
| **csr_req_arbiter** | 非缓存/设备(IO)访问路由 | NC/强序请求单独走；**CP0 > HPCP** 优先 |
| **lowpower** | 配合 WFI | 每通道独立时钟门控；读写都空闲时拉 `biu_yy_xx_no_op`，配合 `cp0_biu_lpmd_b` 静默总线 |
| **other_io_sync** | 跨时钟域同步 | 把系统侧的 6 类中断（me/mt/ms/se/st/ss）+ 调试请求两级触发器同步到核时钟 |

**两个值得记的点**：①**store 与 victim 分两条写路径且 victim 优先**——脏行逐出关系到
别核能否拿到最新数据，不能被普通 store 堵住；②**outstanding 读不是靠缓冲项数、而是靠
AXI ID 区分**——返回数据按 rid 路由回 IFU 或 LSU 的对应 miss 项，真正的并发上限由上游
RB（8 项）决定，与 §7.4 的 MLP≈8 自洽。

**两个值得带走的通用思想**：
- **AXI ID = 乱序事务的"名牌"**。总线允许多笔读/写同时在飞、且**乱序返回**，怎么知道
  回来的数据是谁的？给每笔请求贴一个 ID，返回时认牌对号入座。这与 ROB 用 IID 管乱序指令
  （§9.1）、cache 用 MSHR/RB 管乱序 miss 是**同一个方法**——*用一个小标签把"并发 + 乱序"
  管起来*。BIU 把 IFU/LSU 的 miss 项编成 AXI ID，数据回来按 `rid` 找回主人。
- **ACE 让 BIU 一个端口演两个角色**：对本核自己的访存，BIU 是**主**（主动发 AR/AW 取数）；
  对别核发来的侦听，BIU 又是**从**（被动收 AC、回 CR/CD 交数）。"既要主动取、又要被动交"
  正是缓存一致性的本质——你的 cache 既服务自己，也要应别人之需（呼应 §10.3 的 SNB 侦听）。

## 11. 中断与异常处理（trap / CLINT / PLIC）

§9 讲了 RTU 如何在退休级**挑出最老的异常并 flush**；本节接着讲**陷入之后发生了什么**
——控制状态寄存器（CSR）怎么被原子更新、执行流怎么跳到处理程序。这是精确异常对软件
可见的那一面（H&P 附录「异常与中断」）。

### 11.1 统一陷入入口（trap entry，RTL: `cp0/rtl/ct_cp0_regs.v`）

**特权级**：M / S / U 三级，当前级由 `pm[1:0]` 跟踪（`2'b11`=M、`2'b01`=S、`2'b00`=U），
复位进 M 态。完整 trap CSR 一应俱全：

| 组 | CSR | 作用 |
|----|-----|------|
| 状态 | `mstatus`/`sstatus` | MIE/MPIE/MPP/SPP 等中断使能与特权栈 |
| 向量 | `mtvec`/`stvec` | trap 入口基址 + 模式（Direct / Vectored） |
| 返回 PC | `mepc`/`sepc` | 出错/返回指令地址 |
| 原因 | `mcause`/`scause` | bit63=中断标志，低位=原因码 |
| 出错值 | `mtval`/`stval` | 出错地址或指令编码 |
| 使能/挂起 | `mie`/`mip`、`sie`/`sip` | 各类中断使能与挂起位 |
| 委派 | `medeleg`/`mideleg` | 把异常/中断下放给 S 态处理 |
| 翻译 | `satp` | Sv39 页表基址 + ASID |
| **玄铁私有** | `mxstatus`/`mhcr`/`mcor`/`mhint`/`mrvbr`/`mcer` | 扩展状态、cache/预取硬件控制、复位向量基址、cache 错误记录 |

**陷入时一拍内原子完成的动作**（RTU 给出 `rtu_cp0_expt_vld` + epc + vec + mtval 那拍）：
```
若不委派（去 M 态）:  mepc←出错PC ; mcause←{int,code} ; mtval←出错值
                      mstatus: MPP←pm ; MPIE←MIE ; MIE←0   （特权与中断使能压栈）
                      pm←M
若委派（去 S 态）:    sepc/scause/stval 同理 ; SPP←pm[0] ; SPIE←SIE ; SIE←0 ; pm←S
```
**`mret`/`sret` 出栈**：恢复 `MIE←MPIE`、`pm←MPP`，并把 MPP 置 U（防嵌套提权），PC 回 mepc。
这正是教科书的「中断使能/特权两级栈」——一进一出严格对称。

**trap 入口 PC 怎么算**（mtvec 两模式）：
- **Direct（mode=0）**：所有 trap → `base`；
- **Vectored（mode=1）**：中断 → `base + 4×cause`（按号散开，省去软件分派），异常仍 → `base`。

**委派（delegation）**：在 S/U 态发生、且 `medeleg/mideleg` 对应位置 1 时，trap 直接交
S 态，**不绕一圈 M 态**——这是跑 Linux 时绝大多数缺页/系统调用的快路径。

**异常原因码**（RISC-V 标准，`mcause` 低位）：
| code | 异常 | code | 异常 |
|------|------|------|------|
| 1 | 取指访问错 | 8/9/11 | U/S/M 态 ecall |
| 2 | 非法指令 | 12 | 取指缺页 |
| 3 | 断点 | 13 | load 缺页 |
| 4/6 | load/store 地址未对齐 | 15 | store 缺页 |
| 5/7 | load/store 访问错 | — | — |

**中断原因码**（`mcause` 最高位=1 时）与对应挂起/使能位（mip/mie）：

| code | 中断 | 挂起/使能位 | 来源 |
|------|------|-------------|------|
| 1 / 3 | S / M 软件中断 | (s/m)sip · (s/m)sie | CLINT `msip`（§11.2，核间 IPI） |
| 5 / 7 | S / M 定时中断 | (s/m)tip · (s/m)tie | CLINT `mtimecmp`/`stimecmp`（§11.2） |
| 9 / 11 | S / M 外部中断 | (s/m)eip · (s/m)eie | PLIC（§11.3） |
| 玄铁扩展 | **计数器溢出中断** | `moie` | PMU/HPCP 计数器溢出（§13.2，性能采样） |

C910 实现这三类标准中断 + 玄铁的 **moie 计数器溢出中断**。中断须同时满足"mip 挂起 +
mie 使能 + 当前特权级允许"，才在退休边界被接受。

**两条铁律**：①**中断只在退休 inst0 边界被接受**（保证精确）；②**同一指令上中断优先于异常**
（`expt_vec[5]` 中断标志置位即走中断向量）。**无 NMI、无 CLIC**——采用经典 CLINT+PLIC 模型。

### 11.2 CLINT：核内本地中断（RTL: `clint/rtl/ct_clint_func.v`）

**先理解"为什么中断要分两套系统"**——这是中断体系最重要的思想。中断按"是否需要全局仲裁"
天然分两类：**本地中断**（定时器、核间软件中断）每核私有、延迟敏感、不需要在多个核/多个源
之间排队，交给紧贴核的 **CLINT**；**平台中断**（外设：网卡、串口、DMA…）全局共享、数量多、
要按优先级仲裁分发，交给 **PLIC**（§11.3）。**把"私有快路径"和"共享需仲裁"分开做**，是
中断系统的经典二分，也是 RISC-V CLINT/PLIC 划分的根本动机。

CLINT 管两类本地中断，服务 **2 个 hart**：

**① 定时器中断——"比较寄存器式定时器"的通用方法**：有一个 64 位全局自增计数器 `mtime`
（所有核看同一时间基准），外加每 hart 一个 `mtimecmp`。软件往 `mtimecmp` 写一个"未来的
时间值"，当 `mtime ≥ mtimecmp` 时硬件拉高 `mtip`。**要下一次中断，就把 mtimecmp 再加一个
周期**——OS 的时间片调度、超时、jiffies 全靠它。C910 还额外提供 S 态的 `stimecmp`：传统上
S 态（OS）想要定时中断，得陷入 M 态求固件（SBI）代写 mtimecmp，每次都有特权切换开销；
直接给 S 态自己的比较器后，**OS 不绕 M 态自管定时**（即 Sstc 思想）——这是"把高频快路径
下放到低特权级"的典型优化。

**② 软件中断（IPI）——多核协作的基础原语**：每 hart 一个 `msip` 位，**一个核写另一个核的
msip，就能"戳"对方产生一次中断**。这就是 IPI（核间中断），是 SMP 一切跨核协作的底层信号：
启动时 boot hart 用它唤醒自旋等待的 secondary hart（§11.5）；运行时用于 **TLB shootdown**
（改了页表通知别核刷 TLB）、调度迁移、panic 广播。**"写一个内存映射位 → 对方收到中断"**
是用最小硬件实现核间通信的经典手法。

### 11.3 PLIC：平台级中断（RTL: `plic/rtl/plic_*`）

PLIC 仲裁**外部设备中断**。C910 配置 **144 个外部中断源**（IP 可参数化至 1024，
此处 `PLIC_INT_NUM=144`，另含 16 个保留），按**每 hart × {M, S} 双 context**分发：

| 维度 | 规格 |
|------|------|
| 中断源 | 144（+16 保留）；IP 上限 1024 |
| 优先级 | 每源 **5 bit = 32 级**（0=关闭） |
| context | 每 hart 的 M / S 两套（IP 支持 4 hart） |
| 阈值 | 每 context 一个 priority threshold，优先级须**严格大于**阈值才上报 |
| 认领/完成 | claim（读出最高优先 ID）→ 处理 → complete（写回 ID 清挂起） |
| 仲裁结构 | **层次化 32-to-1 仲裁树**：1024 源分 32 轮、每轮 4→1 再 8→1，选最高优先 |
| 总线 | APB（`csky_apb_1tox_matrix`） |

**claim/complete 握手是 PLIC 的精髓**：硬件做完优先级仲裁，软件用一次读（claim）拿到
当前最高优先中断号、一次写（complete）声明处理完毕——**把"谁最该被处理"的复杂仲裁
留给硬件、把控制权交给软件**，是中断控制器的经典分工（对比 ARM GIC 的 IAR/EOIR）。

### 11.4 中断/异常设计取舍小结

| 设计点 | C910 选择 | 动机 | 教科书坐标 |
|--------|-----------|------|-----------|
| 中断模型 | 经典 CLINT+PLIC，无 CLIC/NMI | 跑 Linux 够用、逻辑简单 | RISC-V 特权规范 |
| trap 入口 | Direct/Vectored 两模式 | 向量模式省软件分派 | 异常向量化 |
| 委派 | medeleg/mideleg 直达 S 态 | 缺页/syscall 不绕 M 态 | 虚拟化/OS 快路径 |
| 中断时机 | 仅退休 inst0 边界 | 保证精确异常 | Smith&Sohi 精确中断 |
| S 态定时器 | CLINT 直供 stimecmp | 免 M 态转发定时中断 | Sstc 思想 |
| PLIC 仲裁 | 硬件层次树 + 软件 claim/complete | 硬件挑最优、软件掌控 | GIC 式分工 |

### 11.5 复位与启动流程

把"陷入"反过来看就是"上电启动"——核如何从复位进入第一条指令：

| 复位后状态 | 值 | 来源 |
|------------|-----|------|
| 特权级 | **M 态**（pm=2'b11） | `ct_cp0_regs.v` 复位值 |
| 起始 PC | **复位向量基址 MRVBR** | `mrvbr_reg ← biu_cp0_rvba`（来自外部引脚 `pad_core_rvba`，每核可不同） |
| 中断 | 全关（MIE=0） | mstatus 复位 |
| 地址翻译 | 关（satp=0，裸机物理寻址） | satp 复位；属性走 sysmap PMA（§8.5） |
| Cache | 全 invalid（需预热） | tag valid 位复位清零 |
| 核 ID | 每核唯一 hartid | `biu_cp0_coreid ← pad_core_hartid[2:0]` |

**典型启动序列**：复位 → M 态从 MRVBR 取第一条指令 → 初始化（配 PMP 划区、建页表、
开 cache、设 mtvec）→ 必要时 `mret` 降到 S 态跳入 OS。**多核 SMP**：各核同时从各自
MRVBR 启动，通常约定一个 boot hart 做初始化、其余 secondary hart 自旋等 IPI（msip）
唤醒——这正是 §11.2 CLINT 软件中断的用武之地。

## 12. 低功耗与时钟门控

高性能核的功耗大头是**时钟翻转的动态功耗**。C910 的省功耗哲学贯穿全文，这里系统收口
（H&P 第 1 章「功耗墙」、附录「能效」）。

### 12.1 细粒度三级时钟门控（RTL: `clk/rtl/gated_clk_cell.v`）

所有时序逻辑的时钟都过一个 ICG（集成时钟门控）单元 `gated_clk_cell`，使能式为：
```
clk_en = ( global_en && (module_en || local_en) ) || external_en
         ▲全局总开关        ▲模块级    ▲局部细粒度    ▲旁路(扫描/特殊)
```
**三级层次**让"全局/模块/局部"逐层关断：全局关则全停；模块级关则整单元停；局部 `local_en`
做最细的"这一拍这个寄存器组有没有活"。**全设计共 748 个 ICG 实例、分布在 247 个文件**
——几乎每个流水级、每个队列都有自己的门控时钟。这就是文中反复出现的 `*_gateclk_vld`
信号（如 `rtu_cp0_expt_gateclk_vld`）的来源：**没活干的块，时钟根本不翻转**。

### 12.2 全部省功耗手法汇总

C910 的低功耗手法分两大类——**硬件自动**做的，和**软件可控开关**的。

**(A) 自动硬件手法**（无需软件干预，时刻在省）：

| 手法 | 所在 | 省什么 |
|------|------|--------|
| **细粒度时钟门控** | §12.1 | 全设计 **278 个 `gateclk_vld`**——逐 ROB 表项 / 逐发射队列项 / 逐流水级"有活才开钟" |
| **way-predict** | §4.3 / §8.2 | 只读预测命中那一路 SRAM，省约一半 I-Cache Data 读功耗 |
| **per-bank 精确激活** | §4.3 / §8.2 | 只唤醒目标 bank 的 SRAM（CEN 精确使能） |
| **Loop Buffer** | §4.2 | 小循环期间完全不访问 I-Cache 与分支预测器 |
| **变延迟乘除** | §6.2 / §6.5 | DIV/FDIV 按操作数有效位宽迭代（`skip_srt`/提前结束）——小操作数少迭代、少翻转 |
| **BIU 通道门控** | §10.6 | 读/写/侦听每通道独立门控；读写全空拉 `no_op` 静默总线 |
| **L2 可编程延迟** | §8.4 | 配低速低功耗 SRAM |
| **预取机会化丢弃** | §7.4 PFU | 预取资源紧张直接放弃，不硬撑 |

**(B) 软件可控开关**（mhcr / mhint CSR）——**常被忽视的一大类:几乎每个耗电的推测功能
都能被软件单独关闭**，在功耗敏感、或分支/访存行为规律差（预测净亏）的代码段省动态功耗：

| CSR | 可逐项开关的功能 |
|-----|------------------|
| **mhcr** | I-Cache(ie) · D-Cache(de) · 写分配(wa) · 写回(wb) · **RAS(rse)** · **BHT 方向预测(bpe)** · **BTB(btbe)** · **间接预测(ibpe)** · **L0-BTB(l0btbe)** |
| **mhint** | **D/I-Cache 预取(dcache/icache_pref_en)** · **L2 预取(l2pld)** · **way-predict(iwpe)** · **loop(lpe)** · 预取距离 · ECC 使能 |

> **关键认识**：分支预测器、预取器、way-predict 这些"赌一把省时间"的结构**自身要耗电**
> （每拍读 SRAM、更新状态）。当代码预测命中率低时，开着它们反而净亏——所以 C910 把它们
> 做成 **可逐项关断**，让软件按场景权衡"预测收益 vs 预测功耗"。这是教科书很少提、但商用核
> 必备的一层低功耗手段。

### 12.3 WFI 低功耗模式（RTL: `cp0/rtl/ct_cp0_lpmd.v`）

`wfi` 指令进入 LPMD（low-power mode）状态机（`ct_cp0_lpmd.v`，**3 态**）：执行到
`inst_lpmd_ex1_ex2` → **IDLE → WAIT**（向 BIU 发请求、等总线排空 `lpmd_ack`）**→ LPMD**
（停掉核心时钟）→ 输出 `cp0_biu_lpmd_b` / `cp0_had_lpmd_b` 告知 BIU 与调试模块；
**任一使能中断 `regs_lpmd_int_vld` 到来即唤醒**回 IDLE。这是"无事可做时整核休眠、
来活立刻醒"的标准 WFI 实现——注意进 LPMD 前必须先等 BIU **ack**，确保在飞的总线事务
落定、不丢数据。

> **低功耗范围说明（重要）**：开源 C910 RTL 里**没有**显式的电源门控（power gating）、
> 状态保持（retention）或电压域信号——核内低功耗手段是 **细粒度时钟门控（§12.1，748 个
> ICG）+ WFI 整核时钟停** 两层。真正的"断电休眠"（power domain 切断、DVFS 调压调频）
> 属 SoC 集成层，由片外电源管理实现，不在核 RTL 范围内。换句话说：**C910 核做的是
> "省着翻转时钟"，不是"断电"**。

**取舍**：细粒度门控省动态功耗显著，但每个 ICG 有面积/布线代价、且门控使能在关键路径上
要提前一拍算好；激进的整核休眠省得多但有唤醒延迟。C910 选择"门控做到极细 + WFI 整核
休眠"两手都要——这是电池/散热受限的应用级核的典型选择。

## 13. 物理内存保护 PMP 与 可观测/调试（PMU / HAD）

### 13.1 PMP 物理内存保护（RTL: `pmp/rtl/ct_pmp_*`）

**先理解 PMP 解决什么问题**：MMU 页表管的是"虚拟地址能不能访问"，但有两类场景页表管不了——
①机器态裸跑（MMU 关闭，无页表）；②要防止连 S 态（OS 内核）都不能碰的区域（如安全固件、
TEE 飞地）。PMP 在**物理地址**这一层、由 **M 态**设置一组"谁能访问哪段物理内存"的规则，
是隔离与可信执行（TEE）的硬件地基（RISC-V 特权规范 PMP 章）。**思想**：MMU 是"翻译 + 权限"，
PMP 是翻译之后再加一道"物理层闸门"——纵深防御。

| 项目 | C910 |
|------|------|
| 区域数 | **8 个**（pmpaddr0~7，cfg 打包在 pmpcfg0） |
| 匹配模式 | OFF / TOR（区间） / NAPOT（2 次幂对齐）；**NA4 未实现**（硬连 0） |
| 权限 | R / W / X + **L（锁）** |
| 粒度 | **最小 4KB**（非规范允许的 4B，地址右移 12 位） |
| 最大区 | 1TB（NAPOT） |
| 检查时机 | **地址翻译之后**查物理地址，5 个并行检查器（3×访存 + 预取 + PTW 取指） |
| 违例 | 抛 access fault 异常 |

**M 态语义的两个要点**：①无规则匹配时 **M 态默认全通（RWX）**、S/U 态默认全禁——
所以裸机 M 态不配 PMP 也能跑；②**带 L 锁的规则连 M 态自己也受约束**（且锁定后只有复位
能改），这是安全启动里"M 态自缚手脚、防止被攻破后乱改内存"的关键。配合 **MPRV** 位，
load/store 可按 MPP 的特权级查 PMP（M 态代访 U 态内存的场景）。

> 注意 PMP 只管"能不能访问"，"能不能缓存/是否强序"等内存属性由 MMU 的 XMAE/sysmap 管（§8.5）。

**三种匹配模式背后的编码思想——一个寄存器怎么同时编码"基址 + 大小"**：
- **TOR（区间）**：用相邻两项 `pmpaddr[i-1] ≤ addr < pmpaddr[i]` 划区间，大小任意，但要两个
  寄存器配合。
- **NAPOT（自然对齐 2 次幂）——一处精妙的单寄存器编码**：把"基址 + 大小"塞进**一个**地址
  寄存器，靠**末尾连续 `1` 的个数**表示大小：末位为 `0`→4KB、`…01`→8KB、`…011`→16KB……
  末尾 k 个 1 即 2^(k+3) 字节，且基址自动按该大小对齐。匹配只需一次"掩码 & 比较"。
  **用编码技巧把两个量压进一个寄存器、再用一次按位运算判完**——这是体系结构里反复出现的
  方法（同类还有浮点隐含位、cache tag 复用地址位）。
- C910 **不实现 NA4**（4 字节粒度），最小 4KB——4B 粒度的比较器代价高、用得少，砍掉这个
  昂贵极端档是典型取舍。

**为什么"翻译之后查 + 5 个并行检查器"**：PMP 查的是物理地址，必须排在 MMU 翻译之后；而
一拍内可能同时有多笔访存/取指要查（3 访存 + 预取 + PTW），故复制 **5 个并行比较器**让 PMP
不成为流水线瓶颈——**空间换吞吐**的又一例。

### 13.2 PMU / HPCP 硬件性能计数器（RTL: `pmu/rtl/ct_hpcp_*`）

PMU 是性能分析的眼睛（前文 §9.5 的瓶颈定位全靠它）：

| 项目 | C910 |
|------|------|
| 固定计数器 | 2 个：`cycle`（周期）、`instret`（退休指令数），均 64 位 |
| 可编程计数器 | **16 个**（`mhpmcounter3~18`），64 位，各自经 `mhpmevent` 选 1 个事件 |
| 可计事件 | **42 种**（6 bit 事件号） |
| 溢出中断 | 有：`mcntinten`/`mcntof`（每计数器一位，类 Sscofpmf）——溢出可触发中断做采样 |
| 计数控制 | `mcountinhibit` 逐计数器开关 + 按特权级过滤（PMDM/PMDS/PMDU 分别屏蔽 M/S/U 态计数） |
| 访问 | M 态读写、S 态可见、U 态只读 |

**超标量友好——一拍可加多**：计数加法器是 4 bit，`instret` 一拍把 3 个退休槽（每槽含
折叠指令）累加，可一次 +6；`event20`（寄存器分配失败）可把 8 条管线一拍累加。**否则
3 发射核的退休计数会失真**。

**42 个事件里最该知道的几类**（对照 §9.5 调优）：
```
取指/分支:  icache访问/miss、BHT误预测、跳转误预测、conditional/jump 退休数
TLB:        iutlb/dutlb/jtlb miss
访存:       dcache 读/写 访问与 miss、SQ discard、跨4K stall、spec fail（顺序违例）
顶层 stall:  frontend stall、backend stall、sync(fence) stall
指令构成:    IR 级 ALU/load-store/vector/CSR/sync/FPU/ecall 指令数
```

**怎么用 PMU 做性能分析——通用方法（这才是 PMU 的价值）**：
1. **选事件**：给 `mhpmcounter3~18` 各自的 `mhpmevent` 写上要计的事件号；
2. **圈定区间**：清零计数器，用 `mcountinhibit` 精确框住要测的代码段（启停计数），跑目标代码；
3. **读差值、算比率**——**裸计数没意义，派生指标才有**：
   - **IPC** = instret / cycle（越接近 3 越好，§3.2）——总体效率；
   - **分支误预测率** = BHT 误预测 / 分支数 → 前端瓶颈（§4）；
   - **MPKI**（每千条指令 miss）= dcache miss / instret × 1000 → 访存瓶颈（§7）；
   - **前端/后端 stall 占比** = frontend/backend stall / cycle → 是"喂不饱"还是"咽不下"（§9.5）；
4. **采样剖析（profiling）**：把某计数器设成"快溢出" + 开 `moie` 溢出中断，**每溢出一次就在
   中断里记下当前 PC**，积累出按 PC 的热点分布。这正是 `perf`/`gprof` 这类工具的硬件基础——
   **用"计满即中断"把连续的性能事件变成可统计的采样点**。

**为什么超标量计数必须"一拍可加多"**：若加法器只能 +1，3 发射核一拍退休 3 条时 instret 就
少计了。所以 instret 加法器是多 bit、一拍把 3 个退休槽累加——**计数器的累加宽度必须匹配
被计事件的并行度，否则测量本身就失真**。这是一个容易被忽视、却决定 PMU 是否可信的细节。

### 13.3 HAD 调试与跟踪（RTL: `had/rtl/ct_had_*`）

**先理解硬件调试的核心思想——"停核 + 注入指令 + 借指令窥探"**。调试器（GDB 那头）并不能
凭空读核内部的寄存器和内存，它的通用套路是：
1. **halt**：通过 JTAG 让核进入调试态，流水线停在一个干净的边界（像一次特殊的"陷入"）；
2. **注入指令**：调试态下关掉正常取指，改由调试模块往 IFU **喂指令**（`had_ifu_ir`）；
3. **借指令窥探**：想读 `x5`？注入一条把 `x5` 送出去的指令，结果经 WBBR 回读给调试器；
   想读/写内存？注入 load/store——DDC 还能**自动合成 `mv`+`sd` 序列**替你搬一片内存；
4. **resume**：看够了恢复现场、跳回原 PC 继续跑。

**所以"调试能力"是用『注入指令 + 观察其结果』间接搭出来的**——这是一切 run-control（JTAG）
调试器的通用原理。RISC-V Debug Spec 的 program buffer / abstract command 本质也是这套，只是
C910 用了 C-SKY 私有的 HACR 寄存器体系来实现。理解了这个套路，下表的每一项就都是它的零件：

C910 用的是**玄铁/C-SKY 自有的 HAD 调试协议**（HAD v2.3），**不是 RISC-V Debug Spec**：

| 维度 | C910 HAD | 对比 RISC-V Debug |
|------|----------|-------------------|
| JTAG | TAP + **16 位 IR（HACR）**，含 bank/index/core 选择 | 标准 5 位 IR + DMI |
| 取数寄存器 | HAD_ID/PC/CSR/WBBR/BABA… 多 bank | dmcontrol/dmstatus/abstractcs |
| 进入调试 | `had_rtu_*_dbgreq`（JTAG break / 硬件断点 / trace） | `haltreq` |
| 调试态执行 | 直接往 IFU 注入指令 `had_ifu_ir` + WBBR 回写 | program buffer |
| 硬件断点 | **2 个**（BABA/BAMA 地址掩码匹配 + RC 取反 + 8 位过 N 次计数 + BC 条件：取指/分支/load/store） | tdata1/2/3 触发器 |
| DDC | 调试数据通道：扫入地址/数据，硬件合成 `mv/sd` 指令搬内存 | abstract memory access |
| PCFIFO | **16 项**，记录退休的控制流跳转目标 PC（一拍可写 3 条） | — |
| 跟踪 | OTC 计数器：每退休 N 条触发一次 halt 做采样（非包流式 trace） | CoreSight ETM |
| 多核 | **ETM 交叉触发总线**：一核进/出调试，广播让其他核一起 halt/resume | haltreq 广播 |

**最值得记的两点**：①**断点带"过 N 次再停"计数器 + 链式触发（SQC）**，能调"第 N 次循环
才断"这类难题；②**多核 halt-all 交叉触发**，一核停则全簇停，方便调多核竞争 bug。

> 这部分是 C910 的"非教科书"工程实现：用成熟的 C-SKY HAD 体系而非新生的 RISC-V Debug Spec，
> 体现了玄铁脱胎于 C-SKY 处理器家族的历史路径。

### 13.4 可测试性设计（DFT）

量产芯片必须可测，C910 RTL 内置标准 DFT 钩子：
- **扫描链（scan）**：`pad_yy_scan_mode` / `scan_en` 进入扫描测试模式。**每个 ICG 时钟
  门控单元都有一根 `pad_yy_icg_scan_en`**——扫描时强制开门钟，否则门控会挡住扫描移位。
  这正是 §12 时钟门控与 DFT 的接口约定（也解释了"为什么每个 ICG 都留一根 scan_en"）。
- **MBIST（存储器内建自测）**：对 I/D-Cache、L2、TLB、各 SRAM 阵列做产测自检（`mbist`/`bist`）。
- L1/L2 的 **ECC**（§8.2/§8.4）既是运行期可靠性，也辅助产测筛除坏 SRAM 位。

> DFT 看似与体系结构无关，却解释了门控、SRAM、ECC 设计里那些"测试用"端口的由来——
> 可测试性是商用 IP 的硬约束。

## 14. 端到端数据流走查（把所有单元串起来）

前面分单元讲了"零件"，这一节把它们装成"整机"——用四条典型指令的全程，串起 §3~§13
的每个结构。**读懂这四条走查，就能完整复述这颗处理器如何工作。**

### 走查一：一条 ALU 指令的一生（理想直通路径）

```
PCGEN  L0-BTB(0拍)/BTB 给出取指 PC                                      §4
IF/IP  I-Cache(VIPT,2路) 命中，way-predict 只点亮一路；predecode 标边界    §4/§8.2
IB     打包进 IBUF(32 项)                                               §4.3
ID     3 译码器之一解码                                                  §5
IR     RAT 分配整数 preg（消除 WAR/WAW）；preg 不够则在此 stall           §5.1/§9.5
IS     派进 AIQ0/AIQ1（深 8）；唤醒-选择，源就绪即发射                     §5.2
RF     读 PRF + 前递网络旁路                                            §6.2
EX1    ALU 算出结果，立刻前递（back-to-back 依赖下一拍可发）              §6.2
EX2    写回 PRF；CBUS 报 ROB"已完成"                                    §6.4/§9.2
退休    ROB 按序到它 → 提交，preg 经 PST 进 RETIRE 态                    §9.2/§9.4
```
**一句话**：顺序前端取来、乱序中段执行、顺序后端退休——延迟 1 拍，全程无气泡。

### 走查二：一次 load miss 的全程（存储层次总动员）

```
load 在 LSIQ(深 12)发射 → AG 算 VA → D-uTLB 翻译得 PA（miss 则 JTLB→PTW，§8.5）
 → DC 查双 tag + 比 SQ 前递（bytes_vld 字节位图，§7.3）
 → DA 判定 L1 miss → 登记 RB(8 项，决定 MLP≈8)                          §7.4
 → BIU read_channel 上 ACE AR（按 AXI ID 跟踪）                         §10.6
 → CIU 查 snoop filter：别核有副本就侦听(可 cache-to-cache)，否则下查 L2  §10.3
 → L2(16 路, 2 bank, 5 级流水) 命中则返数据；miss 再经 CIU 出 AXI4 到 DDR §8.4
 → 关键字优先：要的那个字先经 R 通道交付 ld_wb，load 不等整行            §7.4
 → 整行入 LFB → 写回 D-Cache（FIFO 选受害路，脏行经 VB 逐出）            §8.3
```
**一句话**：RB 让后续无关访问继续跑（非阻塞），关键字优先把有效延迟压到最短，
BIU/CIU/L2 一路把数据捞回来。

### 走查三：一次分支误预测的恢复（前端抢跑 + 后端精确清理）

```
BJU 在 EX1 发现误预测（方向或 jalr 目标错，对比 PCFIFO 预存值）          §6.2
EX2 三枪齐发：① iu_ifu_chgflw 让 IFU 立刻从正确目标取指（抢回延迟）
            ② cancel 杀 IU 错误路径   ③ mispred_stall 把新指令卡在 ID    §6.2
后端继续跑老指令（错误路径被 cancel 压住，重命名表此刻是污染态）
分支退休 → RTU flush 状态机：FLUSH_IS → 等 pipeline empty → FLUSH_BE
 → 发 rtu_yy_xx_flush：RAT 用 PST 的 RETIRE 态位图一拍重建、推测态全蒸发   §9.3/§9.4
 → 放行新路径指令
```
**一句话**：前端早重定向抢回取指延迟，后端按序 flush 保证精确状态——快与对兼得。

### 走查四：一次跨核一致性访问（MOESI 上场）

```
core1 要读 core0 改过的行：core1 load miss → BIU → CIU                  §10.6/§10.3
CIU 查 snoop filter（cp[3:0] 位图）→ 命中 core0 → SNB 向 core0 发 AC
core0 的 SNQ(6 项)借 load 管线读出脏行 → 经 CD 通道给 CIU（CTC）         §7.2/§10.3
CIU 直接把数据转发 core1（cache-to-cache，不经 DDR）                     §10.3
状态迁移：core0 M→O（仍持脏、允许他人读），core1 I→S，L2 记 dirty+shared  §10.2
```
**一句话**：MOESI 的 O 态让脏行在核间直接传递、暂不写内存——这是 §10 多核一致性的精华。

## 15. 核心体系结构权衡总表（对照教科书）

这是本文最该记住的一张表——C910 每个"为什么这么设计"的浓缩：

| 设计点 | C910 的选择 | 取舍 / 动机 | 教科书坐标 |
|--------|-------------|-------------|-----------|
| 执行模型 | 乱序 + 重命名 + 推测 | 挖 ILP，代价是复杂的恢复逻辑 | H&P 3 章 / Tomasulo |
| 重命名方式 | 统一物理寄存器堆 + RAT | 比"ROB 存数据"省数据搬移 | R10000/Alpha 21264 学派 |
| 发射队列 | 分布式 7 队列各 8 项 | 端口少、时序好（高频）；代价是负载不均 | Shen&Lipasti 分布式 RS |
| 整数 preg 数 | 96 项 | 窗口大小 vs 寄存器堆端口面积 | 端口面积∝容量² |
| 分支方向预测 | Bi-Mode BHT 64Kb | 解决 2-bit 计数器别名污染 | McFarling/Bi-Mode |
| 目标预测 | L0-BTB(0拍)+BTB(1拍) 分级 | 热点零延迟 vs 容量 | 分级预测 |
| 误预测恢复 | 早重定向前端 + 晚 flush 后端 | 抢回取指延迟 + 保证精确 | 精确异常 |
| ROB | 64 项瘦表项，外包 PC/数据/异常 | 极致省面积，"只管序不管值" | C910 工程亮点 |
| 退休 PC | 增量重建（1 加法器） | 替代 64×39 位 PC 存储 | 面积优化 |
| 重命名恢复 | PST RETIRE 态位图重建 RAT | 免 checkpoint / 免 ROB walk | 对比 21264 checkpoint |
| I/D Cache 索引 | VIPT / PIPT 分用 | 取指省周期 / 访存避别名 | H&P 2 章 cache 别名 |
| Cache 替换 | I-Cache FIFO（非 LRU） | 1 bit vs 计数器，省面积 | 替换策略权衡 |
| 非阻塞 cache | RB 8 项 → MLP≈8 | 隐藏 miss 延迟 | hit-under-miss |
| miss 交付 | 关键字优先 | 缩短 load 有效延迟 | critical word first |
| store→load | 前递 / 重发，不拼接 | 数据通路简单换偶发重发 | store-to-load forwarding |
| 访存依赖 | spec_fail_predict 预测器 | flush 太贵，学一次免疫 | store-set / MDP |
| 长延迟单元 | DIV/MULT 搭 ALU 管线 | 共享端口省面积 | 资源共享 |
| 浮点异常 | 不 trap，用 fflags | 简化精确异常逻辑 | IEEE 推荐 |
| ISA 扩展 | XIE(xtheadc) 硬件复合指令 | +40% CoreMark | ISA 是体系结构核心 |
| 一致性 | MOESI + 集中侦听过滤 | 小规模 SMP 的成本平衡 | H&P 5 章 |

## 16. 与经典处理器的横向对比

把 C910 放进体系结构史的坐标系，更容易理解它"取了谁、舍了谁"：

| 维度 | C910 | MIPS R10000 (1996, 教科书经典) | Alpha 21264 (1998) | ARM Cortex-A72 (同代对标) |
|------|------|-------------------------------|--------------------|---------------------------|
| ISA | RV64GC+XIE | MIPS IV | Alpha | ARMv8-A |
| 译码宽度 | 3 | 4 | 4 | 3 |
| 乱序窗口(ROB/等价) | 64 | 32 | 80 (in-flight) | ~128 |
| 物理寄存器(整数) | 96 | 64 | 80 | ~128 |
| 重命名 | 统一 PRF + RAT | 统一 PRF + active list | PRF + checkpoint | 统一 PRF |
| 分支方向预测 | Bi-Mode | 2-bit | 局部+全局锦标赛 | 锦标赛 |
| 误预测恢复 | PST 位图重建 | active list 回滚 | checkpoint 回滚 | — |
| L1 I/D | 64K/64K 2路 | 32K/32K 2路 | 64K/64K 2路 | 48K/32K |
| 访存乱序 | LQ16/SQ12 + MDP 预测 | 顺序 LSU | load 推测 + 重放 | 乱序 LSU |
| 流水深度 | 12 | ~6 | 7 | 15 |

**C910 的定位**：微架构思想上是 R10000/21264 这一脉乱序核的 RISC-V 现代复刻，但在
**省面积/省功耗的工程取舍**上比教科书核走得更远（瘦 ROB、增量 PC、位图恢复、FIFO 替换、
长延迟单元搭车）。它不追求 Intel/Apple 那种超宽超深（8+ 宽、200+ 窗口）的极限性能，
而是在"够用的乱序能力 + 高频 + 可接受面积"之间找平衡——这正是嵌入式/边缘应用级核的
典型工程哲学。

### 关于物理实现指标（PPA）的说明

> **主频、面积、功耗（PPA）不在 RTL 里，取决于工艺库与后端实现，需查官方数据手册。**
> 本文所有数字均来自 RTL（结构性参数），PPA 属实现层：同一份 RTL 在不同工艺/库/约束下
> 主频面积都不同。可公开参考的量级——C910 在 **12nm 级工艺约 2.0~2.5 GHz**；ISA 扩展对
> 性能的贡献在 §2 已量化（CoreMark 4.4→6.1）。**精确 PPA 请以目标工艺的综合/后端报告或
> T-Head 官方 datasheet 为准**，不要把本文的结构参数当成 PPA 指标。
